      Lesson 11

      Full-Text Search

      Finding text is only part of search. Users also need useful ordering, sensible handling of typos and fast responses. Learn how inverted indexes and text analysis support those goals, and how PostgreSQL and Elasticsearch approach the problem.

      From substring matching to useful search

      A small catalog can start with a simple substring query. For an existing products table, the following searches its name and description using a case-insensitive pattern. The application binds $1 to a value such as %laptop%.

      PostgreSQL — a bounded substring search
      SELECT id, name, description
FROM products
WHERE name ILIKE $1 OR description ILIKE $1
ORDER BY id
LIMIT 20;

      % matches any sequence of characters and _ matches one character. Binding the pattern avoids SQL injection, but these wildcard meanings still apply. If the API promises literal substring search, escape user-supplied wildcards and the escape character before adding the surrounding % characters.

      This query answers whether the pattern occurs. It does not decide whether a laptop is a better result than a laptop bag, correct a typo such as laptpo, or infer that a product is a laptop when no searchable text says so. Ordering by ID is predictable, but is not relevance ranking.

      The query and index determine the work

      A leading-wildcard search without a suitable index may scan many rows. A normal B-tree usually cannot make an arbitrary %term% search efficient. That does not mean relational databases must always scan every row: PostgreSQL has both full-text indexes and trigram indexes for different search needs.

      As the catalog and traffic grow, define the required behavior first: literal substrings, words, phrases, prefixes, spelling variants or meaning. These are different contracts with different costs. A row count alone cannot tell you which system is necessary.

      Key takeaways

      • ILIKE matches a pattern; relevance, typos and semantic relationships need additional design.
      • Bound queries, bind values and define whether user input contains literal text or wildcards.
      • Search performance depends on the query, available indexes and workload.

      The inverted index

      A direct approach asks each document whether it contains a term. An inverted index records which documents contain each term, allowing a query to start from the term instead. The mapping is inverted: document-to-words becomes word-to-documents.

      A small document collection
      D1: Introduction to machine learning
D2: Coffee machine manual
D3: Learning to cook

Illustrative postings lists after lowercasing:
machine  → D1, D2
learning → D1, D3

      A query requiring both terms can intersect those lists and find D1. A query allowing either term can combine them and find D1, D2 and D3. A postings list can carry document identifiers, occurrence counts and term positions, depending on the index configuration.

      Positions help distinguish the phrase “machine learning” from two words scattered throughout a long document. They normally refer to token positions, not physical book page numbers. The index narrows candidates; ranking then decides their order. It does not by itself make every matching document useful.

      The cost moves partly to ingestion: the system analyzes documents and maintains search structures as data changes. Storage and indexing work increase in exchange for avoiding repeated scans at query time. Broad queries can still match a large part of the collection.

      Key takeaways

      • An inverted index maps terms to documents containing them.
      • Combining postings finds candidates; positions support phrase and proximity behavior.
      • Faster retrieval requires indexing work and storage, and still needs relevance ranking.

      Analysis: turning text into searchable terms

      Search engines usually transform text before indexing it. A typical analysis pipeline splits text into tokens, normalizes them and applies optional language rules. The chosen pipeline determines what can match later.

      StepPurposeDesign concern
      TokenizationIdentify searchable pieces of text.Word boundaries, punctuation and identifiers vary by language and domain.
      NormalizationMake selected variants comparable, such as upper- and lowercase.Case and accents can be meaningful for some fields.
      StemmingReduce related word forms toward a common searchable form.Language-specific rules can also merge terms you intended to keep distinct.
      Stop-word handlingOptionally remove common words.Removing words can matter for names, phrases and short queries.
      SynonymsApply configured relationships between terms.Domain-specific synonyms require maintenance and relevance testing.

      PostgreSQL calls normalized searchable forms lexemes and stores them in a tsvector. Its query representation is a tsquery. Elasticsearch uses field analyzers for indexed text and compatible search analysis for queries. PostgreSQL text-search concepts.

      Lowercasing an entire query string manually is not a substitute for using the correct analyzer. Product codes, English reviews and multilingual names may need different handling. Test how both documents and queries are analyzed, including punctuation and inputs that reduce entirely to stop words.

      Key takeaways

      • Analysis determines the terms that exist in the index and how a query matches them.
      • Stemming, stop words and synonyms are configurable behavior, not universal defaults.
      • Use compatible index and query analysis suited to the field's language and purpose.

      Relevance, BM25 and field boosting

      Matching selects candidates; scoring orders them. Elasticsearch uses BM25 as its default text similarity. You do not need to derive the formula to use it, but its main signals help explain surprising results.

      SignalIntuition
      Term frequencyMore occurrences in a field can increase relevance, with diminishing returns.
      Document frequencyA term found in fewer documents is generally more discriminating.
      Field lengthLength normalization prevents long text from winning simply by containing more words.

      BM25's k1 controls term-frequency saturation and b controls length normalization. These are tuning parameters, not a reason to change defaults without evidence. Elasticsearch similarity settings.

      The title is important because you say it is

      A field named title does not automatically receive a special business priority. A query can explicitly boost it relative to a description. For a product index with those analyzed fields, this is one possible query:

      Elasticsearch query body — product field boosts
      {
  "size": 20,
  "query": {
    "multi_match": {
      "query": "lightweight laptop",
      "fields": ["title^3", "description"],
      "operator": "and"
    }
  }
}

      The boost changes score contributions; it does not guarantee a particular product is first. This default multi_match mode requires both terms within a matching field when operator is and. Combining words across separate fields requires a query mode designed for that behavior. Multi-match behavior and boosts.

      A relevance score is not a probability that a result is correct. Boosts, corpus statistics and query structure affect it. If “MacBook” should match “laptop” without a shared term, provide suitable product metadata, synonyms or a separate semantic retrieval capability. Lexical scoring does not invent that relationship.

      Key takeaways

      • BM25 uses frequency, rarity and length normalization to rank lexical matches.
      • Field boosting is an explicit query choice; more occurrences do not always mean a better result.
      • Scores need evaluation against real search intent and are not correctness probabilities.

      Typos, autocomplete and meaning

      These features often appear together in a search box, but solve different problems. A fast full-text index does not automatically enable every one of them.

      FeatureExampleTypical mechanism
      Typo tolerancelaptpo should find laptop.Fuzzy matching based on allowed character edits or a spelling-correction workflow.
      Autocomplete / typeaheadlap should suggest laptop-related results.Prefix-aware queries, n-gram indexing or a dedicated suggestion field.
      Synonym matchingA domain treats two names as equivalent.Configured synonym rules or enriched searchable metadata.
      Semantic retrievalFind a relevant concept without shared words.A separate meaning-based retrieval approach, possibly combined with lexical results.

      Elasticsearch's match query supports configurable fuzziness. It expands possible term matches; it does not understand every sentence or guarantee the intended correction. Excessive expansion can increase cost and introduce irrelevant results. Do not assume fuzzy matching is appropriate for exact identifiers such as order numbers. Full-text query options.

      For typeahead, Elasticsearch has a search_as_you_type field with supporting subfields, commonly queried with multi_match and bool_prefix. Choose the mapping and query together rather than wrapping each keystroke in leading wildcards. Search-as-you-type fields.

      In the UI, debounce rapid input, limit suggestion counts and ignore stale responses that arrive after a newer query. Set minimum input lengths and sensible timeouts. A familiar search interface demonstrates a product behavior; it does not reveal whether its provider uses Elasticsearch, Lucene or a proprietary retrieval system.

      Key takeaways

      • Typo tolerance, prefixes, synonyms and semantic retrieval are distinct capabilities.
      • Fuzzy matching requires configuration and can add cost and false positives.
      • Typeahead needs a compatible index, bounded queries and protection against stale UI responses.

      PostgreSQL full-text search

      PostgreSQL can analyze text, index searchable lexemes and rank matches without a separate search service. The following standalone example models the review-and-sentiment dataset from the lecture. Apply schema changes through migrations as covered in Databases & PostgreSQL.

      Example schema — an analyzed vector and GIN index
      CREATE TABLE reviews (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    review text NOT NULL,
    sentiment text NOT NULL CHECK (sentiment IN ('positive', 'negative')),
    search_vector tsvector GENERATED ALWAYS AS (
        to_tsvector('english', review)
    ) STORED
);

CREATE INDEX reviews_search_vector_idx
    ON reviews USING GIN (search_vector);

      The stored generated column keeps the vector synchronized when the review changes. GIN supports efficient lookup of matching lexemes. Explicitly selecting the language configuration makes the indexing behavior reproducible. PostgreSQL text-search tables and indexes.

      Query — bind the user's search text to $1
      WITH input AS (
    SELECT websearch_to_tsquery('english', $1) AS query
)
SELECT r.id, r.review, r.sentiment,
       ts_rank_cd(r.search_vector, input.query) AS rank
FROM reviews AS r
CROSS JOIN input
WHERE r.search_vector @@ input.query
ORDER BY rank DESC, r.id
LIMIT 20;

      websearch_to_tsquery accepts ordinary text and supports quoted phrases, OR and negation. @@ tests a match; ts_rank_cd provides a ranking that considers proximity. These built-in ranks are not Elasticsearch's BM25 scores. The GIN index helps find matches; it does not directly provide the final rank order. PostgreSQL query construction and ranking.

      Keep binding user values instead of interpolating SQL. The same English configuration is used on both sides. An empty or stop-word-only query can produce no searchable terms; define that behavior in the API. Indexes still cost storage and write work, so inspect query plans and latency on a representative dataset.

      Key takeaways

      • PostgreSQL full-text search combines tsvector, tsquery, matching and ranking.
      • A generated vector plus GIN index supports indexed lexical search.
      • Use consistent language configuration, bound values and measured query plans.

      Trigrams for substring and similarity search

      If the requirement is still ILIKE '%laptop%', PostgreSQL's pg_trgm extension offers another route. It indexes character trigrams and supports indexed LIKE/ILIKE and similarity operations.

      Optional index for the reviews table — extension must be available
      CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX reviews_review_trgm_idx
    ON reviews USING GIN (review gin_trgm_ops);

SELECT id, review, sentiment
FROM reviews
WHERE review ILIKE $1
ORDER BY id
LIMIT 20;

      Bind $1 to the intended pattern. Trigram support can accelerate the existing substring contract without changing it into word-based search. Very short or broad patterns may provide too few useful trigrams to be selective. Similarity operators can also support typo-related features, with thresholds that need testing. PostgreSQL pg_trgm.

      Full-text and trigram indexes solve different problems. Add each only for the queries that justify its storage and maintenance cost; installing both is not a prerequisite for search.

      Key takeaways

      • Trigram indexes can support substring matching and similarity searches.
      • Short, broad patterns can remain expensive.
      • Choose word-based or character-based indexing from the required behavior.

      Elasticsearch documents, mappings and Lucene

      Elasticsearch exposes search and indexing APIs around a distributed data store. An Elasticsearch index groups documents; a document is a JSON representation of an entity. A mapping describes how fields are interpreted and indexed. This use of “index” is broader than one SQL index on a table column.

      Elasticsearch builds on Apache Lucene: each Elasticsearch shard contains a Lucene index. PostgreSQL implements its own full-text facilities; it does not need Lucene to offer text search. Different products can use the same general inverted-index idea. Elasticsearch shards and Lucene.

      PUT /reviews — mapping for a new example index
      {
  "mappings": {
    "properties": {
      "review": {
        "type": "text",
        "analyzer": "english"
      },
      "sentiment": {
        "type": "keyword"
      }
    }
  }
}
      Field typeBehaviorExample use
      textAnalyze a string into searchable terms.Natural-language reviews, titles and descriptions.
      keywordIndex a whole value for exact matching, with optional configured normalization.Sentiment labels, IDs, categories, sorting and aggregations.

      A text field is not “a string without discrimination”: its analysis is precisely what changes matching behavior. A keyword field does not infer synonyms or word forms. When one value needs both analyzed search and exact sorting, a text field can have a keyword subfield. Text fields and keyword fields.

      PUT /reviews/_doc/1?refresh=wait_for — one example document
      {
  "review": "A lightweight laptop with a clear screen.",
  "sentiment": "positive"
}

      Use the source database's stable ID as the document ID when indexing a copy of a row. refresh=wait_for can wait for search visibility in a small read-after-write demonstration; requiring that on every ingestion request has throughput consequences.

      Key takeaways

      • Documents, field mappings and shards are distinct parts of the Elasticsearch model.
      • Use analyzed text for words and keyword fields for exact values.
      • Elasticsearch builds on Lucene; PostgreSQL full-text search is a separate implementation.

      Query DSL: score text and filter exact values

      Elasticsearch's JSON Query DSL describes the search operation. The following example requests positive reviews matching a deliberately misspelled query. It is a fuzzy lexical search, unlike the earlier literal substring query.

      POST /reviews/_search — bounded results and an exact filter
      {
  "size": 20,
  "track_total_hits": true,
  "_source": ["review", "sentiment"],
  "query": {
    "bool": {
      "must": [
        {
          "match": {
            "review": {
              "query": "laptpo",
              "fuzziness": "AUTO"
            }
          }
        }
      ],
      "filter": [
        { "term": { "sentiment": "positive" } }
      ]
    }
  }
}

      match analyzes the input against the text field. fuzziness permits configured spelling variation. The term filter matches the keyword sentiment value exactly. Filter clauses restrict eligibility without adding relevance score; the text clause contributes to _score. Boolean queries and filter context.

      Results appear under hits.hits, with document IDs, scores and selected source fields. The total match count is separate from the returned page. This example explicitly requests exact total tracking; that adds work and is not necessary for every product. In hits.total.relation, eq means an exact count and gte means a lower bound. Also inspect timed_out and shard failures before treating the results as complete. Search response fields.

      Why not pass user input straight into query_string?

      query_string accepts a search mini-language with operators and special characters. It is not the same as plain user text. Wrapping input in *...* can introduce expensive leading-wildcard searches and does not reproduce SQL substring semantics on an analyzed field. Prefer a query suited to the intended contract; expose advanced syntax only when deliberately supported and bounded. Query-string syntax and wildcard costs.

      Key takeaways

      • Use text queries for analyzed matching and keyword filters for exact conditions.
      • Result page size and total match count are different; exact counting can cost more.
      • Raw query syntax and leading wildcards require deliberate controls.

      Keeping the search index synchronized

      When PostgreSQL owns the business data and Elasticsearch holds searchable copies, every create, update and deletion must eventually reach the search index. Two successful inserts during initial setup do not solve ongoing synchronization.

      A common derived-index workflow
      Application transaction → authoritative database + durable change record
                                               │
                                               ▼
                                    indexing worker / change capture
                                               │
                                               ▼
                                        search document
                                               │ refresh
                                               ▼
                                       searchable result

      A durable outbox or change-data-capture pipeline can avoid losing an indexing update between a database commit and a separate network call. Retry with stable IDs and version checks so older events do not overwrite newer data. Handle deletes too, and measure indexing lag. These are applications of Background Jobs.

      Elasticsearch search is near real time: an acknowledged write can need a refresh before it appears in search results. Delivery lag from the database and refresh delay are separate. Near-real-time search.

      Preserve a way to rebuild the index from authoritative data. Analyzer or mapping changes may require reindexing into a new index and switching the application to it. Plan how updates arriving during that rebuild are captured, rather than deleting the live index to start over.

      Search results can be stale. Enforce current authorization and critical stock or price decisions at the appropriate authoritative boundary. A deleted private document must not remain accessible merely because its search copy has not caught up.

      Key takeaways

      • A separate search index needs reliable create, update and delete propagation.
      • Use stable identity, ordering/version protection and observable indexing lag.
      • Plan rebuilds and protect sensitive operations from stale search data.

      Preparing the 50,000-review experiment

      The lecture describes loading 50,000 review-and-sentiment records into PostgreSQL and Elasticsearch, then comparing searches. The following is a reproducibility checklist for that experiment, not a claim that the original dataset or cloud instances were tested here.

      1. Record the dataset: document its source, permitted use and a fixed version or checksum.
      2. Parse CSV correctly: reviews can contain commas, quotes and embedded newlines; use a real CSV parser.
      3. Validate once: create one accepted record set with nonempty review text and the same allowed sentiment values.
      4. Keep identity consistent: use the same record IDs and text in both systems.
      5. Create explicit schemas: document PostgreSQL indexes and Elasticsearch mappings and analyzers.
      6. Load bounded batches: choose sizes by byte volume, limits and measured throughput, not a supposedly universal 1,000-row rule.
      7. Verify completeness: compare IDs and sample values, inspect ingestion errors and wait for search visibility.

      PostgreSQL inserts can use parameterized batches or an appropriate bulk-loading mechanism. Elasticsearch's Bulk API can return successful and failed items in the same response. Inspect each item and retry suitable failures; an HTTP success response alone does not mean every document was indexed. Elasticsearch Bulk API.

      Equal counts are necessary but not sufficient: two collections can each contain 50,000 records while containing different data. Use isolated experiment tables and indexes. A reset-and-reload script must never point at production by accident; keep credentials on the server and separate development resources from live ones.

      Key takeaways

      • Use the same validated records and stable IDs in both systems.
      • Inspect bulk item failures and confirm data is searchable before measuring.
      • Document the corpus and configuration so another person can reproduce the experiment.

      Benchmark the same work

      A demonstration where one request finishes sooner is evidence about those requests under those conditions. It does not establish a universal PostgreSQL-versus-Elasticsearch speed ratio. The lecture's reported timings are illustrative observations, not guarantees for a new deployment.

      ControlWhy it matters
      Matching semanticsSubstring, stemmed-word, fuzzy and phrase searches can match different documents.
      Indexes and analyzersAn unindexed scan versus indexed retrieval tests different access methods, not every capability of each engine.
      Result size and countsReturning every SQL row versus one Elasticsearch page is unequal work. Exact counts must be requested consistently.
      Returned fields and bytesSerialization, transfer and rendering can dominate a large response.
      InfrastructureThe same region does not equal the same CPU, memory, storage, shard layout, network path or service tier.
      Warmth and concurrencyConnection setup, serverless cold starts, caches, background indexing and concurrent load affect timings.

      Separate execution time from user-visible latency

      Measure the client-observed duration consistently around each complete request. Database execution plans and Elasticsearch's took help diagnose server-side work, but are not interchangeable with end-to-end timing. A streamed UI can display each result as it arrives; streaming does not by itself make either query faster or prove the comparison is fair. Elasticsearch's took measurement.

      Use a representative query set, repeated runs and stated concurrency. Report cold and warm behavior separately, include p50/p95/p99 and errors, and record enough samples for those percentiles to be meaningful. Alternating query order helps avoid favoring whichever run consistently gets a warmer system.

      A useful study can compare several approaches: the original substring query, trigram-indexed substring search, PostgreSQL full-text search and Elasticsearch full-text search. Keep semantic differences explicit rather than declaring every query interchangeable. Matching counts alone do not prove equivalent matching or ordering.

      Key takeaways

      • Match semantics, returned data, count behavior and environment before comparing speed.
      • Measure end-to-end and server-side time separately.
      • Use repeated, representative workloads and report distributions rather than one stopwatch result.

      Choosing PostgreSQL or Elasticsearch

      Start with required behavior and measured constraints. PostgreSQL may already supply the indexing and ranking a product needs. A separate search service becomes useful when its search capabilities, independent scaling or operational fit justify another system.

      ConsiderationPostgreSQL approachElasticsearch approach
      Data locationSearch can remain beside authoritative relational data.Often uses a separate searchable representation that needs synchronization.
      Search behaviorNative lexical search, ranking and optional trigram capabilities.A broad search DSL, analysis, fuzzy queries, suggestions and aggregations.
      Scaling and workloadSearch shares database resources unless separately provisioned.Search capacity can be scaled separately, with its own cluster and shard considerations.
      OperationsFewer moving parts when PostgreSQL is already in use.Additional capacity, monitoring, access control, backups and reindexing work.

      The ELK connection

      ELK historically names Elasticsearch, Logstash and Kibana: search and analytics, ingestion and transformation, and exploration and visualization. Log analysis is one use of the Elastic Stack, separate from building a customer-facing product-search API.

      Having a logging deployment provides familiarity, but is not automatic permission or capacity to add product search to the same cluster. Evaluate isolation, access boundaries, retention, latency requirements and the consequences of ingestion spikes. Choose a new dependency only when it solves an actual requirement that the current system does not meet adequately.

      Key takeaways

      • PostgreSQL is a capable search option; Elasticsearch adds capabilities and operational responsibilities.
      • Choose from workload, required features and measured limits.
      • An existing logging stack is useful experience, not proof that sharing it is appropriate.

      Designing and evaluating the search API

      The backend should own the public search contract and translate it into safe engine queries. Clients should not need to know the internal index name, raw query language or cluster credentials.

      1. Validate inputs: bound query length, result limits, filters and allowed sort options; define empty-input behavior.
      2. Apply trusted scope: constrain results to the user's tenant and permissions rather than accepting arbitrary client-supplied scope.
      3. Limit work: use timeouts, bounded pagination and rate limits, especially for fuzzy or wildcard searches.
      4. Return a stable contract: expose only public fields and define result ordering, total-count accuracy and cursor behavior.
      5. Handle failures honestly: distinguish no matches from timeouts, incomplete searches and indexing failures.
      6. Render safely: escape document text and control any highlighting markup; search results can contain untrusted content.

      Authorization applies to counts, snippets, suggestions and aggregations as well as full documents. Filtering only after fetching a page can leak information and distort pagination. Build eligible scope into the query and account for stale permissions when the index is derived. See Authorization and API Design.

      Fast is not enough

      Keep a small evaluation set of real queries with expected useful results: exact names, broad categories, phrases, typos, identifiers, different languages and no-match cases. Check whether relevant items appear near the top, how often useful items are missed and whether irrelevant suggestions appear. Review latency, error rate and zero-result rate alongside relevance.

      Change analyzers, boosts, synonym rules or fuzziness against that evaluation set. More matching results are not automatically better. The useful backend skill is understanding the contract, choosing an appropriate index and measuring both retrieval quality and cost.

      Key takeaways

      • Keep credentials, query construction, limits and authorization on the backend.
      • Protect metadata and suggestions as carefully as full search results.
      • Evaluate relevance and latency together using a representative query set.
