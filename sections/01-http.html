    Lesson 01

    Understanding HTTP

    Backend is enormous. If we tried to cover every component that could possibly be part of it we would be here for years. So we deliberately cover only what shows up in the overwhelming majority of codebases — and nothing shows up more often than HTTP: the medium through which browsers talk to servers.

    statelessness client–server headers methods CORS status codes caching compression TLS
    The scoping rule for this whole course

    There are many protocols clients and servers use to talk to each other. HTTP is one of the most used, so it is the one we go deep on. Everything else you can pick up later, on the job. Throughout, treat HTTP and HTTPS as interchangeable — HTTPS is, to oversimplify, a more secure HTTP. The underlying principles are identical; the extra parts (encryption, certificates, TLS) belong more to network engineering than to us.

    The two ideas at the heart of HTTP

    Almost everything else in this lesson falls out of two design decisions. Learn these two and the rest stops feeling like trivia.

    1. Statelessness

    Statelessness means HTTP has no memory of past interactions. Each request carries all the information the server needs to process it — the method, the URL, the headers, the body. After the server responds, it forgets the request happened. If the client makes another request, the server treats it as a brand new, unrelated event.

    The direct consequence is self-contained requests. Because the server does not remember anything, every request must include whatever it needs: authentication tokens, session identifiers, preferences. Fetching a user profile means sending credentials — a cookie or a token — on every single request, so the server can work out which user is asking.

    Why anyone would design it this way

    Benefit 01

    Simplicity

    The server does not need to store session information, which would otherwise cost resources and add complexity to its architecture.

    Benefit 02

    Scalability

    Requests can be distributed across many servers, because no single server needs to be the one that remembers you. Any instance can answer any request.

    Benefit 03

    Crash resilience

    If a server crashes it does not damage the client's state — there is no session in memory that needs restoring, because there was never a session in memory.

    The catch

    Real applications do need continuity — logins, shopping carts. So because HTTP is stateless, developers layer state management on top of it: cookies, sessions, tokens. That is not HTTP being fixed; that is HTTP being extended. We cover exactly how in Lesson 04.

    2. The client–server model

    In every HTTP exchange there is a client and there is a server, always.

    • The client — typically a browser or an application — initiates the communication by sending a request. It is responsible for supplying everything the server needs: the URL of the resource, the headers, the body.
    • The server hosts resources (web pages, APIs, files) and waits for incoming requests. When one arrives it processes it and sends back an appropriate response: a page, JSON, plain text, an error — any kind of content.
    The rule to remember

    The HTTP protocol states that communication is always initiated by the client, in order to get some response from the server. A server cannot spontaneously start an HTTP conversation with you.

    Key takeaways

    • Stateless: every request is self-contained and the server forgets it afterwards.
    • That buys simplicity, horizontal scalability and crash resilience.
    • Continuity (login, cart) is added on top via cookies, sessions and tokens.
    • The client always speaks first.

    What HTTP actually runs on

    Before anything can be sent, the client and server need a connection — some medium for the conversation. HTTP itself does not insist that the underlying transport be connection-based. It only requires that the transport be reliable: it must not silently lose messages, and at minimum must surface an error when it does.

    Of the two dominant transport protocols on the internet, TCP and UDP, TCP is the reliable one. So HTTP relies on TCP, which is connection-based. TCP in turn establishes that connection with a three-way handshake — worth looking up once, but not worth a detour here.

    Where we live in the OSI model

    The OSI model is the usual reference when talking about sending data over a network. As backend engineers we work almost entirely at Layer 7, the application layer. TCP handshakes and TLS encryption border on the layers below — genuinely good to know about, but a rabbit hole. We will stay at the application layer and keep only a rough sketch of what happens beneath it.

    The versions, and what each one changed

    Over the years HTTP kept redefining how clients and servers send and receive data.

    VersionWhat changedWhy it mattered
    HTTP/1.0 Each request opened a new connection. Inefficient — a connection had to be established and closed for every single request/response pair, which slowed everything down.
    HTTP/1.1 Persistent connections (multiple requests and responses over the same TCP connection), chunked transfer encoding, better caching. Significant performance win. Still the most widely used version.
    HTTP/2 Multiplexing — many requests/responses over one connection. Binary framing instead of text, header compression (HPACK), server push. Servers can send resources before the client asks. Head-of-line blocking still exists at the transport level.
    HTTP/3 Built on QUIC, a transport protocol over UDP rather than TCP. Faster connection establishment, lower latency, better packet-loss handling, and multiplexing without head-of-line blocking.
    All you actually need to carry forward

    Client and server establish some kind of network connection, and messages are sent and received over it. That is the whole prerequisite for everything that follows.

    So the parts, named:

    • Request method — the intent (POST).
    • Resource URL — what we are asking for (/api/v1/notes).
    • HTTP version — here HTTP/1.1, currently the most used.
    • Host — the domain we are addressing.
    • Headers — everything else in that block; the bulk of the message.
    • A blank line — signals the headers are over and the body starts.
    • Body — the payload the client wants to send, or the server returns.
    • On the response side, a status code and reason phrase replace the method/URL line: 200 means OK.

    HTTP headers

    Headers are the major part of both requests and responses, so they deserve the most attention. At the simplest level: headers are key–value pairs of parameters sent with a request or returned with a response.

    Why headers exist at all

    A fair question: why not put all of this in the URL, or in the request body? Why invent a separate section just for metadata about the request?

    The parcel analogy

    When you send a parcel, where do you write the recipient's address, phone number, state and PIN code — inside the package, or on top of it? On top. Because the people carrying it from sender to receiver need that information to route it correctly, and if it were sealed inside they would have to open the parcel to read it. Every time. For every handler.

    Headers are the writing on the outside of the parcel: metadata that anyone along the path can read cheaply without touching the contents. They just happen to do a lot more than an address label does.

    The four categories of header

    There are a great many headers. They group cleanly into four buckets.

    Category 01

    Request headers

    Sent by the client, describing the request itself.

    • User-Agent — what kind of client this is: a browser, Postman, a server, a mobile app.
    • Authorization — credentials such as a bearer token, so the server can identify the user.
    • Accept — what content the client expects back: JSON, text, HTML.

    Purpose: help the server understand the client's environment, preferences and capabilities.

    Category 02

    General headers

    Used in both requests and responses; metadata about the message.

    • Date — when the message was produced.
    • Cache-Control — caching directives such as no-cache or max-age.
    • Connection — whether to keep-alive or close.

    Purpose: carry information about the message itself, in either direction.

    Category 03

    Representation headers

    Describe how the resource being transmitted is represented.

    • Content-Type — the media type: JSON, HTML, XML.
    • Content-Length — size of the resource in bytes.
    • Content-Encoding — any encoding applied, e.g. gzip or deflate.
    • ETag — a unique identifier for the resource, mostly used in caching.

    Purpose: make sure both sides know how to interpret the body.

    Category 04

    Security headers

    Control browser behaviour to harden the exchange.

    • Strict-Transport-Security (HSTS) — only ever talk to this server over HTTPS; prevents protocol-downgrade attacks.
    • Content-Security-Policy — restricts where JS, CSS and images may load from; mitigates XSS.
    • X-Frame-Options — prevents the page being embedded in an iframe; mitigates clickjacking.
    • X-Content-Type-Options — stops the browser guessing the MIME type; prevents MIME sniffing.
    • Set-Cookie with HttpOnly / Secure — makes cookies unreadable by JavaScript and HTTPS-only.

    Purpose: protect both sides by constraining how the browser handles resources and by enforcing policy.

    Two big ideas that headers unlock

    Extensibility

    HTTP is highly extensible precisely because headers can be added or customised without altering the protocol. Add a piece of metadata and the whole shape of the interaction can change. That is how HTTP keeps adapting to new technologies:

    • Security enhancements — headers like Strict-Transport-Security force secure connections.
    • Custom headers — you can invent X-Custom-Header for your own application's needs.
    • Content negotiation — Accept, Accept-Language and Accept-Encoding let one server serve different versions of the same content.

    Headers as a remote control

    Think of headers as a remote control the client points at the server. They send instructions and preferences that influence how the server responds:

    • Content negotiation — the client says Accept: text/html and gets HTML; it says Accept: application/json and gets JSON.
    • Caching and expiry — the server uses Cache-Control or Expires to dictate how long the client may reuse a resource.
    • Authentication — the client authenticates through Authorization, which drives access-control decisions.

    Key takeaways

    • Headers are key–value metadata, written on the outside of the parcel.
    • Four buckets: request, general, representation, security.
    • They make HTTP extensible without changing HTTP.
    • They act as a remote control — the client shapes the server's behaviour with them.

    HTTP methods

    Methods exist so that different kinds of action can be expressed. Instead of every request meaning the same thing, the method declares the intent of the interaction. That is the keyword: intent. It gives each request clear semantic meaning — and the semantics are intuitive.

    MethodIntentBody?Idempotent
    GET Fetch data from the server. Should not modify anything. No yes
    POST Create data on the server. Has a body — which makes sense, since that is how you send the new record. Yes no
    PATCH Update part of a resource — an append or selective replacement. E.g. a user changing just their name. Yes yes
    PUT Update by complete replacement — whatever is in the body entirely replaces the previous instance. Yes yes
    DELETE Remove a resource from the server. Usually no yes
    OPTIONS Ask the server what it supports for a cross-origin request. You will rarely write one yourself; you will see them in the network tab as preflight requests. No yes
    PUT vs PATCH — the rule of thumb

    PATCH is an append or selective replacement; PUT is a complete replacement. Plenty of developers reach for PUT when they mean PATCH and quietly break the semantics. Default to PATCH unless you have a specific reason to fully replace the resource.

    Idempotency

    An idempotent method can be called many times and produce the same result. Reason it out per method rather than memorising the list:

    • GET — it does not matter how many times you fetch something, the data is the same and you have not modified the server. Obviously idempotent.
    • PUT — it completely replaces the resource, so replacing old data with the same new data five times lands you in exactly the same place. Idempotent.
    • DELETE — a resource can only be deleted once. After that it is already gone; repeating the call cannot produce a different outcome. Idempotent.
    • POST — not idempotent. A user creates a note: the first request creates one note; the second identical request creates a second note. Same request, different results.

    Key takeaways

    • The method expresses intent, and the intent is part of the contract.
    • Idempotent: GET, PUT, DELETE. Not: POST.
    • Prefer PATCH over PUT unless you truly mean full replacement.

    CORS and the same-origin policy

    The OPTIONS method has one particularly interesting use, and it lives inside the CORS flow. To understand CORS we start with the rule it exists to relax.

    By default, browsers enforce the same-origin policy: a web page may not make requests to an origin different from the one that served it. CORS (Cross-Origin Resource Sharing) is the security mechanism, enforced by browsers, that controls how a web app may interact with resources on a different origin. Without it, a page on example.com simply could not call api.example.com. CORS lets the server specify who may access its resources, and how.

    What counts as a different origin

    Scheme, host and port all matter. In the demo, the front end runs on localhost:5173 and the API on localhost:3000. Same host, different port — so the browser treats it as cross-origin, and the whole CORS machinery kicks in.

    There are two flows. Which one you get depends on the request.

    Flow A — the simple request

    Front end at example.com, server at api.example.com, and we make a GET.

    1. Browser Adds the Origin header automatically

      The client sends the request; the browser attaches Origin to declare where the request came from. The method is a simple one — GET, POST or HEAD.

    2. Server Checks Origin against its CORS policy

      If the origin is allowed, the server includes Access-Control-Allow-Origin in its response.

    3. Server Responds with the resource plus the CORS header

      The body is the actual data; the header is what makes it usable.

    4. Browser Inspects the response before handing it over

      It sees that example.com differs from api.example.com, so it looks for Access-Control-Allow-Origin. If the value is the client's own origin — or *, meaning allow all — the response is passed through to the JavaScript that asked for it.

    Response — allowed browser lets this through
    HTTP/1.1 200 OK
Content-Type: application/json
Access-Control-Allow-Origin: https://example.com

{ "data": [ ... ] }

    And when the header is missing

    Now suppose the server does not add the CORS header — either because it was never configured, or because it does not allow this particular origin. It simply omits Access-Control-Allow-Origin.

    Response — blocked browser refuses to pass this on
    HTTP/1.1 200 OK
Content-Type: application/json
   ← no Access-Control-Allow-Origin

{ "data": [ ... ] }
    Read this carefully

    The request succeeded. The server ran the handler and returned 200 with real data. The browser then noticed the missing header and blocked the response from reaching your JavaScript — you get a CORS error in the console and a CORS failure in the network tab. CORS is a browser-enforced policy, not a server-side firewall.

    Flow B — the preflighted request

    How does the browser decide it needs to ask permission before sending the real request? First the request must be cross-origin. Then any one of these three conditions is enough:

    Trigger 01

    Non-simple method

    The method is not GET, POST or HEAD — e.g. a PUT or a DELETE.

    Trigger 02

    Non-simple headers

    Anything beyond the ordinary general/request headers — an Authorization header, or any custom header.

    Trigger 03

    Non-simple content type

    A Content-Type other than application/x-www-form-urlencoded, multipart/form-data or text/plain.

    Which means, in practice…

    Almost all of our traffic is JSON — Content-Type: application/json trips trigger 03 all by itself. So most real cross-origin requests are preflighted.

    Here is what the browser sends first. Note: OPTIONS, and no body at all.

    Preflight request a general enquiry, not the real request
    OPTIONS /api/v1/notes/42 HTTP/1.1
Host: api.example.com
Origin: https://example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization, content-type

    In plain words: “I am about to make a cross-origin request. Do you support PUT on this route? And will you accept these two headers?”

    If the server handles CORS properly, it answers. If it does not, the browser blocks everything and the real request is never sent.

    Preflight response no body — the headers are the answer
    HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Max-Age: 86400
Content-Length: 0
    Response headerWhat the server is saying
    Access-Control-Allow-Origin “Yes, I allow this client's origin.” May also be *, meaning any client may call me. This is the condition the browser checks first.
    Access-Control-Allow-Methods “These are the methods I support on this route.” The browser ticks off the PUT it asked about.
    Access-Control-Allow-Headers “These non-simple headers are permitted.” Answers the Access-Control-Request-Headers question.
    Access-Control-Max-Age “Do not preflight me again for this long.” With 86400 the answers hold for 24 hours, so the browser stops asking on every route — saving bandwidth for both sides.
    1. Browser Sends the OPTIONS preflight

      No request body. Purely an enquiry about the server's capabilities.

    2. Server Replies 204 No Content with the four CORS headers

      204 is the right code precisely because there is nothing to return but headers.

    3. Browser Ticks off every condition

      Origin allowed, method allowed, headers allowed. If any check fails, it stops here.

    4. Browser Sends the original request

      The real PUT, with its Authorization header and JSON body. The server responds normally, and the response comes back to your code.

    In the network tab

    You will see the OPTIONS request appear immediately before the real one. During development, setting Access-Control-Max-Age: 0 is handy — otherwise the answer is cached and you stop seeing the preflight you are trying to debug.

    Key takeaways

    • Same-origin policy is the default; CORS is how a server opts into being called across origins.
    • CORS is enforced by the browser. Your server still ran the handler.
    • Simple flow: one request, checked for Access-Control-Allow-Origin.
    • Preflight flow: an OPTIONS enquiry first, triggered by a non-simple method, header or content type — JSON alone is enough.
    • Access-Control-Max-Age stops the browser asking again for a while.

    Status codes

    That 200 OK in the response line exists to communicate the outcome of a request in a standardised way. You can look at the code alone and know whether the request succeeded, without inspecting the body and without guessing from its shape.

    Before status codes, clients had to infer the outcome from the content of the response — “if it worked I'd expect this structure; if it failed, that structure; if the server crashed, probably a null object.” Codes remove that guesswork and give clients something to branch on: 401 means log the user out and ask them to sign in again; 400 means show the form again with a correction.

    Standardisation

    Codes mean the same thing across every web service, regardless of platform or language. It does not matter whether your server is Python, Go, Rust, JavaScript or Ruby — success is 200, creation is 201. It is a universal language, and you are expected to follow it.

    Codes are three digits, and the first digit classifies them:

    1xx
    Informational
    2xx
    Success
    3xx
    Redirection
    4xx
    Client error
    5xx
    Server error

    1xx — informational

    You will rarely meet these day to day, but for completeness:

    CodeMeaningWhen it is used
    100 Continue The server has received the headers and the client may proceed to send the body. Common in large uploads: send headers first, and only stream the body once the server has said it is happy.
    101 Switching Protocols The server is switching protocols as the client requested — for example upgrading from HTTP to WebSocket.

    2xx — success

    CodeMeaningWhen to send it
    200 OK The most common code. The request succeeded and the server is returning the requested resource or has performed the requested action. E.g. a successful GET.
    201 Created The request was fulfilled and a new resource now exists. E.g. a POST or a form submission.
    204 No Content Succeeded, but there is nothing to return. This is the preflight OPTIONS response, and a good choice for DELETE — “deleted, nothing to send back.”

    3xx — redirection

    CodeMeaningWhen to send it
    301 Moved Permanently The resource has permanently moved; future requests should use the new URL. You renamed /users to /person — add a 301 on the old route so old clients keep working while they migrate.
    302 Found (temporary) Temporarily somewhere else; the client should keep using the original URL in future. Useful for a campaign: point a route at a different page for a few hours, then revert.
    304 Not Modified The resource has not changed since the client last fetched it, so keep using the cached copy. Used with conditional GETs and ETags — see caching below.

    4xx — client errors

    As a backend engineer you will deal with these most: they are the errors triggered by something the client did.

    CodeMeaningWhen to send it
    400 Bad Request The data is invalid or illogical — you expected a number and got an array, or expected an email and got a phone number. You are telling the client: the format is wrong, fix it and try again.
    401 Unauthorized Authentication is required and the client either failed to provide valid credentials or is not authenticated at all. The JWT expired, or was never sent.
    403 Forbidden The server understood the request and refuses to authorise it — even for an authenticated client. You are user A trying to delete user B's resource. You lack the permission.
    404 Not Found The famous one. The requested resource is unavailable — wrong URL, or it has been deleted.
    405 Method Not Allowed An invalid method for this route — a PUT to something that only accepts GET or POST. Very often a typo on the front end.
    409 Conflict The request conflicts with current state. Folder names must be unique; the user POSTs a folder that already exists. 409 tells them to pick another name.
    429 Too Many Requests Rate limiting. You allow 60 requests per second per client; they exceeded it.

    5xx — server errors

    CodeMeaningWhen it happens
    500 Internal Server Error An unexpected condition — a process broke, an exception went unhandled. Rather than hanging or returning an empty response, say 500 so the client knows the fault is yours.
    501 Not Implemented The server does not support this method or functionality yet, but intends to. You are signalling intent to the client.
    502 Bad Gateway A proxy or load balancer (nginx, say) received an invalid response from the upstream server. You rarely return this deliberately — proxies produce it.
    503 Service Unavailable Temporarily unable to handle the request — heavy traffic or maintenance. Tells the client to try again later.
    504 Gateway Timeout Like 502, but specifically: the upstream did not respond within the timeout. nginx waited on your app server and gave up.
    Notice what the demo server does

    The 500 response says only “internal server error” — no stack trace, no detail. That is deliberate: leaking internals to the client is a security problem. Be generous with detail in your logs, stingy in your responses.

    Key takeaways

    • The first digit is the class; that alone tells the client whose fault it is.
    • 200 read, 201 created, 204 nothing to return.
    • 401 is “who are you?”; 403 is “I know who you are and you still may not.”
    • 502/504 come from proxies, not from your handler.
    • Keep 5xx bodies vague. Keep your logs detailed.

    HTTP caching

    Caching means storing copies of responses for reuse, so the same request need not hit the server again. It improves load time, reduces bandwidth and lowers server load — the client does not download data it already has, and the server does not send data that has not changed.

    Three headers do the work, and the flow is best followed as a trail of requests.

    1. Step 1 · first fetch Server returns the resource and three caching headers
      200 — initial response
      HTTP/1.1 200 OK
Cache-Control: max-age=10   ← reuse for up to 10s
ETag: "3141"                ← fingerprint of this body
Last-Modified: Tue, 26 Aug 2025 09:14:02 GMT

{ "resource": "..." }

      Cache-Control says how long the copy stays fresh. ETag is a fingerprint — usually a hash computed from the response body; the demo uses a random number for clarity. Last-Modified is when the resource last changed.

    2. Step 2 · fetch the same resource again Client asks conditionally, using what it already has
      Conditional GET
      GET /api/resource HTTP/1.1
If-None-Match: "3141"
If-Modified-Since: Tue, 26 Aug 2025 09:14:02 GMT

      In words: “if the ETag no longer matches this, or the resource changed after this timestamp, send me the new version. Otherwise I will use my cached copy.”

    3. Step 3 · nothing changed Server replies 304 Not Modified
      304 — no body sent
      HTTP/1.1 304 Not Modified
ETag: "3141"

      The server compared If-None-Match against the current ETag and checked the modification date. Both matched, so: use your cached version. No body is transferred at all.

    4. Step 4 · the resource is updated Server responds 200 with a new ETag

      After an update, the next conditional GET still carries the old ETag: "3141" — but the fingerprint on the server is now "2943". They disagree, so the server returns 200, the fresh body and the new ETag and Last-Modified.

    5. Step 5 · fetch again Back to 304

      The client now sends "2943", which matches, so the server returns 304 once more. The cycle continues.

    Why you may not want to build on this

    In production this gets complicated fast, because the server has to generate and manage every ETag by hand. Forget to bump one and the client happily keeps serving a stale resource — a genuinely nasty class of bug.

    These days there are better options. Client-side caching libraries such as React Query put the client fully in charge of when to reuse and when to refetch, at what interval, with far more control. Arguably a better solution than traditional HTTP caching. But it is worth knowing HTTP caching exists — if your use case is simple enough, it is right there in the protocol.

    Key takeaways

    • Server sends Cache-Control, ETag, Last-Modified.
    • Client sends back If-None-Match and If-Modified-Since.
    • Unchanged → 304 with no body. Changed → 200 with a new ETag.
    • The failure mode is a forgotten ETag serving stale data forever.

    Content negotiation

    Content negotiation is the mechanism by which client and server agree on the best format for the data. The client indicates its preference — JSON, XML, HTML — and the server responds with a compatible format, or a fallback if it cannot oblige.

    There are three kinds:

    Type 01

    Media type

    The client states the desired format via Accept — application/json, application/xml.

    Type 02

    Language

    The client requests a language via Accept-Language — en, es.

    Type 03

    Encoding

    The client declares supported compression via Accept-Encoding — gzip, deflate, br, zstd.

    In the demo, changing one header at a time changes the response:

    Request — English, JSON
    GET /api/resource HTTP/1.1
Accept: application/json
Accept-Language: en
Accept-Encoding: gzip, deflate, br, zstd

    Switch Accept-Language to es and the same endpoint returns Spanish content. Switch Accept to application/xml and the same endpoint returns XML — still in Spanish. One route, one handler, several representations, all driven by headers.

    Why it matters

    The client declares its preferences — data format, language — and the server can honour them. It makes the client's life easier without adding routes or query parameters.

    Compression

    Compression falls under the same umbrella, via Accept-Encoding and Content-Encoding. To see why it matters, take a large JSON file — 11,000 entries — and fetch it twice.

    3.8 MB
    with gzip
    26 MB
    compression disabled
    ~85%
    bandwidth saved

    Same file, same 11,000 entries. With Content-Encoding: gzip the response is 3.8 MB; with compression turned off on the server it is 26 MB. Now imagine every client downloading that difference. The browser transparently decompresses and ends up with an identical response — another thing that runs behind the scenes that you rarely touch, but should know is there.

    Persistent connections and keep-alive

    In HTTP/1.0 every request–response cycle needed its own connection, and establishing and tearing down TCP connections is slow and resource-intensive. HTTP/1.1 introduced persistent connections: one TCP connection reused for many requests and responses, avoiding that overhead entirely. The mechanism that enables it is keep-alive.

    • Persistent by default in HTTP/1.1. Connections stay open for further requests unless explicitly closed. You do not have to do anything. Fewer connections means lower latency and less resource use.
    • The Connection: keep-alive header is still sometimes used to explicitly ask the server to hold the connection open. It can carry options such as a timeout (how long to stay open) and max (how many requests before closing).
    • Connection: close closes the connection after the response. That was the HTTP/1.0 default, and can still be enforced explicitly in HTTP/1.1.
    Practical note

    You usually will not touch any of this. The defaults are fine.

    Large requests and large responses

    The last mechanical topic: how a server accepts large uploads — video, images, audio, any file much bigger than our typical JSON — and how a client receives large responses.

    Uploading: multipart/form-data

    Multipart is how you send files to a server. Unlike a normal JSON body, the file's binary data is transferred in parts — hence “multipart”.

    Multipart upload
    POST /api/upload HTTP/1.1
Content-Length: 184203
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryX7hQ

------WebKitFormBoundaryX7hQ     ← delimiter: part begins
Content-Disposition: form-data; name="file"; filename="cat.png"
Content-Type: image/png

<binary data…>
------WebKitFormBoundaryX7hQ--   ← same delimiter: part ends

    The important part is boundary. Since the binary data is transferred in parts, something has to mark where each part starts and stops — a delimiter. That is what the boundary string is for. Search the raw request and you will find it once at the start of the binary data and again at the end. The server reads the parts, reassembles the file, and responds with details confirming the upload.

    Downloading: streaming in chunks

    For the reverse direction — a large text file the server should stream rather than send in one lump — two headers do the work.

    Streamed response
    HTTP/1.1 200 OK
Content-Type: text/event-stream   ← not plain text: a stream of events
Connection: keep-alive            ← hold the connection open
Cache-Control: no-cache

data: chunk 1…
data: chunk 2…
data: chunk 3…

    Content-Type: text/event-stream says this is not a text body but a stream of events, and Connection: keep-alive keeps the connection open until everything has been sent. In the network tab you can watch the chunks arriving continuously; the client keeps appending them, reconstructing the whole file as it goes.

    Key takeaways

    • Client preferences travel in Accept* headers; the server answers with Content-Type / Content-Encoding.
    • gzip took a 26 MB response down to 3.8 MB. Compression is not optional at scale.
    • HTTP/1.1 keeps connections alive by default; you rarely need to intervene.
    • Uploads: multipart/form-data with a boundary delimiter.
    • Large downloads: text/event-stream plus keep-alive.

    SSL, TLS and HTTPS

    We do not work with these directly, but the terms come up constantly and are worth being able to place.

    • SSL was the original protocol for securing communication between a client and a server. It encrypts data so that sensitive information — passwords, card numbers — cannot be intercepted. It is now outdated, due to security vulnerabilities, and has been replaced.
    • TLS is the modern, more secure successor to SSL. It encrypts data in transit so that anything between client and server is protected from interception and tampering, and it uses certificates to authenticate the server and establish the encrypted connection, preventing eavesdropping and breaches. TLS keeps getting new versions; prefer the current recommended one.
    • HTTPS is simply HTTP plus the security features TLS provides (originally SSL). When you visit an HTTPS site, TLS encrypts the conversation between your browser and the server, protecting things like login credentials from interception.
    That is enough

    At the application level, that much understanding of TLS and HTTPS is all you need. Deeper is network engineering territory.

    Where that leaves us

    That is a lot of ground. There is always more to read on HTTP, TLS and TCP — but to work on backend systems, this is the set. If you have internalised it and can picture the whole flow of each component, you will be able to read an unfamiliar codebase, follow a request through it, and debug most of what goes wrong — because you now know which pieces come into play, and when.

    If you remember five things
    • HTTP is stateless; every request stands alone, and the client always speaks first.
    • Headers are the remote control — metadata that changes the whole interaction.
    • The method declares intent; idempotency follows from what the intent actually does.
    • CORS is a browser policy. Your handler ran; the browser refused to hand over the result.
    • Status codes are a contract, not a suggestion.
