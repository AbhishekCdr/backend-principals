      Lesson 14

      Logging, Monitoring & Observability

      Understand what your backend is doing by connecting events, measurements and request paths. Use logs, metrics and traces to detect trouble, investigate its causes and verify recovery.

      Three related practices

      A request can cross a load balancer, an API instance, a database and an external service. Other work continues in background workers. Watching one terminal cannot explain what happened across all of these components, especially when traffic is spread across instances and regions.

      PracticePurposeExample question
      LoggingRecord selected events with useful context.Why did this attempt to create a to-do fail?
      MonitoringTrack system behavior over time and detect important changes.Are request failures or database waits increasing?
      ObservabilityMake internal behavior understandable through the evidence the system exposes.Which users, routes and dependencies are affected, and what explains the change?

      Logs, metrics and traces are common telemetry signals, often called the three pillars of observability. They complement one another, but collecting all three does not automatically make a system understandable. Good instrumentation, context and questions matter more than checking off a list of products. Other evidence, such as profiles and deployment history, can also be useful. See the OpenTelemetry observability primer ↗.

      Monitoring can help diagnose problems as well as detect them, and observability does not promise an automatic root-cause answer. Improve coverage around the user journeys and failure modes that matter most, then use incidents to discover what evidence is missing.

      Key takeaways

      • Logging records events; monitoring tracks behavior; observability helps explain the system's internal state.
      • Logs, metrics and traces are complementary signals, not a guarantee of complete understanding.
      • Start with important operational questions and improve coverage as you learn.

      From an alert to an investigation

      Imagine that creating to-dos becomes slow after a deployment. A useful investigation connects an aggregate symptom to representative requests, then checks whether the proposed explanation fits the broader pattern.

      1. Notice the symptom. An alert reports elevated latency or failed requests for the production to-do API.
      2. Narrow the scope. Compare routes, instances, regions and deployment versions over the same time window.
      3. Inspect events. Relevant logs show database pool acquisition timeouts, with request and trace identifiers.
      4. Follow a request. A trace shows a long wait before database work begins, while other spans remain short.
      5. Check the explanation. Pool-use metrics and recent changes help distinguish excessive concurrency from slow queries or leaked connections.
      6. Verify recovery. After mitigation, check both request performance and successful business operations.

      A dashboard can link these signals when identifiers, timestamps and data-source integrations are configured. Metrics may link to an example trace through an exemplar, or you may search logs by service and time. An aggregate metric does not inherently contain every related log, and a log's trace may be missing because it was not retained or sampled.

      A slow span narrows the investigation; it does not by itself prove the root cause. Confirm hypotheses with dependency metrics, query plans, profiles or additional evidence as needed. The recovery decisions still follow the principles in Error Handling & Fault Tolerance.

      Key takeaways

      • Move from an aggregate symptom to affected components and representative requests.
      • Correlated signals need shared identifiers, consistent time windows and configured integrations.
      • Use evidence to test a cause and verify the outcome after mitigation.

      Log events that answer questions

      A log is a record of an event at a particular time. Useful events include startup, shutdown, configuration rejection, important business outcomes, dependency failures and security-related decisions. Logging every statement or every intermediate value creates volume without necessarily making the application easier to understand.

      Prefer stable event names with separate fields. A request-completion event can identify the service, environment, route template, method, status, duration and request ID. A business event can describe a successfully committed operation. Add trace and span IDs when an active tracing context is available.

      Decide exactly what an event means. “To-do created” should not be emitted before a transaction commits if that transaction can still roll back. A request accepted for background processing is different from a job completed. Where proof of a business action is required, design a durable audit record; ordinary application logs may be sampled, dropped or retained briefly.

      Choose a clear owner for each important outcome so one exception does not generate the same full stack trace in the repository, service and HTTP handler. Lower layers can add meaningful context while the final boundary records the request failure. Diagnostic detail belongs at the level where it helps explain the operation.

      Key takeaways

      • Log meaningful lifecycle, business and failure events with stable names and useful fields.
      • Make event wording reflect what actually completed, including transaction or job state.
      • Avoid duplicate noise and distinguish diagnostic logs from durable audit records.

      Severity levels and filtering

      LevelTypical intentExample
      DebugDetailed diagnostic information.A safe description of a branch decision during troubleshooting.
      InfoNormal, meaningful operation.The server became ready or an important business action completed.
      WarnA notable condition that may need attention.A dependency failed temporarily and a controlled fallback is in use.
      ErrorAn operation failed unexpectedly or needs investigation.A database failure prevented a valid request from completing.
      Fatal, where supportedA condition prevents the process from continuing safely.Required startup initialization cannot complete.

      A configured threshold of info commonly includes info, warn and error while excluding debug. Production often starts at info; a scoped, temporary debug setting can help during an incident. More verbose logging still needs redaction and a volume budget. Development logs are not exempt from secret-handling rules.

      Do not label every invalid form or unauthenticated request as an application error. Use a consistent policy for expected rejections and monitor unusual patterns separately. An authentication attack can matter even when each individual rejection is working correctly.

      Level names and behavior depend on the logger. A severity value alone does not restart the application. Some fatal logging methods terminate the process; others only record a high severity. Restarting depends on supervision and deployment policy. Go's standard slog package defines debug, info, warn and error, rather than a built-in fatal operation.

      Key takeaways

      • Choose severity according to operational meaning and use thresholds deliberately.
      • Expected client rejections are different from unexpected server failures.
      • Check the logger's fatal behavior; severity and process supervision are separate concerns.

      Structured logging and readable output

      Structured logging keeps event fields separate so tools can query them reliably. JSON is a common representation, but structure and destination are different choices: a process can write JSON to standard output, where an agent collects it. Console output does not necessarily mean unstructured logging.

      Illustrative request-completion event
      {
  "timestamp": "2026-10-18T09:30:00Z",
  "level": "info",
  "event": "http.request.completed",
  "service": "todo-api",
  "environment": "production",
  "method": "POST",
  "route": "/todos",
  "status": 201,
  "duration_ms": 42,
  "request_id": "req-example-1",
  "trace_id": "8b31c6e439224e89a182be463dd96f20",
  "span_id": "2079ac680ad52ef1"
}

      Keep field names and types consistent. Numeric duration fields are easier to aggregate than messages containing “42ms,” and a route template avoids parsing user-specific paths. A formatter can display the same structured events readably during development; you do not need to discard structure to make local output convenient.

      A small Go logging fragment

      With log/slog and os imported, this fragment constructs a logger with common service fields. It illustrates formatting and filtering, not a complete application or a connection to a telemetry backend.

      Go standard-library logger
      options := &slog.HandlerOptions{Level: slog.LevelInfo}
logger := slog.New(slog.NewJSONHandler(os.Stdout, options)).With(
    "service", "todo-api",
    "environment", "production",
)
logger.Info("server.started", "port", 8080)

      A TextHandler can present text output, and LevelDebug allows more diagnostic events. Neither automatically adds a trace ID: supply correlation fields through your logging integration. See the slog documentation ↗ for handler and level behavior. Plain text can also be collected and parsed, but a deliberate field schema reduces brittle extraction.

      Key takeaways

      • Separate log structure, display format and collection destination.
      • Use stable fields and types; readable development output can preserve structure.
      • A logger formats records; collection and trace correlation require additional setup.

      Metrics: counts, current state and distributions

      Metrics describe behavior numerically over time. Choose a measure with a clear definition, unit and scope: requests per second, current pool usage, completed to-dos or a distribution of request durations. A dashboard label such as “errors” is ambiguous unless you know what it counts.

      InstrumentMeaningExample
      CounterAccumulates events; may reset when a process restarts.Total requests or committed to-do creations. Use changes over time to calculate rates.
      GaugeRepresents a current value that can rise or fall.Active requests, queue depth, memory usage or connections in use.
      HistogramRecords a distribution of observations.Request durations or response sizes, supporting counts, averages and estimated percentiles.

      These are common choices; metric systems also offer other instruments, such as summaries. See Prometheus metric types ↗. A count of completed operations is not the same as the number of operations currently active.

      Define success and failure correctly

      Statuses greater than 200 are not all failures. Responses such as 201 Created and 204 No Content are successful. Redirects have their own meaning; 4xx responses often represent client rejection; 5xx responses indicate server failure. Track these separately, and define business success explicitly. A 200 response can still carry an incorrect business result.

      An illustrative five-minute server-error ratio
      5xx responses in the window / all eligible requests in the same window

Example: 20 / 1,000 = 0.02 = 2%

      Keep numerator and denominator aligned by service, environment, time and exclusions. Define what happens with no traffic or missing data instead of interpreting absence as zero errors. A latency average can hide slow users, so also inspect percentiles such as p95 or p99. Aggregate compatible distributions before calculating a fleet percentile; averaging individual instances' p95 values does not give the fleet p95. See histograms and summaries ↗.

      Key takeaways

      • Use counters for accumulated events, gauges for current state and distributions for latency.
      • Define error ratios precisely; 201 and 204 are successes, and empty data is not proof of health.
      • Inspect tail latency and aggregate distributions instead of averaging percentiles.

      Metric labels and cardinality

      Labels distinguish useful dimensions of a metric, such as service, environment, method, route template and status class. Every distinct label combination creates another time series. This number of combinations is called cardinality, and it affects memory, storage, ingestion cost and query performance.

      Usually manageableUsually unsuitable for metric labels
      Route template: /todos/{id}Raw path containing a different ID for every request.
      Known status class or operation name.Arbitrary exception text or user-supplied values.
      A bounded priority enum.User IDs, request IDs, trace IDs, email addresses or to-do titles.

      Put per-request identifiers in appropriately protected logs or trace records when needed, rather than in ordinary metric dimensions. Even bounded dimensions multiply when combined, so assess the total across instances and histogram buckets. Treat unmatched routes as a bounded category instead of giving each unknown path a new label. See Prometheus guidance on label cardinality ↗.

      Key takeaways

      • Each distinct metric label set costs another time series.
      • Prefer bounded categories and route templates over IDs, raw paths and arbitrary text.
      • Use logs or traces for detailed request context while still applying privacy controls.

      Traces and spans

      A trace describes a related set of operations, often the journey of one request across services. A span represents an operation with a start, an end and contextual attributes. Child spans can show database calls, external requests or selected service work. Different spans share a trace ID while retaining their own span IDs and relationships.

      Illustrative trace — selected operations
      HTTP POST /todos                         42 ms
├─ authenticate                           3 ms
├─ todo.create                           31 ms
│  └─ database.insert                    26 ms
└─ response.serialize                     2 ms

      Parent duration includes its children's work and other overhead. Parallel spans may overlap, so adding every span's duration does not give elapsed request time. Trace viewers commonly display a waterfall to make nesting and overlap visible. Only instrumented and collected operations appear; the trace is not a recording of every executed line of code. See OpenTelemetry traces ↗.

      A trace is not an atomic transaction

      Some APM products call a top-level request a “transaction.” This describes a unit of monitored work, not a database transaction with commit and rollback guarantees. Tracing observes execution; it does not make multiple operations atomic.

      Name spans after stable operations, not individual user content. Add useful, bounded attributes and safe failure categories. A span that ends must also have its error status recorded where appropriate; ending a span alone does not mean the operation succeeded.

      Key takeaways

      • A trace connects operations; spans describe individual operations and their relationships.
      • Nested or overlapping span durations cannot simply be added to obtain total latency.
      • Tracing and an APM “transaction” provide visibility, not database atomicity.

      Context propagation and correlation

      Tracing needs context to follow work. HTTP instrumentation extracts supported incoming trace context or starts a new trace, creates a server span and makes its context available to downstream code. Service and repository calls use that context to create related spans. Instrumented outgoing clients inject propagation headers for the next service.

      W3C Trace Context commonly carries this relationship through headers such as traceparent. In Go, request context is passed through context.Context; other languages use their own context facilities. Use established instrumentation rather than generating unrelated trace IDs at every layer. See OpenTelemetry context propagation ↗.

      A request ID used in support reports and a distributed trace ID are different identifiers, even if you record both. Trace context is also not authenticated identity: a client-controlled header must not decide a user's permissions. Add identity-related metadata only after the application has established the relevant identity and a legitimate need to record it.

      For background jobs, preserve selected propagation metadata with the message. A worker can create a related span or a linked trace according to the queue integration. Do not keep a request span open indefinitely for delayed work. Keep secrets and unnecessary personal data out of propagated baggage, which may cross service boundaries.

      Key takeaways

      • Extract, carry and inject trace context through supported instrumentation.
      • Correlate logs with tracing identifiers without treating them as proof of user identity.
      • Connect asynchronous work deliberately and minimize data propagated to other services.

      Instrumentation and OpenTelemetry

      Instrumentation is the code or integration that emits measurements, events and spans. Automatic integrations can capture supported HTTP and database operations. Manual instrumentation adds business meaning, such as a to-do creation outcome or a workflow stage. Neither approach removes the need to decide what questions the data should answer.

      OpenTelemetry provides APIs, SDKs, conventions, instrumentation and transport mechanisms. It is vendor-neutral and can send data to different backends. It is not itself a complete long-term telemetry database or a dashboard. Language, library and signal support vary; check the integration you actually use.

      1. API and instrumentation: application and library code describe telemetry events.
      2. SDK and exporter: configuration determines recording, processing, sampling and export.
      3. Collector, when used: receives, processes and forwards telemetry to configured destinations.
      4. Backend and interface: store, query, visualize and alert on the resulting data.

      A Collector can batch, filter or redact data and route it to multiple destinations. It is optional in some architectures, and collecting data does not make the application independent of transport failures. Configure queue limits, retries and shutdown flushing deliberately. See the OpenTelemetry Collector overview ↗.

      Initialize supported instrumentation before the work it should observe. Avoid adding two independent root-request instruments that duplicate spans or metrics. A proprietary agent and OpenTelemetry may coexist through supported integrations, but their ownership and export paths must be clear. The Go instrumentation guide ↗ shows the actual APIs behind these concepts.

      Key takeaways

      • Combine automatic technical coverage with selected manual business instrumentation.
      • Distinguish instrumentation, SDK/exporter, Collector and storage/dashboard responsibilities.
      • Configure one coherent telemetry path and avoid duplicate request instrumentation.

      Instrumenting a create-to-do workflow

      Follow the operation rather than memorizing a particular SDK. The HTTP layer owns the request span, final status and request-duration metric. The service can add a child span for business work, while supported repository instrumentation records database activity. The service ends its own span, not the enclosing request span.

      Conceptual service flow — pseudocode, not an SDK API
      receive validated input and request context
start a child span named "todo.create"
attach a validated priority category if useful

try:
    create and commit the to-do through the repository
    record the committed business outcome
    emit a safe "todo.created" event with correlation IDs
    return the created to-do
on business-operation failure:
    record a sanitized failure category on the span
    mark the span as failed when appropriate
    propagate the error to the request boundary
always:
    end this child span

      Keep telemetry delivery failures separate from business-operation failures. A full exporter buffer after a successful commit must not cause the application to claim that the to-do was never created and encourage an unsafe repeat. Diagnostic event delivery needs its own bounded failure policy; business-critical audit requirements need a stronger design.

      Record expected validation rejection separately from an unexpected database failure. Do not attach the user's to-do title or description by default: those fields can contain personal information or secrets. Avoid recording raw SQL parameters or database error text without reviewing and sanitizing them.

      In a New Relic implementation, an agent's transaction and segment concepts can supply this request and operation hierarchy. With OpenTelemetry, spans and context serve that role. Follow the chosen integration's lifecycle and error APIs; recording an exception event and setting span error status may be separate operations.

      Key takeaways

      • Let each layer own the spans and measurements appropriate to its responsibility.
      • End spans on all paths and describe committed outcomes, expected rejections and failures accurately.
      • Keep telemetry delivery failures and sensitive payloads out of the business success contract.

      Collection pipelines and tool responsibilities

      Writing a JSON event or starting a span does not make it appear in a dashboard. Configure collection, transport, storage and querying. A possible architecture sends application telemetry through agents or Collectors to backends, then connects dashboards and alerting to those backends. Metrics can also be scraped from an endpoint at configured intervals.

      ComponentTypical role
      Prometheus ↗Collect, store and query time-series metrics; applications and exporters provide the measurements.
      Grafana ↗Query connected data sources, explore signals, build dashboards and configure alerting.
      Loki ↗Store and query logs delivered by supported clients or collectors.
      Jaeger ↗Collect, store and explore distributed traces.
      OpenTelemetry Collector or Grafana Alloy ↗Receive and process telemetry, then forward it through configured pipelines.
      Elasticsearch, Logstash and KibanaA common combination for ingestion, indexed search and log exploration.
      New Relic ↗ or Datadog ↗Integrated platforms for application monitoring, tracing and related telemetry investigation.

      An update to the lecture's tool list

      Promtail reached end of life on March 2, 2026. For new setups or migrations, use Grafana Alloy or another supported collection client rather than treating Promtail as a current default. See Grafana's Promtail notice ↗.

      These products are composable options, not a mandatory stack. Operating separate services gives control but requires upgrades, capacity planning and maintenance. A managed platform can reduce that work while introducing its own costs, limits and data-handling considerations. Evaluate existing team skills, integrations, volume and retention needs instead of assuming either route is always simpler or cheaper.

      Grafana is not the source of every metric, and Prometheus does not automatically discover business outcomes hidden in application code. The instrumentation, collection and dashboard layers have to agree on what is produced and how it is interpreted.

      Key takeaways

      • Connect instrumentation to collection, storage, exploration and alerting explicitly.
      • Choose a manageable set of tools with clear responsibilities rather than installing every product.
      • Promtail is end of life; use a supported telemetry collection path.

      Dashboards and actionable alerts

      Start dashboards with user-facing traffic, errors and latency, then add resource saturation and dependency health. Database pool waits, queue age, CPU, memory and garbage-collection behavior can explain why user experience is changing. Display service, environment and version clearly so a staging experiment is not mistaken for a production incident.

      Alert on conditions that justify action, with an owner, a useful time window and a runbook. “Error rate above 80%” is an illustration, not a sensible universal threshold. Choose signals and thresholds around the service's objectives, expected traffic and acceptable impact. Include enough volume context to distinguish a sustained problem from one failed request.

      A service-level indicator (SLI) measures a defined outcome, such as the fraction of eligible requests completed successfully. A service-level objective (SLO) specifies the target over a period. See the SRE guide to service-level objectives ↗. Alerts can use these objectives to focus attention on user impact instead of paging whenever a resource briefly changes. See Google SRE's monitoring guidance ↗.

      Freshness and absence are part of the dashboard

      Scrape intervals, SDK batching, network queues, storage ingestion and dashboard refresh all contribute delay. There is no universal ten- or fifteen-second freshness guarantee. Show the selected time range and check ingestion lag before deciding that an event did not happen. A blank chart may mean no traffic, a wrong filter or a broken telemetry pipeline.

      Avoid pages for every expected 401 or invalid form. Monitor unusual authentication patterns separately, and preserve visibility into genuine failures. Alert delivery is also a dependency: test the notification route, escalation path and recovery notification in an appropriate test setup.

      Key takeaways

      • Connect request health, business outcomes and resource pressure in dashboards.
      • Give alerts meaningful thresholds, context, ownership and an action to take.
      • Understand collection delay and missing data; neither an empty chart nor a green panel proves complete health.

      Privacy and safe telemetry

      Telemetry may pass through collectors, storage services, dashboards and third-party platforms. A field added to a span can be exposed just as easily as a field written to a log. Decide what is necessary before capture, and apply the same care to events, attributes and propagated context.

      • Exclude passwords, API keys, authorization headers, session cookies and reset tokens.
      • Avoid full request bodies, raw query parameters and user-written titles or descriptions by default.
      • Use an opaque user ID only when needed; it still requires access controls and appropriate retention.
      • Review exception messages, database parameters and URLs for embedded credentials or personal data.
      • Encode fields safely so untrusted content cannot forge log entries or corrupt their structure.

      Prefer an allowlist of safe fields and redact close to the source. Restrict telemetry access, protect transport and storage, and define retention. Collector-side filtering can add protection, but cannot undo a secret already written to an application log. The safe logging guidance in Lesson 12 applies across the whole pipeline.

      Key takeaways

      • Apply privacy rules to logs, spans, attributes and propagation, not just public API responses.
      • Capture only necessary fields and redact secrets before they leave the application.
      • Protect telemetry access, transport, storage and retention.

      Sampling, retention and telemetry overhead

      Recording more data has costs: application work, network traffic, collector capacity, storage and investigation noise. Keep enough detail to answer important questions, with separate policies for routine diagnostics and records that must be retained for a defined purpose.

      Head sampling chooses whether to record a trace early, before its final outcome is known. Tail sampling makes decisions after observing enough of the trace to consider properties such as errors or duration. Tail sampling needs buffering and suitable routing of related spans, and cannot recover spans already discarded upstream. See OpenTelemetry sampling ↗.

      Sampled traces are examples, not automatically a complete request census. Prefer appropriate aggregate instrumentation for traffic and error counts. If metrics are derived from spans, understand where sampling occurs and how it affects those metrics. Different SDK and backend pipelines can behave differently, as illustrated by Datadog's trace-metric documentation ↗.

      Bound queues and export work so a telemetry outage does not exhaust application memory or block every request. Monitor dropped records, export failures, ingestion lag and collector health. Plan graceful flushing on shutdown, while recognizing that crashes can still lose buffered diagnostic data. Sampling and retention settings belong in your configuration management policy.

      Key takeaways

      • Choose sampling and retention deliberately rather than assuming every request is stored forever.
      • Know whether metrics cover all eligible traffic or a sampled source.
      • Bound telemetry resource use and monitor the collection system's own failures.

      Verify the workflow and share ownership

      Instrumentation is unfinished until you verify its output. Use an isolated test environment and representative operations to check the application, collection path and dashboard together. Do not change a real deployment to “production mode” merely to make a demonstration visible; configure an explicit test service and environment identity.

      1. Successful operation: create a to-do and confirm the success metric, event and expected span relationships.
      2. Expected rejection: call a protected route without credentials and confirm a 401, consistent classification and safe metadata.
      3. Controlled dependency failure: simulate a database failure and confirm the failure category, request outcome and trace context.
      4. Slow operation: introduce a controlled delay and check the duration signal and relevant span.
      5. Collection problem: interrupt a test exporter and verify bounded behavior, pipeline diagnostics and recovery.

      If authentication rejects a request before it reaches the service, expect an HTTP/authentication path, not a database span that never ran. Likewise, verify that each request is counted once and that filtering or sampling explains any missing records. Check time ranges, environment filters and ingestion status before declaring the integration broken.

      Developers own useful events, operation semantics and context propagation. Platform teams own reliable collection, storage, access and delivery. Both share naming conventions, dashboards, alert policies and incident feedback. This is an engineering skill that improves through practice; no product removes the need to understand what the measurements actually mean.

      Key takeaways

      • Verify successful, rejected, failed and slow operations across the complete telemetry path.
      • Check correlation, counting, privacy and pipeline failure behavior in a controlled environment.
      • Share ownership between application and platform teams and improve instrumentation from real questions.
