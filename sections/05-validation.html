      Lesson 05

      Validations & Transformations

      Before an API acts on client data, it needs two answers: is this input acceptable? and what representation should the application use? Validation checks the contract; transformation converts accepted input into a useful form. Together they protect data integrity at the boundary of your backend.

      Where the pipeline belongs

      In a typical layered backend, a matched route leads to a controller, which calls a service, which may call a repository. These layers divide responsibilities rather than prescribe a particular framework.

      LayerResponsibility
      ControllerHTTP input, response shape and status codes; pass validated input to the appropriate service.
      ServiceBusiness rules and orchestration: repository calls, notifications, emails or webhooks. A service need not use a database.
      RepositoryPersistence operations: query, insert, update and delete in PostgreSQL, Redis or another store.
      1. RequestMatch a route and parse the input

        The method and path select the handler. The body parser turns JSON text into values.

      2. BoundaryValidate and transform

        Apply that route's schema in middleware, a framework pipeline or a shared function at the start of the controller. Reject invalid input before business side effects.

      3. ApplicationExecute the service

        Use the validated result to perform business logic and any persistence work.

      4. ResponseReturn through the controller

        Serialize the result into the API's response format and send the appropriate HTTP status.

      Exact middleware order varies. Request size limits may run before parsing; authentication can run before route-specific validation. The invariant is to validate external input before using it for business operations. State-dependent rules, such as available stock, still belong in the service and persistence layers where they can be enforced correctly.

      Key takeaways

      • Controller = HTTP; service = business logic; repository = persistence.
      • Validate at the input boundary before database writes, emails or other side effects.
      • Boundary checks complement business rules and database constraints.

      A schema is the input contract

      Validate every input source your API consumes: body, query parameters, path parameters and headers. A successfully parsed JSON body is only valid JSON; it is not necessarily valid data for this endpoint. A schema spells out required fields, types and constraints.

      For a book-creation endpoint, suppose name must be a string of 5–100 characters:

      PayloadResult
      {}Reject: name is required.
      {"name": null}Reject: present, but not a string.
      {"name": 0}Reject: wrong type.
      {"name": "Go"}Reject: fewer than 5 characters.
      {"name": "Designing Data Systems"}Accept: type and length match.

      Also decide whether empty strings and null are allowed, what happens to unknown fields, and which defaults apply. Optional means a field may be absent; nullable means it may explicitly contain null. Those are different promises. If trimming names is part of your contract, check the length after trimming.

      Do not pass arbitrary fields through

      Choose to reject or discard unknown fields. A client-supplied isAdmin must not become a writable property just because the request body was passed straight into a model.

      Key takeaways

      • Check presence, type, then constraints; valid JSON alone proves none of these.
      • Cover the body, query, path and consumed headers, including nested fields.
      • Define optional, nullable, default and unknown-field behavior explicitly.

      Type, syntactic and semantic validation

      These categories overlap; they are useful ways to ask what a check proves.

      KindQuestionExample
      TypeIs the value the expected kind? age is a number, married a boolean, tags an array of strings.
      SyntacticDoes its structure match the format? reader@example.com is email-shaped; 1995-06-12 follows YYYY-MM-DD.
      SemanticDoes the value make sense in this context? A birth date exists on the calendar and is not in the future; an age is within the application's allowed range.

      Format is not proof

      test.com is not an email address: it lacks a local part and @. Even a well-formed email does not prove that the mailbox exists or belongs to the user; that needs a verification flow. Phone numbers need a documented national or international format, not an assumption that every country uses ten digits. Store them as strings to preserve leading zeroes and the country-code prefix.

      Likewise, 2025-02-30 has the right date shape but is not a real calendar date. Compare birth dates to the current date under a defined timezone policy, not to a hard-coded year from a demo. The lecture's age range of 1–120 is an example product rule, not a universal rule for every application.

      Validate inside collections too

      Type-validation example
      {
  "stringField": "notes",
  "numberField": 10,
  "arrayField": ["one", "two"],
  "booleanField": false
}

      If arrayField becomes [1, 2], it is still an array but its elements fail the string rule. Report the element path, such as arrayField[0]. Similarly, the JSON string "false" is not the boolean false.

      Key takeaways

      • Type checks the kind; syntax checks the structure; semantics checks the meaning.
      • Validate array elements and nested properties, not just their containers.
      • Valid email or phone syntax does not prove ownership; a date shape does not prove a real date.

      Cross-field and conditional rules

      Some contracts depend on several fields together. A schema can express these relationships as well as individual field constraints.

      RuleWhat to enforce
      Password confirmationpasswordConfirmation equals password, and the password independently satisfies the password policy. The lecture's eight-character minimum is only a demo constraint.
      Conditional partner nameWhen married is true, require a non-empty partner string. When false, the field may be absent; if present, it still needs a valid type.
      Related datesstartDate must not be after endDate.
      Age and birth dateIf you collect both, check their consistency under your date policy. Prefer deriving age from birth date when possible.

      Password confirmation catches typing mistakes; it is not an authentication mechanism. Never echo passwords in a demo response or log them as part of a validation failure. A successful request can return an acknowledgement or safe fields instead.

      Key takeaways

      • Cross-field checks compare values; conditional checks change requirements based on another field.
      • Passing each field's own constraints does not prove that the fields agree.
      • Confirmation checks do not replace password security; keep secrets out of responses and logs.

      Fail early with useful errors

      Without boundary validation, {"name": 0} can reach a service that expects a string, cause an exception or reach persistence with the wrong meaning. You have already spent work and may have performed side effects before discovering the problem.

      A database is not your input schema

      A number inserted into a text column does not necessarily fail: a driver or database can convert it to text. PostgreSQL permits assignment conversions to string types. Even TEXT NOT NULL does not enforce a 5–100-character book name. See PostgreSQL's value-storage conversion rules.

      Reject a contract violation with 400 Bad Request, or use 422 Unprocessable Content consistently for well-formed but invalid input. Reserve 500 for unexpected server failures. Known database constraint violations can also be mapped to an appropriate client error; database errors are not automatically 500s.

      Example validation response
      HTTP/1.1 400 Bad Request
Content-Type: application/json

{
  "error": "VALIDATION_FAILED",
  "details": [
    { "field": "email", "code": "invalid_format", "message": "Use a valid email address." },
    { "field": "phone", "code": "invalid_type", "message": "Phone must be a string." }
  ]
}

      An empty body object may produce several required-field errors. Fixing the email may leave only the phone error; fixing both allows execution to continue. Field paths and stable error codes help a client put messages beside inputs. These messages support API documentation, but do not replace it. Unlike ordinary format errors, login errors should avoid revealing whether an account exists, as discussed in Lesson 04.

      Key takeaways

      • Reject invalid requests before side effects; return clear field-level 4xx errors.
      • Database coercion may accept wrong input; retain database constraints as a separate safeguard.
      • Use safe error messages without stack traces, passwords or account-existence leaks.

      Transformation: from wire values to application values

      Transformation changes a value's representation: parsing a numeric string, trimming a name or normalizing a date. Validation decides whether a value is allowed. They work together; a successful conversion does not prove that the resulting value is acceptable.

      Pagination from Lesson 02
      GET /bookmarks?page=2&limit=20

Raw query values:    { "page": "2", "limit": "20" }
Validated result:    { "page": 2,   "limit": 20   }

      Query values arrive as text before framework-specific parsing. A schema that immediately insists on numbers rejects a perfectly reasonable request. Transform at the boundary, then validate the numeric result. For the lecture's example, require integer 0 < page < 500 and 0 < limit < 10000. These are illustrative ceilings; choose limits your service can afford.

      1. Check the raw representation

        Require one value per field and an accepted integer string. Reject blank values, arrays, repeated parameters and trailing junk such as 2abc under this contract.

      2. Convert deliberately

        Parse the whole value as a number. Do not use a permissive parser that silently accepts only a numeric prefix.

      3. Check the converted value

        Require a finite integer in range: pages 1–499, limits 1–9999. Reject zero, negatives, fractions and overflow.

      4. Pass the validated result onward

        The service receives the parsed values, not the original request object. Defaults such as page 1 and limit 20 may apply to missing fields, but should not silently replace invalid values.

      Coercion is not permission

      Generic truthiness can turn the string "false" into true. Some numeric conversions turn an empty string into zero. Accept only documented representations, then check the result. Never turn invalid data into plausible-looking data by accident.

      Key takeaways

      • Transformation changes representation; validation checks acceptance.
      • Check raw input → convert → check the result → pass that result to the service.
      • For pagination, require bounded integers; reject ambiguous input and default only missing values.

      Normalization needs an explicit policy

      Transformations may happen before a check or after it, depending on what the check needs. Keep their ordering beside the schema so the complete input contract is easy to find.

      InputPossible transformationBoundary to respect
      Reader@EXAMPLE.COMReader@example.com Lowercase the domain. Lowercasing the whole address requires an explicit account policy: the local part can be case-sensitive under SMTP's rules.
      A national phone numberA validated international representation Use known country context. Blindly prepending + does not make an arbitrary number valid or infer its country.
      1995-06-12An internal calendar-date value A birth date is not an instant. Do not invent midnight UTC and accidentally shift the date when displaying it in another timezone.
      " Ada Lovelace ""Ada Lovelace" Trim if the name contract allows it, then validate its length. Never apply generic trimming or lowercasing to passwords.

      Key takeaways

      • Normalize only when the contract defines the change and preserves the intended meaning.
      • Email casing, phone country context and date timezones need deliberate decisions.
      • Keep transformations and checks together; do not silently alter secrets.

      Frontend and backend validation work together

      Frontend: immediate feedback

      Show a missing field or malformed email before submitting. This helps the user correct mistakes quickly and avoids unnecessary requests.

      Backend: enforce the contract

      Check every request, regardless of who sent it. A script, mobile app, Postman or Insomnia can bypass your web form completely.

      In a form, an invalid email can stop submission before an API call happens. Once the form looks valid, the request reaches the server and the server checks it again. Shared schema definitions can reduce drift, but executing those rules in the browser does not remove the server's responsibility.

      Security has several layers

      Validation supports data integrity; it does not replace authorization, parameterized database queries or context-aware output encoding. See the OWASP input validation guidance.

      Key takeaways

      • Frontend validation improves user experience; backend validation enforces the input contract.
      • Every client can bypass the web form. The server must validate independently.
      • Validation complements authorization and injection defenses; it does not replace them.

      Designing an API: the checklist

      For each endpoint, be able to explain its input contract before writing its business logic.

      Key takeaways

      • Sources: which body fields, query/path parameters and headers do you consume?
      • Shape: which fields are required, optional or nullable, and what are their types?
      • Constraints: which lengths, ranges, formats, nested and cross-field rules apply?
      • Transformations: what do you parse or normalize, in what order, and what is rejected?
      • Errors: can clients identify and fix a failure without receiving sensitive details?
      • Execution: does only validated output reach business operations, with domain rules and database constraints still enforced?
