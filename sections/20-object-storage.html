      Lesson 20

      Object Storage & File Uploads

      Store user files independently of application instances. Follow the bytes from authorized upload intent to validated publication, reliable delivery and recovery.

      Why instance-local uploads become a problem

      A profile-picture endpoint can receive multipart form data, save a file and record its path in a database. This can work on a persistent single-server installation. The trouble begins when that path is treated as durable, shared storage even though it belongs to one replaceable application instance.

      FailureWhat causes itRequired property
      Upload exhausts memoryThe parser or application buffers a large body, possibly with extra copies.Enforced limits, bounded concurrency and streaming or direct uploads.
      Files disappear after deploymentThe old container and its writable layer are removed.Storage whose lifetime is independent of the application instance.
      Intermittent missing imagesAn upload reaches A; a later download reaches B, which has a different local disk.A shared storage authority accessible by all authorized instances.
      A disk failure loses dataThe failed disk held the only recoverable copy.Redundancy, integrity checks, repair and a recovery plan.
      Database and files disagreeOne write succeeds and the other fails.A recoverable workflow across the two systems.

      A Docker container's writable layer is lost when that container is removed, not necessarily when the same container is stopped and restarted. Replacement during deployment is the common hazard. Volumes can persist independently and shared filesystems can serve multiple instances; neither is inherently the wrong choice. See Docker's storage model ↗.

      If a file exists on only one of three equally likely instances, a random request succeeds about one-third of the time and fails about two-thirds. Real results depend on routing and placement. This is the same external-state requirement discussed in horizontal scaling.

      Key takeaways

      • Local storage can be valid, but its lifetime and sharing must match the deployment.
      • Container removal, instance replacement and memory exhaustion are different failures.
      • Separate durable user bytes from replaceable application compute.

      Block, file and object storage

      These are interfaces with different semantics, rather than a simple ranking from slow to fast. A filesystem commonly sits on a block device. An object service also ultimately stores data on physical devices, but exposes a different interface to your application.

      InterfaceWhat you addressTypical operations and use
      Block storageNumbered blocks on a device or volume.Read/write block ranges; a foundation for filesystems and database storage. Examples: an SSD or EBS volume.
      File storageFiles through paths and directories.Open, read, seek, write, rename and permission operations, with filesystem-specific guarantees. Local filesystems and NFS offer different deployment properties.
      Object storageAn object key within a bucket.Upload, retrieve, inspect metadata, list and delete through service APIs. Well suited to media, exports, archives and backups.

      Block sizes, latency and attachment rules depend on the system. Block devices are not universally restricted to one machine: EBS Multi-Attach ↗ exists, but safe concurrent access needs suitable coordination. Storage growth also does not always require downtime; Elastic Volumes ↗ supports online changes under documented conditions.

      Filesystems provide useful coordination semantics, but they do not make every multi-write edit atomic. An application can write a replacement temporary file and rename it under appropriate filesystem rules; crash durability can require additional synchronization. Do not assume every editor implements the same save algorithm or that network filesystems have identical behavior.

      Key takeaways

      • Block addresses device ranges, file storage addresses paths, and object storage addresses keys.
      • Choose the interface from access, sharing, durability and consistency requirements.
      • Latency, online resizing and multi-machine access are implementation-dependent.

      What an object and a bucket contain

      An object combines a key, a sequence of bytes and metadata. System metadata describes properties such as size, modification time, content type and ETag. User metadata can record application values, but client-provided metadata is not proof of identity or authorization.

      Conceptual stored object
      Bucket: application-media
Key:    tenants/t_42/users/u_7/avatars/9b71c2.png
Bytes:  the uploaded image contents
System metadata: size, content type, ETag, modification time
Application record: owner, original filename, status, key, version ID

      A bucket is a named service container and a policy/configuration boundary. Keys identify objects within that bucket; versioning can retain multiple versions under one key. Bucket-name uniqueness rules depend on provider, bucket type and namespace. For ordinary S3 global-namespace buckets, uniqueness is across accounts and Regions within an AWS partition, rather than across every cloud platform. Check the relevant bucket naming rules ↗.

      Store a stable bucket/key reference, and a version identifier when required, in the database. A short-lived signed URL is a delivery credential, not the permanent identity of a file. Keep original display filenames separate from storage identity.

      Key takeaways

      • An object is bytes plus a key and metadata within a bucket.
      • Store stable object references, ownership and state in the application database.
      • Metadata and filenames supplied by clients remain untrusted input.

      Prefixes look like folders

      In a general purpose S3 bucket, uploads/2026/cat.png is one complete key. The slashes do not create a chain of filesystem directories. A listing can group matching names by prefix and delimiter, which produces the folder-like view in storage consoles.

      Conceptual prefix listing, not a filesystem traversal
      Stored keys:
  uploads/2026/cat.png
  uploads/2026/dog.png
  uploads/readme.txt

List with prefix "uploads/" and delimiter "/":
  Contents:       uploads/readme.txt
  CommonPrefixes: uploads/2026/

      A zero-byte object named uploads/empty/ can act as a folder marker; it is still an object. Moving a prefix in a general purpose bucket generally requires copying and deleting its individual objects. It is not one atomic directory operation, and it has request, storage and possibly transfer costs. See prefix and delimiter semantics ↗.

      Scope these rules to the service being used. S3 directory buckets have additional semantics, including a RenameObject operation for S3 Express One Zone ↗. “Object stores can never rename” is therefore too broad.

      Key takeaways

      • General purpose bucket folders are commonly prefix groupings of flat keys.
      • Folder moves can involve many independent object operations.
      • Specialized bucket types and providers may expose additional operations.

      Design keys and ownership deliberately

      Generate storage keys on the server from validated identifiers and a collision-resistant object ID. Preserve the user's original filename for display or a safely constructed download filename. Reusing an untrusted filename as a shared key can cause collisions, confusing Unicode handling and dangerous behavior if a later component interprets it as a local path.

      Object keys are not inherently filesystem paths, so ../ does not by itself traverse S3 directories. The risk appears when proxies, URL normalization or local extraction apply path semantics. Avoid ambiguous components and do not concatenate arbitrary client paths into storage or filesystem locations.

      An ownership prefix can help scope IAM permissions, but the server must derive its tenant and user IDs from trusted context. A string prefix check alone does not prove access: respect separator boundaries, ownership changes and the actual authorization policy. Opaque keys are not secrets or permission checks.

      Do not present random leading prefixes as a universal S3 requirement. Modern S3 supports sequential naming and automatic scaling. At high rates, measure workload distribution, handle transient throttling with bounded retries and consult current performance guidance ↗. A timestamp prefix is not automatically a design bug.

      Key takeaways

      • Separate server-generated identity from the original display filename.
      • Derive ownership from authenticated context; enforce it independently of key secrecy.
      • Choose partitioning strategies from current provider behavior and measured demand.

      Metadata and data have different responsibilities

      A useful conceptual design separates an index of object identity and metadata from storage of the bytes. A lookup maps a key to the information needed to retrieve its data. The data side manages capacity, placement, redundancy, integrity checking and repair. Both need substantial engineering.

      This is a mental model, not a description of S3's private implementation. Do not assume its metadata is one globally distributed B-tree or that a fixed number of frontends, shards or drives serves every object. Internal placement and algorithms can change without changing the public API.

      Use the application database to answer product questions such as “which attachments may this user see?” with ownership, status and pagination. Fetch known objects by key. Bucket listing remains useful for inventory, reconciliation, administration and workloads that actually need listing; it is not forbidden on every request path. Avoid repeatedly scanning a large bucket to reconstruct application state.

      Key takeaways

      • Separate reasoning about object lookup from storage and recovery of bytes.
      • A conceptual architecture is not a guarantee of a provider's internal layout.
      • Keep the application's searchable file catalog and authorization in an appropriate database.

      Replication and erasure coding

      Replication stores additional copies. Three full copies consume three times the logical data size before other overhead. Failure-domain placement matters: three drives sharing one power source do not provide the same resilience as independent failure domains.

      Erasure coding stores data fragments plus redundant fragments computed from them. In an illustrative Reed–Solomon scheme with 14 data shards and 6 parity shards, any 14 valid shards can reconstruct the data. Losing up to six shards is tolerable under this model; one shard alone cannot recover the object.

      Illustrative capacity arithmetic, not an S3 layout specification
      Three replicas:       stored / logical = 3.00×  (200% extra)
14 data + 6 parity:   stored / logical = 20 / 14 ≈ 1.43×
Extra coding capacity:                 6 / 14 ≈ 42.9%

      Encoding, recovery reads, network traffic, small-object overhead and repair speed affect the real tradeoff. A larger count of tolerated fragment losses does not alone prove higher durability than another design; failure correlations and recovery time matter. Provider durability claims cannot be derived from this example without their full reliability model.

      Key takeaways

      • Redundancy needs independent failure domains and working repair mechanisms.
      • In the illustrative 14+6 code, any 14 valid shards recover the object.
      • Capacity efficiency and durability are related but not interchangeable measurements.

      Durability, availability and recoverability

      Availability concerns whether an authorized operation can succeed when needed. Durability concerns retaining data over time despite failures. Recoverability concerns restoring the intended state after mistakes, compromise or corruption. Waiting may resolve a temporary outage; it does not restore a permanently lost object.

      S3 Standard is designed for 99.999999999% durability, eleven nines, and has a separate availability design target. These are service design metrics, not a promise that a particular object cannot be lost. With a simplified annual loss fraction of 10−11, ten million objects imply an expected 0.0001 losses per year, equivalent to one per 10,000 years on average under that model. This is not an independent-failure guarantee or a prediction of when a loss will occur. See storage-class durability and availability targets ↗.

      Durable storage also preserves an accidental overwrite. Enable versioning where recovery requirements justify it, protect permissions to delete versions, and test restores. Replication to another account can help isolate credentials, but is not automatically an independent backup if unwanted changes also propagate. Retention, deletion behavior and access boundaries need explicit policies.

      In a versioning-enabled general purpose bucket, an ordinary delete generally creates a delete marker; deleting a specific version can permanently remove that version. Versions consume storage. See S3 Versioning ↗.

      Key takeaways

      • Availability, durability and recovery from mistakes answer different questions.
      • Eleven nines is a design target, not a substitute for backups and restore testing.
      • Versioning helps only while recoverable versions remain protected and retained.

      Consistency and whole-object operations

      For ordinary general purpose bucket usage, replacing an object means publishing a replacement value under its key, rather than editing arbitrary filesystem byte offsets. Readers should not receive half of one successful object replacement mixed with half of another. Range retrieval is supported; it is different from an in-place partial write.

      S3 provides strong read-after-write consistency for object writes and deletes and strongly consistent listings. After a successful write, a subsequent authorized origin read observes that write or a later one. This does not guarantee every request returns 200: authorization, deletion, networking and other failures still exist. Nor does it make multi-object updates transactional or force CDN and browser caches to refresh. See the S3 consistency model ↗.

      Legacy advice to sleep after every successful S3 upload is not a remedy for modern origin consistency. Diagnose permission, key, cache or workflow errors instead. Other providers and cross-region replication can have different guarantees. Specialized APIs may add append or rename behavior; check the exact bucket and API contract rather than treating immutability as universal.

      Key takeaways

      • Whole-object replacement and partial retrieval are different operations.
      • Strong origin consistency does not refresh external caches or create a database transaction.
      • A successful write is not a guarantee that every later network request succeeds.

      Conditional writes prevent unintended overwrites

      An unconditional write to an existing key can replace its current value. Concurrent writes can both succeed at different times even though only one value remains current. HTTP POST does not universally mean “always create a new entity,” and a method name alone does not provide collision protection.

      ConditionIntentWhat to handle
      If-None-Match: *Create only if no current object exists under the relevant API's rules.Existing object: precondition failure, commonly 412.
      If-Match: "etag"Replace only if the current object's ETag matches the observed ETag.A changed ETag rejects a stale update; reread and resolve the conflict.

      If A reads ETag E1, B replaces that value with E2, then A's conditional replacement using E1 fails instead of overwriting B's change. ETags are opaque validators, not universally MD5 checksums or unique revision numbers. Recreating identical content can preserve a validator, so do not assume ETag comparison detects every intermediate change.

      Handle documented conflicts and retry behavior, including concurrent delete cases. The successful condition applies to one object operation. It does not automatically provide a safe distributed lease, fencing token, leader election protocol or multi-object transaction. See S3 conditional write semantics ↗ and atomicity and race conditions.

      Key takeaways

      • Use supported conditional writes when create-only or stale-write protection is required.
      • ETags are validators; do not treat them as universal checksums or revision counters.
      • A conditional object write is a coordination primitive, not a complete distributed lock design.

      S3-compatible does not mean identical

      S3 compatibility usually means a service implements enough of the S3 API to work with familiar clients and SDKs. It does not promise every AWS feature, error case or guarantee. Avoid assuming that a provider supports a feature merely because the SDK exposes its method.

      Check conditional operations, consistency, browser POST policies, checksums, multipart completion, versioning, encryption, lifecycle behavior, CORS and request limits against the actual provider's current documentation. Integration tests should exercise the features the application depends on. Do not copy a historical feature comparison as a permanent statement about a provider.

      Key takeaways

      • Compatibility is a feature-by-feature contract, not an identity guarantee.
      • Verify required semantics against the selected provider and bucket type.
      • Test important rejection and concurrency behavior as well as successful uploads.

      Uploading through the application server

      A proxy upload sends bytes from browser to backend and then to storage. It can be a production-ready choice when centralized inspection, protocol mediation or other requirements justify it. The backend can authorize the request and apply validation before accepting the file into its published storage area.

      Buffering an entire upload creates memory demand proportional to file size and concurrency. Twenty buffered 100 MB files already represent about 2 GB of bodies before parser copies, runtime overhead and other work. Multipart parsers differ: some buffer, some spool to disk, and some expose streaming APIs. Do not infer their behavior from a function's name.

      Streaming with backpressure bounds buffering, but the SDK may buffer multiple multipart chunks or concurrent parts. Budget memory across the parser, SDK and all active uploads. Enforce body limits before expensive parsing, count actual received bytes even without Content-Length, limit concurrency, and clean up partial work after cancellation.

      Also inspect reverse-proxy buffering, body limits, gateway payload caps and timeouts. An idle timeout measures inactivity, not necessarily total transfer duration. Increasing an application timeout cannot bypass a provider's hard payload limit. Streaming avoids whole-body buffering but still uses network capacity and connection state.

      Key takeaways

      • Proxy uploads are valid when the requirements justify their resource costs.
      • Use backpressure, early size limits and bounded concurrency across every buffering layer.
      • Check proxy and gateway limits separately from application behavior.

      Direct uploads with presigned URLs

      For many applications, the backend can authorize an upload without relaying its bytes. It chooses the bucket and key, records the intent, and returns a short-lived signed capability. The browser then uploads directly to the storage endpoint while the bucket remains private.

      A SigV4 presigned URL binds request details such as the method, key, expiry and signed headers through a signature derived from the signer's credentials. Use the provider SDK to construct it. The browser receives credential-identifying fields, a signature and sometimes a session token, but not the signing secret. Changing signed request details causes authorization to fail.

      The URL itself is a bearer capability. Anyone possessing it can attempt the permitted operation. It can normally be reused until expiry, subject to credential expiry and policy changes; it is not a single-use link. Expiry is checked when a request begins, so an already-started transfer may continue afterward. Keep lifetimes short and keep URLs out of logs, analytics and unnecessary sharing. See presigned URL permissions and expiration ↗.

      Authorize issuance, choose keys server-side and scope the signer to the required actions. Signing a content-type header restricts the supplied label, not the actual byte format. Direct uploads move validation and publication into a later workflow; they do not remove those responsibilities.

      Key takeaways

      • The backend grants scoped upload authority; the browser transfers bytes directly.
      • Protect signed URLs as reusable bearer credentials until they expire or become invalid.
      • Authorization and content validation remain application responsibilities.

      Enforcing upload policy and size

      A presigned PUT without an enforced size constraint should not be treated as a bounded avatar upload. Depending on the client and provider, signed request headers can constrain aspects of the upload, but browsers do not let JavaScript freely set Content-Length. For S3 browser uploads requiring an explicit accepted size range, a presigned POST policy is a useful option.

      Illustrative policy conditions; the SDK supplies signature fields and expiry
      [
  ["content-length-range", 1024, 5242880],
  ["starts-with", "$Content-Type", "image/"],
  {"key": "tenants/t_42/users/u_7/avatars/server-generated-id"}
]

      The range here is 1 KiB to 5 MiB. Prefer an exact server-generated key when one upload should target one object; a prefix policy grants broader authority. The client sends the returned form fields and file to the returned URL. Matching field values and policy conditions must both be provided as required by the SDK. See presigned POST fields and conditions ↗.

      Browser helper using server-issued POST fields
      async function uploadWithPost(file, grant) {
  const form = new FormData();
  for (const [name, value] of Object.entries(grant.fields)) {
    form.append(name, value);
  }
  form.append("file", file);
  const response = await fetch(grant.url, {
    method: "POST",
    body: form
  });
  if (!response.ok) throw new Error(`Upload failed: ${response.status}`);
}

      Append the file after the policy fields. Let the browser set the outer multipart Content-Type and boundary. The form's object Content-Type field is separate from that outer header. A matching image label does not prove the body is an image; inspect the bytes before publishing. Exact error codes can vary by the violated condition and provider.

      Key takeaways

      • Enforce size and destination at the storage boundary where supported.
      • POST policy fields and conditions must agree; prefer one exact key for one upload intent.
      • Client labels and client-side checks do not validate the actual file contents.

      Upload intent, verification and publication

      There is no automatic transaction covering both the application database and object storage. Model the upload as a stateful workflow with retries and reconciliation. The application should expose only objects that have passed its publication requirements.

      1. Create an intent

        Authenticate and authorize the caller. Reserve quota, generate a unique key, and persist an upload ID, owner, expected constraints, expiry and pending state before issuing the grant.

      2. Transfer the bytes

        The browser uploads directly to private staging storage. A failed transfer can be retried under the grant's rules.

      3. Verify completion

        The client sends the application upload ID. The server loads the owned record and verifies the expected object, rather than accepting an arbitrary client-supplied key.

      4. Validate and publish

        Inspect required properties and content, then atomically update the database state and profile reference. Repeated completion calls should return a consistent result.

      HeadObject ↗ returns metadata without downloading the body. It can check size and recorded validators, but cannot prove that a claimed image is decodable or malware-free. HEAD is a billable request under applicable pricing, not free. Missing objects can produce 403 or 404 depending on permissions; handle permissions and transient errors distinctly.

      A still-valid upload grant can overwrite its staging key after verification. Avoid publishing a mutable, client-writable target based only on a previous HEAD. Where supported, pin verification and reads to a version ID; alternatively copy a specifically validated version or conditionally matched source to a new, server-controlled publication key. Protect that published key from upload grants.

      Key takeaways

      • Persist intent first, then verify and publish through an idempotent state transition.
      • HEAD checks metadata; content inspection is a separate operation.
      • Bind publication to the bytes actually validated, despite reusable upload capabilities.

      Content inspection and safe downloads

      Keep unvalidated uploads private. Validate actual file structure with suitable parsers and resource limits, including decoded image dimensions, archive expansion, media duration or other format-specific risks. Malware scanning can be appropriate to the product. A checksum helps detect integrity problems; it does not make malicious content safe.

      For avatars, decoding and re-encoding into an approved format can provide a clean publication artifact with bounded dimensions. Reject or separately handle active formats such as HTML and SVG according to the product's requirements. Do not let arbitrary uploaded markup execute under a trusted application origin.

      For private downloads, authenticate and authorize access to a ready database record, then issue a short-lived signed GET or an appropriate CDN capability. Configure Content-Type, safe Content-Disposition filenames and caching behavior deliberately. Use separate content origins and avoid leaking private responses through shared caches. See trust boundaries and browser security.

      Key takeaways

      • Validate bytes and resource usage before publishing content.
      • Integrity checks, format checks and malware checks serve different purposes.
      • Authorize downloads independently and choose safe origins, response headers and cache policies.

      Abandoned uploads and reconciliation

      Clients close tabs, lose networks and retry. A file may exist even though its completion request never arrived; a pending row may exist without any stored object. Storage events can help trigger processing, but event-driven completion also needs duplicate handling, retries and reconciliation.

      A cleanup worker claims expired intents using a state transition that cannot race with publication, then deletes their staging objects and releases reservations. Retain enough state to retry failed deletion. Reconcile stuck verification jobs and orphaned artifacts using the database catalog, inventory or bounded listings as appropriate.

      Do not apply a blanket “delete after 24 hours” rule to a prefix that also contains published objects. Keep staging and published namespaces separate, or manage lifecycle tags safely. If objects remain at their original key, the cleanup rule must distinguish ready objects. Lifecycle expiration is asynchronous and is not an exact 24-hour timer.

      Incomplete multipart uploads are a separate resource: abort them explicitly or configure an appropriate abort lifecycle rule. Deleting an application row alone does not clear their retained parts. Connect cleanup to durable job retries and task lifetime management.

      Key takeaways

      • Plan for every combination of stored bytes, pending records and missing client callbacks.
      • Cleanup and publication must coordinate rather than race.
      • Separate staging lifecycle from published retention and incomplete multipart cleanup.

      CORS for browser-to-storage requests

      Direct uploads commonly cross origins. Configure the bucket to allow the actual frontend origin, required upload methods and request headers. When browser JavaScript needs to read ETag or other non-safelisted response headers, expose those headers explicitly. Multipart clients often need the returned ETags to track parts.

      CORS is browser access policy, not authentication. It does not stop curl or a leaked signed URL from attempting an authorized upload. A valid signature can still be unreadable to JavaScript because CORS is wrong, and successful CORS does not grant storage permissions. See S3's CORS evaluation ↗.

      If curl works and the browser fails, inspect preflight and upload responses separately: origin, requested method, requested headers, endpoint Region, redirects and exposed response headers. For POST, use the browser-generated multipart boundary. Do not make a private bucket public to solve a CORS error.

      Key takeaways

      • Allow the intended browser origin, methods and headers at the storage endpoint.
      • Expose ETag when the client must read it; CORS and authorization are separate.
      • Debug preflight and actual upload requests without weakening bucket access.

      Large files, multipart uploads and resuming

      S3 multipart upload splits one object into independently uploaded parts, followed by a completion operation. This is different from a browser multipart/form-data POST. Retry failed parts instead of restarting the whole file, and bound parallel uploads so client memory, bandwidth and request costs remain controlled.

      Persist the storage upload ID, part numbers and returned validators needed for completion, associated with the authorized application intent. Resuming also requires access to the original file and valid part grants; a browser tab does not magically retain a file handle after every restart. The backend must authorize signing, completion and abort against the same owned intent.

      Only mark the application ready after storage completion and content verification. Use the SDK's error handling, checksum support and current part-size/count limits instead of assuming the final ETag is a whole-file MD5. Retained incomplete parts incur storage charges until completed or aborted. See multipart upload operations and cleanup ↗.

      Key takeaways

      • Storage multipart upload supports independent part retries and controlled parallelism.
      • Resumption needs persistent upload state, original bytes and renewed authorization where necessary.
      • Complete or abort uploads and verify the resulting object before publication.

      Downloads, range requests and delivery cost

      A 50 MB decimal file over a steady 2 Mbit/s connection takes about 200 seconds, or 3 minutes 20 seconds, before overhead. An async server need not dedicate an actively running CPU worker for that entire time, but it still retains connection state and consumes bandwidth. I/O is normal backend work; the decision is where to perform it economically.

      Object storage and a CDN can deliver bytes while application servers focus on authorization and business logic. A range GET asks for a byte interval and can return 206 Partial Content with Content-Range. Media players use byte ranges along with container indexes and codec information to seek; range support alone is not video transcoding or adaptive streaming. An invalid range can produce 416. See GetObject range semantics ↗.

      Budget stored bytes, old versions, request counts, retained multipart parts, retrieval charges for selected classes, transfer/egress, replication and processing. HEAD, LIST and failed operations can have applicable charges too. Estimate from access patterns and the provider's current pricing ↗, rather than treating cheap storage as cheap delivery.

      Measure upload completion and abandonment, verification latency, rejected sizes, orphan age, download latency, throttling, bytes transferred and cost. A complete design connects authorization, byte transfer, validation, publication, retention and recovery; a bucket alone is not the workflow.

      Key takeaways

      • Long transfers occupy connections and bandwidth without necessarily occupying a CPU worker continuously.
      • Range requests retrieve byte intervals; media formats and delivery pipelines determine seeking behavior.
      • Evaluate total storage, request, processing and delivery costs and monitor the whole upload lifecycle.
