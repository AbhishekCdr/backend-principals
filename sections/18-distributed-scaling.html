      Lesson 18

      Scaling & Performance II

      Continue from the performance foundations into shared state, traffic distribution, database scaling, edge delivery and execution models. Each added component needs a clear responsibility and a defined failure policy.

      Stateless application instances

      When a load distributor can choose any application instance, a valid request should not depend on a previous request having reached that same machine. If a user signs in through instance A and their next request reaches B, B needs access to the authoritative information required to recognize the session and perform the operation.

      This is the useful meaning of stateless application instances: durable business state and session continuity do not depend on one instance's private memory or local disk. The system still has state, and request handlers still have local variables and network connections. Disposable local caches and temporary files can be appropriate when they can be reconstructed and their loss does not violate the application's promises.

      Statelessness makes routing, replacement and scale-out easier. It is not the only way to scale: stateful systems can also scale using explicit partitioning, replication or ownership. The important question is where state lives, who owns it and what happens if that owner disappears.

      Requests can move; required state remains accessible
      Client → routing layer → application A / B / C
                              |    |    |
                              shared interfaces
                              /       |       \
                      session store  database  object storage

Local memory: request work and explicitly disposable data
Durable state: stored under a defined availability and recovery policy

      Key takeaways

      • A request should not require private state left on one particular application instance.
      • Stateless application instances still use stateful databases, sessions and connections.
      • Local disposable state is acceptable when loss and reconstruction are explicitly handled.

      Sessions, uploads and shared dependencies

      An in-process session map works only where that map exists. A shared database or session store lets every authorized instance validate the same session token. Cookie configuration, signing or encryption keys, expiration and revocation behavior must also be compatible across instances. JWTs are not required to scale a browser session.

      Uploaded files have the same issue. A file saved only on instance A may be absent when the next request reaches B or A is replaced. Store durable objects through a shared service, such as object storage, and keep metadata and access rules in the appropriate authoritative store. A shared file service is another possible design where its semantics fit the workload.

      StateTypical shared designQuestion to answer
      SessionsDatabase or shared session storeHow quickly does revocation reach every instance?
      UploadsObject storage plus metadataWho may read the object, and when is the upload complete?
      Business recordsA database with defined consistency and recoveryWhat is the behavior during failure or failover?
      Recurring workCoordinated scheduling or durable queue ownershipDoes adding a replica accidentally run the job twice?

      A local SQLite file does not become a shared database simply because application code is identical on several machines. Replicated or remotely served SQLite designs require their own architecture; arbitrary file sharing is not a substitute. Likewise, a shared Redis endpoint moves a dependency out of the app but does not by itself make that dependency highly available. See authentication, job ownership and shared-state scaling tradeoffs.

      Key takeaways

      • Share required session and upload state through suitable storage interfaces.
      • Keep security configuration and authorization consistent across instances.
      • Externalizing state creates dependencies that still need capacity, availability and recovery planning.

      Where load balancing happens

      Multiple serving instances need a way to select a destination. A reverse-proxy load balancer receives traffic, selects a backend and forwards the request, then relays the response. This forwarding normally does not mean an HTTP redirect asking the browser to navigate elsewhere.

      A standalone load-balancer machine is one implementation, not a universal requirement. Managed frontends, DNS-based distribution, client-side balancing and service discovery can also participate. Understand whether selection happens per connection, request or stream, and where transport and TLS terminate.

      Layer 4 balancing typically works with transport connections; Layer 7 balancing can inspect application information such as HTTP hostnames and paths. An API gateway may add authentication, quotas and route policies as well as forwarding. These responsibilities can overlap in a product, but their names alone do not describe its behavior.

      The balancing layer also needs enough capacity and its own availability design. Moving all traffic through a single unprotected proxy can introduce another failure point. Verify request timeouts, body limits, retries and trusted forwarding headers across the full path.

      Key takeaways

      • Routing chooses an instance; proxy forwarding is different from redirecting the browser.
      • Selection can happen at several layers and at connection or request granularity.
      • Plan the balancing layer's capacity, availability and request-handling policies.

      Round robin and weighted round robin

      Round robin selects eligible backends in a rotating sequence. With three similar instances, the conceptual sequence is A, B, C, A, B, C. It is a useful baseline when capacities and request costs are reasonably similar. Equal request counts still do not guarantee equal resource use.

      Weighted round robin assigns a larger share to backends with larger configured weights. Weights of 2:1:1 aim to give A half the traffic and B and C one quarter each over an appropriate interval. The exact short sequence depends on the implementation, such as smooth weighted selection; it need not always send two consecutive requests to A.

      Example backendWeightLong-run share in this simple model
      A22 / 4 = 50%
      B11 / 4 = 25%
      C11 / 4 = 25%

      Hardware specifications alone do not prove the right weights. A backend with twice the CPU cores may not sustain twice the workload if it waits on the same database. Measure effective capacity and watch for skew when expensive requests happen to concentrate on one instance. See NGINX's balancing overview ↗.

      Key takeaways

      • Round robin distributes turns, not equal amounts of computational work.
      • Weights specify intended traffic shares; implementations determine the short sequence.
      • Choose weights from measured serving capacity and monitor workload skew.

      Connection-aware and adaptive selection

      Least-connections selection favors an eligible backend with fewer active connections under the balancer's definition. A long operation may keep a connection occupied longer, helping the policy respond to uneven work. Weighted variants account for configured capacity, but they do not promise an exact 2:1 request ratio at every moment.

      A server with an active request can still receive more requests when it is the selected candidate. The algorithm does not reserve each server for a single request. Connections also differ from outstanding requests: HTTP/1.1 commonly keeps connections open after a response, HTTP/2 multiplexes streams, and HTTP/3 runs over QUIC rather than TCP.

      Some products offer least-outstanding-request, latency-aware or resource-aware policies. They depend on the actual measurement and feedback mechanism. A low response time could reflect quick errors rather than useful work, and CPU measurements may miss a downstream wait. Stale or noisy feedback can produce poor routing decisions too.

      Select the algorithm from the workload and the product's documented semantics. Combine it with health eligibility, concurrency limits and overload controls. A smarter selection policy cannot create capacity in a saturated shared dependency. See the NGINX method descriptions ↗ and capacity and queueing fundamentals.

      Key takeaways

      • Least-connections uses occupancy as a signal; it is not perfect knowledge of request cost.
      • Connection counts and in-flight request counts differ with persistent and multiplexed protocols.
      • Adaptive selection still needs reliable measurements and overload protection.

      Health checks, recovery and draining

      A load balancer can send active probes to assess whether a backend should receive traffic. It may also use passive evidence from real connection or request failures. A dead process can cause a connection error or timeout; it does not necessarily return an HTTP error itself. The proxy may generate a response for the client.

      Probe intervals, timeouts, accepted status codes and failure/recovery thresholds are configurable. Requiring several failures before removal and several successes before recovery helps avoid flapping. A simple illustrative policy might mark a target unhealthy after three failed probes and eligible again after two successful ones. There is still a detection window.

      Readiness asks whether the instance should serve new work. Liveness asks whether restarting it could help. A lightweight readiness check can include necessary initialized dependencies, but repeatedly exercising expensive business operations can add load. Treat common dependency failures carefully: removing every instance or restarting all of them may worsen an outage.

      Product failure behavior matters. For example, AWS Application Load Balancer documents a fail-open behavior when all registered targets are unhealthy; do not assume every balancer always sends zero traffic to every unhealthy target. See its health-check policy ↗.

      Planned removal also requires draining existing work after routing withdrawal. Recovering instances may need initialization and cache warmup before full traffic. In-flight operations can fail during an unplanned loss, and retries must respect idempotency. See graceful shutdown.

      Key takeaways

      • Configure probe timeouts and failure/recovery thresholds rather than assuming instant detection.
      • Separate readiness, liveness and planned draining; probes themselves have a cost.
      • Verify all-unhealthy behavior and preserve safe retry semantics during failures.

      Read replicas scale suitable reads

      Application replicas can all reach the same database until that shared database becomes the limiting resource. One database scaling approach keeps a writable primary and creates replicas that replay its changes and serve permitted read workloads. Applications or routing middleware decide which operations can use those replicas.

      An illustrative primary-and-replica topology
      Writes and freshness-critical reads → primary
                                      |
                               replicated changes
                                 /           \
                      read replica A      read replica B
                      suitable reads      suitable reads

      Replicas can move read work away from the primary and place data closer to application instances. They also consume resources for receiving and applying changes. A workload with 70% read requests does not automatically reduce primary resource use by 70%: operations have different costs, some reads still need the primary, and replication has overhead.

      This topology does not distribute the primary's write workload across writable nodes. Additional read replicas are not a universal solution for write saturation. Nor does a failover standby necessarily expose the same read-serving interface as a read replica in every managed product. Verify the engine and service's actual behavior.

      PostgreSQL supports readable hot standbys as part of its replication facilities. Replication modes, supported queries and failover choices affect the design; other engines have their own mechanisms. See PostgreSQL standby and replication concepts ↗.

      Key takeaways

      • Route suitable read work to replicas and writes to the intended writable authority.
      • Measure load reduction rather than equating read-request percentage with saved resources.
      • Read replicas do not automatically scale writes or provide every failover guarantee.

      Replication lag and read-after-write behavior

      A user changes their profile name and immediately reloads it. The write commits on the primary, but a read routed to a lagging replica can return the previous name. The write may have succeeded even though the next screen appears to undo it.

      Replication lag is not a fixed geographic round-trip time. It also depends on transfer, queueing, replay throughput, long operations, load and failures. An observed average of 200 ms does not establish a maximum. A fixed browser delay of 300 ms therefore cannot guarantee that the next read sees the write.

      ApproachTradeoff
      Route required follow-up reads to the primaryProvides the needed view under the database's transaction semantics, while retaining primary load.
      Wait for a replica to reach an appropriate commit/replay positionNeeds engine support, a meaningful consistency token, a timeout and a fallback policy.
      Choose suitable synchronous replication semanticsCan improve guarantees for designated replicas, with extra commit latency and availability consequences.
      Allow a documented stale viewSuits some feeds or analytics, but not every account or payment decision.

      Receiving or flushing replication data is not always the same as applying it so a query can see it. PostgreSQL's remote_apply option waits for the designated synchronous standbys to replay a commit; routing reads to another asynchronous replica would still need consideration. See its synchronous replication semantics ↗.

      Returning the committed representation from the write can avoid an unnecessary immediate fetch, but does not replace the consistency policy for later reads. A primary read can also be obscured by an old application or CDN cache. Design freshness across the entire path.

      Key takeaways

      • Asynchronous replicas may return older data after a successful primary write.
      • Average lag and fixed sleeps cannot establish a read-after-write guarantee.
      • Use explicit routing or replication guarantees and include caches in the freshness policy.

      Partitioning and sharding are different scopes

      Partitioning divides a logical data set into smaller pieces. A database can partition one table within a single database server. Sharding usually means distributing partitions across independently placed database nodes or groups so storage and processing can spread across machines. The terms overlap, but a partitioned table is not automatically a distributed database.

      Splitting orders by date can help when queries constrain that date and the database can prune unrelated partitions. It can also simplify archival and deletion of old ranges. Splitting data does not guarantee that every query becomes faster, and a well-indexed large table is not inherently slow merely because it has many rows.

      Non-overlapping illustrative date ranges
      Range A: 2026-01-01 ≤ order_date < 2026-07-01
Range B: 2026-07-01 ≤ order_date < 2027-01-01

A query restricted to March can target Range A.
A query for all orders of user 5, with no date constraint,
may need both ranges unless another routing/index design helps.

      A shard normally still has its own indexes and may have replicas for availability or reads. Partitioning, sharding, replication and indexing solve related but different problems. PostgreSQL's native table partitioning describes partition pruning and its requirements; it does not by itself turn ordinary partitions into independent distributed write nodes. See the partitioning documentation ↗.

      Key takeaways

      • Partitioning can happen on one server; sharding distributes data across nodes or groups.
      • Query benefits depend on whether the workload can target the relevant pieces.
      • Shards still need indexes, replication and an operational recovery plan.

      Choose shard keys for the workload

      The shard key determines which piece owns a record and whether an operation can find its destination efficiently. A tenant or user key may keep that user's related data together. A date key can make archival simple but concentrate every new write on the latest shard.

      StrategyPotential benefitRisk
      RangeEfficient routing for matching ranges and useful locality.Uneven ranges, hot recent data and range-boundary maintenance.
      HashCan distribute many keys more evenly.Range queries can fan out; very hot individual keys remain hot.
      Directory or placement mapExplicit control over where tenants or groups live.The map and migration process need consistency and availability.

      Consider how to route reads and writes, generate identifiers, enforce uniqueness, join related records and perform cross-shard transactions or reports. A query that must visit every shard can become slower as shards are added. Global ordering and pagination also require a design rather than simply concatenating arbitrary result pages.

      Adding a shard often requires moving data, updating placement information and handling requests during migration. A toy hash(key) modulo shard_count formula changes many destinations when the count changes; production rebalancing needs more than changing that number. A managed sharding layer can handle mechanics while still depending on a suitable application data model. See Vitess's sharding-oriented architecture ↗.

      Key takeaways

      • Choose keys from locality, distribution and routing requirements, not table size alone.
      • Plan hot keys, cross-shard work, uniqueness and pagination explicitly.
      • Rebalancing requires a safe migration and placement strategy.

      Managed databases still have a responsibility boundary

      Managed services can operate provisioning, replication, backups and failover features for you. They do not all implement the same architecture. “Serverless,” “distributed” and “managed” describe different properties; none alone promises automatic sharding or unlimited write capacity.

      Architecture exampleWhat to examine
      Managed PostgreSQL with replicasWritable-primary capacity, read routing, replica lag and failover semantics.
      Disaggregated PostgreSQL compute and storageCompute scaling and storage behavior; do not infer automatic row-level write sharding.
      A sharding middleware layerShard-key model, routing and resharding capabilities.
      Distributed SQLData placement, transaction guarantees, quorum costs and cross-region latency.

      For concrete differences, compare Neon's compute/storage architecture ↗, Vitess ↗ and CockroachDB's architecture ↗. Product language, implementation language and SQL compatibility do not by themselves establish how a service distributes writes.

      Your team still owns schema and query design, access control, connection budgets, freshness choices, cost limits and restore requirements. Verify which features the chosen plan actually includes and practice recovery. Replication is not a backup: an accidental deletion can propagate to replicas too. Decide the acceptable loss window and restoration time, then test them.

      Key takeaways

      • Compare concrete database capabilities rather than treating every managed product as equivalent.
      • The provider operates selected mechanisms; the application still owns data and consistency choices.
      • Verify backup, restore and failover behavior instead of assuming replicas cover all recovery needs.

      CDNs reduce distance for reusable content

      A content delivery network serves eligible content from distributed points of presence, or PoPs. On a cache hit, the response can avoid a trip to the origin. This can reduce viewer latency and origin traffic. A miss may still fetch the origin, possibly through additional cache tiers. See CloudFront's delivery model ↗.

      Geography imposes a propagation component on network latency. As an illustrative calculation, if a round-trip fiber path totals 20,000 km and propagation is approximately 200,000 km/s, propagation alone takes 0.1 seconds. That is not a measured Tokyo-to-Virginia guarantee: actual path length, routing, equipment, handshakes and congestion affect the result.

      Moving a response close to the viewer can remove much of that distant path. It does not guarantee a 2 ms response or a fixed 50% traffic reduction. Benefits depend on routing, cacheability, hit rate, payloads and origin behavior. Nor is a PoP necessarily located at every user's first ISP hop; CDN operators use varied networks and peering arrangements.

      Static bundles, images, fonts and videos are common candidates. Generated public pages and API responses can also be cached under an appropriate policy. An edge proxy can accelerate routing for uncached traffic, but it cannot skip required origin work simply by being nearby.

      Key takeaways

      • CDN hits can avoid distant origin requests and reduce origin load.
      • Propagation is only one part of network latency; fixed speedup and traffic-saving claims need measurements.
      • Cacheability and the actual request path determine the benefit.

      Cache policies must preserve freshness and privacy

      A CDN needs a policy defining what may be reused, for whom and for how long. Origin headers, CDN rules and cache-key construction all participate. Two responses with the same URL are not interchangeable if they differ by user, tenant, language or another relevant input.

      Illustrative policies for different response types
      Content-hashed public bundle, such as app.8d21f3.js:
  Cache-Control: public, max-age=31536000, immutable

Sensitive response that must not be stored by caches:
  Cache-Control: no-store

      The long-lived asset policy assumes a changed bundle gets a changed URL. The HTML pointing to that bundle needs its own suitable freshness policy. For generated public API responses, decide how much staleness is acceptable and how updates invalidate or replace cached results. Availability, stock and payment decisions may need a fresher source than a product description.

      Purging by URL, prefix or tag depends on the provider's features and configuration. A purge is an invalidation mechanism, not a promise that every browser cache immediately disappears or every race is solved. A miss normally causes a later fetch; purging does not necessarily prepopulate every edge. See Cloudflare's origin cache-control behavior ↗.

      Do not put authenticated personalized responses into a shared public cache by accident. Carefully review cookies, Authorization, Vary and explicit cache rules rather than relying on a filename extension or a single header. Test one user's response against another user's request. See the security lesson and cache invalidation fundamentals.

      Key takeaways

      • Define cache eligibility, identity, lifetime and invalidation for each response class.
      • Version immutable assets and give HTML and generated data their own freshness policies.
      • Protect personalized data from shared-cache leakage and test actual CDN behavior.

      DDoS protection and origin exposure

      A denial-of-service attack consumes resources so legitimate work cannot complete. A distributed attack uses many sources; a botnet is one way to generate it. Network saturation, expensive uncached endpoints and forced autoscaling can produce availability problems or unexpectedly high cost even without a process crash.

      A suitably configured CDN or security edge can absorb some traffic, cache responses, enforce rules and apply challenges or rate limits before requests reach the origin. The exact protections, coverage and controls depend on the service. See Cloudflare's DDoS protection documentation ↗.

      This does not make the origin invulnerable. Attackers may bypass the edge if the origin is directly reachable, and legitimate-looking expensive requests can still pass through. Restrict origin access where appropriate, validate forwarded identity, protect costly operations and set concurrency and scaling budgets. Challenges also affect real users and need deliberate configuration and monitoring.

      Key takeaways

      • DDoS can harm availability and cost through both traffic volume and expensive work.
      • An edge security service helps only within its configured scope and request path.
      • Protect the origin and retain application-level limits and monitoring.

      Edge computing moves selected work closer

      Edge computing executes code near a request's ingress location instead of only returning a cached object. Useful tasks include redirects, routing, header validation, localization and selected authentication checks. The gain comes from the execution and data paths avoided, not from a guarantee that the same computation uses fewer CPU cycles.

      A signed token can sometimes be checked locally with trusted keys and the correct issuer, audience and expiration rules. A server-side session may still require a distant authoritative lookup, retaining that network cost. Local verification also needs a revocation policy. Resource authorization remains necessary, and an origin must not blindly trust a public client-supplied header claiming “already authenticated.”

      Runtime limits vary. Cloudflare Workers uses V8 isolates, while other execution platforms use different isolation models. It would be inaccurate to say edge code universally cannot use TCP or a filesystem: Workers documents outbound TCP sockets ↗ and a compatibility-dependent virtual filesystem ↗. Those facilities still have restrictions and do not turn temporary local files into durable shared storage.

      Check CPU time, memory, duration, network access, library compatibility, storage and data placement for the chosen runtime. If an edge function immediately queries a distant database, moving its code alone may add an extra hop. Benchmark the whole path rather than assuming “edge” is always faster. See how Workers executes code ↗.

      Key takeaways

      • Move work to the edge when it avoids an expensive path without weakening correctness or authorization.
      • Authentication speed depends on where its authoritative data and revocation state live.
      • Verify runtime capabilities and limits; edge platforms are not interchangeable.

      Asynchronous processing needs a durable handoff

      Some operations need a completed result before the response; others can finish later under an explicit contract. Creating a team invitation illustrates the distinction. The invitation must exist durably and pass authorization checks, but email delivery can follow asynchronously.

      Conceptual invitation workflow
      Request handler:
  authenticate and authorize the inviter
  validate the invite and enforce membership/uniqueness rules
  begin database transaction
    insert invitation with acceptance_state = pending
    insert outbox event requesting invitation-email delivery
  commit
  return the created invitation with delivery_state = pending

Dispatcher:
  publish committed outbox work to a durable job system

Worker:
  load authorized delivery data and send the email
  record delivery outcome; acknowledge according to the job protocol

      The response now waits for durable acceptance rather than the external email round trip. A 201 can describe the created invitation resource while delivery remains pending; a 202 can describe an accepted asynchronous operation. Neither should claim that an email has already been delivered. Expose the status the product actually promises.

      Writing the invitation and then publishing a job creates a failure gap if the process crashes between them. A transactional outbox records the intent with the database change, then a dispatcher can retry publication. Delivery may still be repeated, so design idempotency and failure handling. See the outbox pattern ↗ and background job reliability.

      Queuing changes user waiting time, not the total required work. Workers need capacity, deadlines, retries, dead-letter or failure handling, and queue-age monitoring. An untracked task launched after returning the response is not a durable handoff. Authentication and critical business checks still belong before accepting the work.

      Key takeaways

      • Respond after the operation's promised acceptance state is durable.
      • Distinguish created, accepted, delivered and completed states in the API and UI.
      • Protect the database-to-job handoff and make workers retry-safe and observable.

      Long jobs and truthful completion states

      Media processing often becomes a workflow after a durable upload: generate thumbnails, produce encodings, transcribe audio and publish the ready asset. Some steps can run in parallel, while others depend on prior output. Persist the uploaded object and job state so closing the browser does not destroy accepted work. Completion time still needs a product expectation, even when it is asynchronous.

      Account deletion also needs a lifecycle rather than an immediate claim that every byte is gone. A server can validate the request, mark the account as deleting, revoke access as required and durably schedule cleanup. The response should say deletion was requested or is in progress. Only mark it complete when the defined deletion workflow actually finishes.

      Illustrative asynchronous response contract
      HTTP/1.1 202 Accepted
Location: /operations/deletion-123
Content-Type: application/json

{"operationId":"deletion-123","status":"pending"}

      Large deletions may require bounded batches and resumable checkpoints instead of one enormous transaction across every store. Prevent new writes that recreate deleted data, respect foreign keys, and define what happens if one cleanup step fails. Cross-service objects, backups and any retained records need the platform's documented policy; a success toast is not evidence that all storage has been erased.

      Choose a job runtime that fits duration and resource needs. A long video transcode may exceed a short-lived function's limits and belong in a batch worker or container job. Scaling producers faster than consumers merely grows the backlog unless admission and worker capacity are managed.

      Key takeaways

      • Persist uploads and workflow state before promising background completion.
      • Return pending states for deletion or processing that has not finished.
      • Use bounded, resumable work and prevent new writes from defeating cleanup.

      Monoliths and service boundaries

      A monolith is deployed as one application unit, even when it contains well-separated modules and runs in many replicas. Microservices divide the system into services that can be deployed and operated independently. Repository layout does not decide the architecture: a monorepo can contain several services, and several repositories can still have tightly coupled releases.

      A modular monolith can be a useful starting point because function calls, transactions, development and deployment remain relatively direct. It can also scale horizontally. A microservice split is not a prerequisite for serving a large user base.

      Reason to consider a boundaryWhat to establish first
      Independent releases and ownershipA stable domain boundary and a team able to operate the service.
      Different capacity or isolation needsA measurable reason to scale or contain one workload separately.
      A distinct runtime or toolchainBenefits that justify another deployment and communication boundary.

      There is no mandatory threshold of 100 or 200 engineers. Organizational needs can motivate service separation, but team size alone does not determine a safe boundary. Nor does needing a fast image library automatically require another service: native libraries, separate worker processes and existing runtime bindings may be alternatives. Benchmark the implementation rather than assuming a language switch creates a fixed tenfold speedup.

      Independent scaling can also begin by separating a background worker from the HTTP serving process. Accept a service boundary when its ownership, release, isolation or capacity benefit pays for the additional operational work.

      Key takeaways

      • A monolith can be modular and horizontally scaled; microservices are independently operated deployment units.
      • Choose service boundaries from domain and operational needs rather than headcount or fashion.
      • Consider simpler worker or library boundaries before introducing a new network service.

      Service separation adds distributed-system costs

      A function call across modules can become an HTTP, RPC or message exchange across services. That introduces serialization, network latency, timeouts, partial failures and versioned contracts. Repeated chatty calls can erase an expected scaling benefit.

      A request crossing order, payment and notification services needs correlated telemetry to explain its path. Carry trace context across boundaries and record useful service outcomes. Logs and metrics remain useful, but they do not automatically reconstruct a distributed request without appropriate context and instrumentation. See observability practices.

      Service-owned databases are not simply replicas of one shared database. They can hold different domains and schemas, so keeping a business workflow consistent requires explicit coordination. A local transaction in the order service does not automatically roll back an already completed external payment or an email sent by another service.

      Durable events, outboxes, idempotency and compensating workflows are possible tools. A saga coordinates steps and business compensations; it is not equivalent to an invisible ACID transaction spanning arbitrary services. Design intermediate states, retries and operator recovery. See the saga pattern ↗.

      Choose boundaries that reduce total operational and organizational friction. If every service must be changed and deployed together, the system may have acquired network failure modes without gaining useful deployment independence.

      Key takeaways

      • Network boundaries introduce latency, partial failure, contracts and operational ownership.
      • Service-owned data requires business-level coordination, not just replica synchronization.
      • Use explicit workflow states and recovery instead of assuming one global rollback.

      Autoscaling still needs capacity planning

      Autoscaling changes capacity from a policy and observed or predicted demand. CPU, memory, outstanding work, queue age or application-specific metrics can be inputs. Choose a signal that represents the limiting resource; a universal memory threshold cannot describe every workload.

      New capacity takes time to become useful. That can include scheduling, starting a container or VM, initializing the application, establishing connections and warming caches. It does not always require compiling source or booting a fresh operating system: prebuilt images, warm capacity and the selected platform change the path.

      Policy dimensionDecision
      Minimum capacityBaseline readiness, failure headroom and any acceptable scale-from-zero delay.
      Maximum capacityCost budget, account quotas and downstream capacity that must not be exceeded.
      Scale-out timingSignals, stabilization, startup delay and expected bursts.
      Scale-in timingSafe draining, backlog and avoiding repeated capacity oscillation.

      Dynamic threshold-based scaling is reactive, but autoscaling is not limited to that model. Scheduled and predictive policies can prepare for known or recurring peaks. Forecasts still have limits, so retain headroom and overload protection. See AWS's predictive scaling model ↗.

      Protect database connections, external-service quotas and queues as application instances grow. More servers can amplify pressure on the same saturated dependency. Budget alerts, concurrency caps and graceful rejection need to work together; a spending alert alone is not a real-time enforcement mechanism.

      Key takeaways

      • Select workload-relevant signals and include startup and warmup delay.
      • Set capacity bounds from availability, budget and downstream limits.
      • Use predictive or scheduled preparation where useful, with safe scale-in and overload behavior.

      Serverless changes the operating boundary

      Serverless computing delegates more infrastructure operation to a provider. Servers still execute the code, but the application team generally works with a supported runtime, deployment artifact and event or request interface rather than administering each host. Functions, managed containers and edge runtimes have different execution models.

      An HTTP function can be invoked through a gateway, function URL or platform routing layer. Other functions respond to queue messages, object uploads or schedules. A new invocation does not necessarily mean a new physical server, and a successful response does not imply that the execution environment is immediately destroyed.

      Configuration still matters: runtime, memory or CPU allocation, duration, permissions, networking, concurrency and dependencies may remain your responsibility. The provider's lifecycle can reuse initialized environments, create more of them or retire them. Do not use a reused environment as the only home for durable application state.

      Compare the whole cost model
      Traditional deployment:
  provisioned capacity + storage/network + operational costs

Serverless deployment, depending on the product:
  requests + billed execution/resources + provisioned warm capacity
  + gateway/queue/storage/network + observability and operations

      Request-driven billing can help bursty or infrequent workloads, but does not guarantee lower total cost. A provider may bill wall-clock duration, allocated memory, CPU time, requests or reserved capacity under different plans. Include retries, data transfer and dependent services. See Lambda's pricing dimensions ↗ and its execution-environment lifecycle ↗.

      Key takeaways

      • Serverless delegates host operations while retaining application configuration and correctness responsibilities.
      • Invocation, execution environment and physical server are different concepts.
      • Compare complete workload costs rather than assuming billing covers only useful CPU time.

      Cold starts and execution environment reuse

      A cold start includes work needed to prepare an execution environment before it handles an invocation. It can involve loading code, starting a runtime, initializing libraries and opening dependencies. An initialized environment can serve later work, but reuse and retirement are controlled by the platform rather than guaranteed for a fixed number of seconds.

      Isolation designs differ. Firecracker ↗ is a microVM technology used for function and container services; Workers uses V8 isolates ↗ inside an existing runtime. Neither description establishes a universal end-to-end startup time, and not every serverless product uses the same mechanism.

      Language labels alone do not predict cold-start behavior. Compiled programs are commonly built before deployment, while interpreted or JIT runtimes still perform initialization. Package size, imports, runtime setup, application initialization and dependency calls all matter. Measure the deployed artifact under realistic concurrency instead of ranking languages by a simplistic “interpreted is faster” rule.

      Reduce unnecessary initialization and use supported warm-capacity or snapshot facilities when the latency target justifies their cost and constraints. For example, Lambda offers provisioned concurrency ↗ to pre-initialize capacity. A few periodic pings do not guarantee that future traffic uses the same environment or that a burst avoids additional initialization.

      Compare cold and warm distributions at the required arrival rate. A low startup overhead can still accompany a slow distant database call. A conventional always-running deployment also experiences initialization during replacement or scaling, so evaluate the request path and readiness policy rather than the deployment label alone.

      Key takeaways

      • Cold starts prepare execution environments; warm reuse is helpful but not guaranteed durable state.
      • Benchmark artifact, runtime and dependency initialization instead of inferring it from language category.
      • Supported warm-capacity controls are more explicit than synthetic pings, with their own cost and limits.

      Duration, connections and stateful protocols

      Function runtimes have quotas for duration, concurrency, memory, payloads and network activity. For standard Lambda function invocations, 15 minutes is a maximum execution duration, not a minimum. Other modes and services can differ, and HTTP gateways can impose shorter timeouts than the compute layer. Check the current Lambda quotas ↗ and the limits of each component in the actual request path.

      A durable workflow can coordinate steps over a long period without one function continuously executing for that whole time. A thirty-minute media job still needs a runtime and orchestration design that supports its work; splitting a workflow is different from assuming a short function can ignore its timeout.

      Serverless functions can use ordinary databases when their networking and drivers support it. Reuse safe clients where documented, bound connection demand across execution environments and use a suitable pooler, proxy or data API when needed. You do not inherently need to replace the database with a product called “serverless.” See Lambda's RDS connection options ↗ and environment reuse guidance ↗.

      WebSockets and other long-lived protocols need a supported connection-lifetime design. Some platforms provide gateways or stateful components to manage them, while a short HTTP handler may be unsuitable. Keep durable state outside disposable execution environments, and handle connection loss, replacement and duplicate events deliberately.

      Key takeaways

      • Check runtime and gateway limits separately; a workflow's total lifetime differs from one invocation.
      • Serverless can use conventional databases, with controlled connections and compatible networking.
      • Choose explicit support for persistent protocols and keep durable state outside disposable environments.

      Choose the next change from evidence

      Use the problem, constraints and ownership model to choose an architecture. Serverless can suit event-driven tasks, variable demand and independently triggered operations. A continuously running service may fit steady utilization, particular runtime requirements or a required connection model. Either can serve important user-facing work if its measured behavior and safeguards meet the requirements; latency-sensitive does not automatically mean “never serverless.”
