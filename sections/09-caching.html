      Lesson 09

      Caching

      Reuse work you have already done. Caching makes repeated reads and expensive computations cheaper by keeping useful results close to the consumer. The design challenge is deciding what to keep, how long to trust it and what happens when it disappears.

      What caching actually saves

      Caching stores reusable data or computed results somewhere cheaper or faster to access, so later requests can avoid repeating the original work. That saving might be a database query, a calculation, an external API call or a long network journey.

      Usually the cache holds a frequently used subset of a larger dataset: the working set. A small dataset might fit entirely. What makes it a cache is the role it plays, not a requirement that it contain only part of the data or live in RAM. A copy on a nearby disk can be quicker to serve than the same file across an ocean.

      TermMeaning
      Cache hitA usable entry exists for the requested key.
      Cache missNo usable entry exists; load or compute the result from its source.
      Cache fillStore that result so a later request can reuse it.
      Stale dataA cached result no longer reflects the current source or required freshness.
      Source of truthThe authoritative system used to establish the correct value.

      A hit saves work; a miss can add work because the application checks the cache before contacting the source. Storage, network calls, serialization and keeping copies consistent all have costs. Caching is useful when the reuse outweighs those costs.

      Key takeaways

      • A cache reuses data or computation to reduce latency, load or cost.
      • A hit finds a usable result; a miss needs the original work.
      • A cache can use RAM or disk, and its contents may be stale or absent.

      Recognizing a useful caching workload

      Look for repeated reads, expensive results and a clear tolerance for older data. Popularity alone is not enough: two requests must be allowed to share the same answer. These patterns illustrate the idea without assuming a particular company's private architecture.

      WorkloadReusable workWhat affects correctness?
      Search resultsResults or intermediate computations for repeated searches.Query, language, location, personalization and index changes.
      Trending topicsA periodically computed regional ranking.Region, audience and how much delay the product permits.
      Video deliveryEncoded video segments stored near viewers.Content version, rendition and access policy.
      Product or profile pagesRepeatedly requested descriptions, images or public fields.Edits, privacy changes, prices and stock availability.

      Search engines do not crawl and rebuild the entire web index for each query. Crawling, indexing and serving results are distinct stages; caching can avoid repeated work within a system that already maintains an index. Google's overview of search.

      Netflix provides a concrete delivery example: Open Connect works with ISPs and embedded appliances to localize video traffic. This reduces the amount of content that needs to cross distant networks for every viewer.

      Key takeaways

      • Repeated, costly reads with an acceptable freshness window are good candidates.
      • Cache matching results, including their location, audience and other relevant inputs.
      • Nearby copies reduce network work; stored computations reduce repeated processing.

      Hardware caches and the memory hierarchy

      Caching appears at several levels of a computer. CPU caches keep recently used instructions and data close to execution units. RAM holds active application data. Persistent storage holds data beyond a process or machine restart. These layers cooperate.

      LayerTypical roleImportant distinction
      L1, L2 and L3 CPU cachesReduce time spent fetching instructions and data from memory.Small and fast; sizes and sharing between cores depend on the processor.
      RAM / main memoryHold the active data of applications, databases and caches.Fast, usually volatile and more expensive per unit of capacity than disk.
      SSD / HDDRetain larger datasets without continuous power.SSDs are electronic; HDDs have moving parts. Both differ from RAM.

      Why sequential access can help

      CPUs move data in chunks called cache lines. Traversing contiguous array elements often reuses a line that is already loaded, and hardware prefetching can anticipate upcoming accesses. This is spatial locality. Reusing the same data soon is temporal locality. It does not mean the CPU always copies an entire array into its cache.

      Random-access memory permits direct addressing without mechanically seeking to a disk position. Actual latency still depends on the hardware and access pattern. At the application level, a remote cache also has network and serialization costs. As covered in Databases & PostgreSQL, a database can serve reads from its own memory buffers, so a database call does not necessarily cause physical disk I/O.

      Key takeaways

      • CPU caches exploit locality; application caches reuse larger results.
      • RAM is usually volatile; SSDs and HDDs provide non-volatile storage.
      • Measure the whole request, including network costs and existing database caching.

      CDNs: caching near the user

      A content delivery network serves content through geographically distributed locations. The origin supplies the original content; an edge server can keep a reusable copy. A point of presence (PoP) is a location containing network infrastructure and servers.

      1. The client requests a resource such as an image, stylesheet or video segment.
      2. The CDN directs the request to a suitable edge using DNS and/or network routing.
      3. On a usable cache hit, the edge responds with its stored copy.
      4. On a miss, it obtains content from an upstream cache or the origin, then caches it if policy permits.

      “Nearest” usually means a suitable network path, taking routing, availability and capacity into account. It is not a promise that the geographically closest server handles every request. The benefit is less origin traffic and a shorter delivery path. Cloudflare's CDN overview.

      Delivery and video quality are different decisions

      Encoding produces different video renditions. An adaptive streaming player can choose among them based on bandwidth, buffer state and device capabilities. CDN routing delivers the selected segments. DNS does not normally switch a viewer to a “720p-only server” because their connection is slow. Edge caches can also use disk storage for large media objects.

      HTTP freshness and privacy

      Response directivePurpose
      max-age=60Set a freshness lifetime of 60 seconds.
      s-maxage=300Set a shared-cache freshness lifetime, overriding max-age there.
      privateAllow eligible private caching but prohibit shared caching.
      no-cacheRequire successful validation before reuse; storage can still be allowed.
      no-storeDirect compliant caches not to store the request or response.

      An expired HTTP response can remain stored and be revalidated, for example using an ETag. Authentication and privacy-sensitive responses need deliberate caching rules; a URL alone may not distinguish different users' responses. Header semantics come from RFC 9111; CDN configuration must respect them.

      Key takeaways

      • A CDN brings reusable content closer to consumers and reduces origin traffic.
      • Routing selects a delivery path; adaptive streaming selects video quality.
      • HTTP freshness, revalidation and privacy directives determine safe response reuse.

      DNS caching: avoiding repeated lookups

      DNS returns records, including IPv4 A and IPv6 AAAA addresses. Names can have multiple addresses or aliases. Browser, OS and resolver caches avoid repeated lookups.

      Simplified cold lookup for example.com
      Client asks its recursive resolver
  Resolver asks a root server       → referral to .com servers
  Resolver asks a .com server       → referral to example.com's nameservers
  Resolver asks an authoritative server → answer for the requested record
Resolver caches the answer and returns it to the client

      Cached referrals skip intermediate steps. The resolver follows referrals iteratively on the client's behalf. An authoritative server answers from its zone, rather than recursively looking up the record elsewhere.

      Browser and OS behavior varies, including when encrypted DNS is used, so there is no universal “OS first, browser second” sequence. DNS TTLs govern reuse. Changing an authoritative record does not instantly replace copies already cached elsewhere. DNS resolution and caching.

      Key takeaways

      • Browser, OS and resolver caches can avoid DNS network work.
      • On a cold lookup, the resolver follows referrals to an authoritative answer.
      • Cached records and referrals have TTLs; changes are not immediately visible everywhere.

      Application caches: local and shared

      An application can keep entries inside its own process or use a separate cache service. Both are software-managed caches. Neither requires you to directly manage CPU cache lines.

      PlacementUseful propertyTradeoff
      In-process cacheA lookup avoids a network round trip.Each process has its own copy; restarts lose it and replicas can disagree.
      Shared cache serviceApplication replicas reuse a common store.Adds network latency, operational cost and another failure dependency.

      Redis and Valkey provide key-based access to data structures such as strings, hashes, lists and sets. A string value can contain serialized JSON. Memcached provides a simpler cache of keys and opaque values. These are not relational tables with SQL joins. Amazon ElastiCache is a managed service for supported cache engines, not a separate caching strategy.

      In-memory does not settle persistence

      Redis can persist data using RDB snapshots, an append-only file (AOF), both, or neither. Recovery and possible data loss depend on configuration. Memcached is normally treated as disposable cache storage; do not assume every in-memory engine restores all entries after a restart. See Redis persistence options.

      A shared Redis deployment does not have to span the globe. Put a cache near its callers unless the architecture has a reason otherwise. Multiple application instances can share a single cache service; distribution across cache nodes is a separate deployment decision.

      Key takeaways

      • Local caches avoid network calls but create independent copies per process.
      • Shared caches centralize reuse and introduce a network dependency.
      • Data structures, persistence and deployment guarantees depend on the selected engine and configuration.

      Cache-aside: load only when needed

      Cache-aside, also called lazy loading or lazy caching, makes the application responsible for consulting and filling the cache. It is a useful starting point for caching database results.

      1. Validate the request and establish the caller's authorization and scope.
      2. Build a key that identifies the requested result and check the cache.
      3. On a hit, decode and return the permitted cached data.
      4. On a miss, read the authoritative source or compute the result.
      5. Store a successful result with an appropriate TTL, then return it.

      Only requested data is loaded, but the first request pays the miss cost. Expiration, eviction and restarts create later misses too. Cache-aside can be combined with updates on writes. AWS caching patterns.

      A small Redis example

      Redis commands — illustrative project data
      SET cache:v1:org:org-1:project:project-2 '{"id":"project-2","name":"Website"}' EX 60
GET cache:v1:org:org-1:project:project-2
TTL cache:v1:org:org-1:project:project-2
DEL cache:v1:org:org-1:project:project-2

      SET ... EX 60 writes the value and its 60-second expiration in one command. GET returns the stored string or a missing-value response; TTL inspects the remaining lifetime; DEL invalidates the entry. JSON encoding and decoding happen in the application when using this string representation. A normal GET does not refresh the TTL. Redis SET options.

      Use the client library for your language, with connection reuse and bounded timeouts. For a disposable result cache, a failed cache fill should not erase a successful database read. A cache timeout is an operational error to record, even if the fallback path treats it like a miss. Do not replace a valid value with a cached transient server error.

      Key takeaways

      • Cache-aside checks the cache, loads on a miss and saves a reusable result.
      • Set the value and TTL together; reads do not automatically extend expiration.
      • Preserve authorization and use bounded, observable cache failure handling.

      Writes, invalidation and consistency

      A cache fill answers “how does data get here?” A write strategy answers “what happens when the source changes?” These are related decisions, not mutually exclusive product choices.

      StrategyWrite pathTradeoff
      Invalidate after commitCommit the database change, then remove affected cache entries.The next reader reloads; invalidation must reach every relevant cached view.
      Write-through / update on writeUpdate the cache as part of the write workflow, alongside persistence.Adds write work and can populate values nobody reads.
      TTL-only refreshLeave the entry until it expires.Simple, but readers may see an older value during the allowed window.

      Write-through designs vary in who coordinates persistence and caching. An application that commits PostgreSQL and then writes Redis has performed two operations across two systems. Calling this write-through does not make the pair atomic: the second write can fail, or concurrent writers can update the cache out of order.

      Why deleting a key is not a complete consistency guarantee

      Suppose a reader misses the cache and reads version 1. Before it fills the cache, a writer commits version 2 and deletes the key. The original reader then stores version 1. The cache is stale again even though invalidation happened after the commit.

      A TTL limits how long that entry remains reusable. Stronger requirements can need version checks that reject older fills, coordinated refreshes or an authoritative read. Changes made by scripts and background jobs must also participate in the update policy. Document the consistency guarantee instead of promising that every cache read is always fresh.

      Key takeaways

      • Choose how writes update or invalidate cached copies.
      • A database write plus a cache write is not automatically one atomic operation.
      • Concurrent fills can reintroduce stale values; use a policy suited to the required consistency.

      Cache keys and freshness budgets

      A key is a claim that requests using it may share one result. If the key omits an input that changes the answer, the cache can return the wrong data even when it is fast and has a high hit rate. Begin with the response contract from API Design.

      Result depends on…Key or policy must account for…
      Organization or tenantThe verified tenant scope, not just the resource ID.
      User permissionsThe authorized audience or per-user scope, plus fresh permission checks where required.
      List optionsFilters, sort order, pagination and page size in a stable representation.
      PresentationLocale, currency, units or other variants that change the response.
      Payload formatA cache schema version so deployments do not decode an incompatible old value.

      Use validated, normalized inputs so equivalent requests generate the same key. Avoid placing passwords, bearer tokens or unnecessary personal data in keys that may appear in logs. Including a user ID does not replace authorization, and cached permissions can themselves become stale after revocation.

      Choose TTL from the permitted delay

      A time to live sets how long an entry remains eligible for reuse. A project activity summary might tolerate a short delay; a payment authorization cannot use the same assumption. Weather forecasts, current observations and emergency alerts also have different freshness needs. “Cache all weather data for an hour” is not a universal rule.

      A TTL measures time since a cache write, not necessarily time since the source was accurate. If the source is a lagging replica or another cache, the value can already be old when stored. Rewriting an old value with a new TTL can extend its apparent lifetime. Carry a source version or observation time when the age matters, and set a maximum acceptable age explicitly.

      Key takeaways

      • Key every input and security scope that changes the result.
      • TTL comes from the product's freshness budget, not an arbitrary default.
      • Entry lifetime and source-data age are different; re-caching old data does not make it fresh.

      Expiration, invalidation and eviction

      Expiration makes an entry unusable after its lifetime. Invalidation deliberately removes or marks a result stale after a change. Eviction makes space when the cache reaches its memory budget. An entry can be evicted before its TTL ends.

      Redis policyWhat happens under memory pressure?
      noevictionReject writes needing additional memory; existing reads can continue.
      allkeys-lruPrefer removing least recently used entries.
      allkeys-lfuPrefer removing least frequently used entries.
      allkeys-randomChoose entries randomly.
      volatile-ttlAmong entries with expiration, prefer the shortest remaining TTL.

      LRU tracks recency; LFU tracks frequency. Redis uses approximations, and its LFU history decays. The volatile-* policies only consider keys with expiration. Ordinary TTL expiration still works independently of memory-pressure eviction. noeviction is a legitimate choice when silently losing entries is unacceptable, but write failures need handling. Redis eviction policies.

      Key takeaways

      • Expiration limits time; invalidation responds to change; eviction frees capacity.
      • LRU favors recent use; LFU favors frequent use.
      • TTL does not guarantee an entry will survive until expiration.

      Caching database queries and external APIs

      Expensive database results

      Imagine the project dashboard aggregates task counts across several tables. Many visits repeat the same calculation. After checking the SQL and indexes, cache the authorized result if the dashboard permits a small delay. This can avoid repeating joins and aggregations described in the database lesson.

      Cache the result your application needs, not a promise that the underlying query will never run again. Each relevant task change may affect a project summary, a filtered list and a user's assigned-task count. Invalidating only the individual task entry leaves those derived views unchanged. Keep the number of cached views manageable and document their dependencies.

      External API responses

      Reusing a provider's response can reduce latency, paid calls and rate-limit consumption. For a weather card, include location and units in the key, respect provider terms and update frequency, and show the observation time when useful. A provider timeout should not silently become a successful empty forecast with a long TTL.

      Read models and final decisions

      A cached product description can serve many page views. A displayed stock estimate can be approximate if the product permits it. The final order still needs an authoritative stock check or reservation and a current price decision. A fast cached read does not enforce a transaction's invariants.

      Short-lived negative caching can reuse a legitimate “not found” result to avoid repeated lookups. Distinguish that result from an outage, keep its scope correct, and invalidate it when the resource is created. Otherwise a newly created item may appear absent.

      Key takeaways

      • Cache repeated query results and provider responses when delay is acceptable.
      • A write can affect multiple cached views, not only one resource key.
      • Critical transactions still enforce authoritative prices, inventory and other invariants.

      Sessions: fast storage can hold important state

      In a server-side session flow, the client carries an opaque session identifier and the server looks up the associated authenticated session. A shared in-memory store can make that lookup efficient across application replicas. See Authentication & Authorization for the distinction between a session identifier, cookies and authorization.

      If Redis contains the only session record, it is the session's state store. It is not merely a copy that can be reconstructed from a profile row. Losing a valid session may log the user out; inventing a replacement session from the user ID would bypass authentication.

      • Enforce the application's idle and absolute expiry rules; refreshing an idle TTL must not erase the absolute deadline.
      • Invalidate the session on logout or revocation according to the authentication contract.
      • A missing, expired or unreadable session must not grant access. An outage can require a temporary service error.
      • Choose persistence, availability and eviction behavior for session state deliberately, separately from disposable result caching.

      The storage technology does not decide the meaning of the data. One Redis deployment might hold a rebuildable dashboard result; another might hold authentication state whose loss changes user access. Their acceptable failure behavior is different.

      Key takeaways

      • Shared session storage lets application replicas validate the same session.
      • Session records may be authoritative state, not disposable cached copies.
      • Expiry, revocation and storage failures must preserve authentication rules.

      Rate limiting with shared counters

      A rate limiter can run in middleware before an expensive handler. For example, allow an account 50 requests per calendar minute across all application replicas. A shared store coordinates the counter so adding servers does not multiply the allowance.

      1. Identify the caller using a verified account, API key identity or appropriately derived client IP.
      2. Build a key for the caller, the limited operation and the current minute bucket.
      3. Atomically increment the bucket counter and establish its bounded expiration.
      4. Allow counts 1 through 50; reject later requests with 429 Too Many Requests.
      5. Return useful retry information, such as Retry-After until the next allowed window.

      Atomic operations matter

      A separate read, increment in application code and write can lose updates when requests overlap. Redis INCR handles the increment atomically, but a separate expiration command can still be skipped if the application crashes. Use a correctly designed atomic script or transaction for the complete counter lifecycle. Repeatedly extending a single counter's TTL on every request changes the intended window behavior. Redis counter and rate-limiter examples.

      Trust the proxy configuration

      Do not blindly accept X-Forwarded-For from the client. Derive the address using a known proxy chain that sanitizes forwarded headers and correctly configured framework trust settings. Otherwise callers can spoof identities to evade an IP-based limit. Express guidance for trusted proxies.

      A fixed-minute window allows boundary bursts: 50 requests just before the boundary and 50 just after it. A sliding-window or token-bucket policy can provide different burst behavior. Shared IPs also group unrelated users, which is why an authenticated identity is often a better key when available.

      Rate-limit counters are enforcement state. Evicting a counter can reset someone's allowance. Decide whether storage failure should reject requests, permit a restricted fallback, or allow traffic; that decision depends on whether the limit protects security, cost or availability. It must be explicit rather than an accidental “all failures are cache misses” rule.

      Key takeaways

      • Shared, atomic counters enforce a limit across replicas.
      • Counter updates and expiration need coordinated handling.
      • Trust forwarded IPs only through configured proxies; account for bursts, eviction and outages.

      Stampedes, cold starts and cache failures

      A popular key expires. A thousand requests arrive before the first database read finishes. Each sees a miss and repeats the same expensive query. This is a cache stampede: the cache's miss path amplifies the work it was meant to save.

      • Coalesce requests: let concurrent requests for one key share one in-flight load. An in-process mechanism only coordinates that process.
      • Stagger expiration: use bounded TTL variation so many different keys do not expire together; stay within the freshness budget.
      • Refresh selectively: refresh hot entries before expiry or serve an explicitly permitted stale result while one refresh runs.
      • Limit fallback load: bound origin concurrency and shed excess requests rather than flooding the database.

      Restarting or deploying a cache can produce a large cold working set. Test that state as well as the warm-cache case. A cache outage can overwhelm the database if every request immediately falls back to it. Use short cache deadlines and a bounded recovery path. AWS lessons on cache failures and load.

      Stale-while-revalidate is a freshness policy, not permission to ignore correctness. It may suit a public summary but conflict with an access revocation. If coordination uses locks, handle timeouts and worker failures; an indefinitely held refresh lock creates another outage.

      Key takeaways

      • Simultaneous misses can stampede the origin.
      • Coalesce loads, spread expirations and cap fallback traffic.
      • Test cold starts and outages; serve stale data only where the contract allows it.

      Measure the benefit and review the design

      Cache hit rate is the fraction of lookups served from the cache. Define whether your metric counts timeouts, revalidations or only normal key lookups, so comparisons remain meaningful.

      Illustrative measurements, not latency guarantees
      hit rate = hits / (hits + misses)

900 hits and 100 misses → 90% hit rate

If a hit takes 2 ms and a complete miss path takes 42 ms:
mean read time = 0.90 × 2 + 0.10 × 42 = 6 ms

      The mean does not describe the slowest requests. Track p95 and p99 latency, miss latency, database and provider load, memory use, evictions, expirations, cache errors and freshness violations. A high hit rate can still hide incorrect data or expensive tail misses.

      A practical design checklist

      1. Work: identify the repeated cost and measure the uncached path.
      2. Authority: identify the source of truth and whether entries are rebuildable.
      3. Identity: include the relevant inputs, tenant and authorized audience in the key.
      4. Freshness: define acceptable age, TTL and write invalidation or update behavior.
      5. Capacity: choose memory limits and eviction behavior suited to the data.
      6. Failure: plan for concurrent misses, cold starts, timeouts and unavailable storage.
      7. Evidence: compare latency, source load and correctness before and after caching.

      Start with a workload that benefits from reuse. Add the smallest cache that meets its freshness and failure requirements, then verify the effect. A cache is successful when it saves meaningful work while preserving the application's promises to its users.

      Key takeaways

      • Hit rate describes reuse; latency and source load show the practical benefit.
      • Monitor tail latency, freshness, capacity and failures alongside averages.
      • Define keys, expiry, write behavior and recovery before relying on a cache.
