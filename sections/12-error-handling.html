      Lesson 12

      Error Handling & Fault Tolerance

      Databases fail, dependencies time out and valid-looking requests reach unexpected edge cases. Build the habit of detecting failures, limiting their impact and recovering safely, while giving users useful responses and protecting their data.

      The fault-tolerant mindset

      Error handling starts when you design an operation. Decide what success means, what can fail, which changes might already have happened, and how a caller should respond. A backend cannot prevent every failure, but it can make failures easier to detect and less damaging to users.

      Think of a signup request: validation, storing the account and scheduling a verification email are separate steps. If the email provider is unavailable after the account is stored, the account still exists. Returning an unexplained failure or claiming the email was delivered gives the user a misleading picture. The response and recovery plan must reflect the actual state of the workflow.

      Success has a business meaning

      A running process and a 200 response do not prove that an operation was correct. Applying a discount twice can quietly lose money while every infrastructure dashboard stays green.

      Work through four questions for each important operation: how will we prevent known mistakes, detect failures, contain their impact and recover without corrupting data? This lesson focuses on those decisions; the implementation belongs in the layers introduced in the request lifecycle.

      Key takeaways

      • Plan failure behavior alongside the successful path.
      • Distinguish a successful HTTP exchange from a correct business outcome.
      • For every important workflow, plan prevention, detection, containment and recovery.

      Logic errors: correct execution, wrong result

      A logic error lets the program run while producing the wrong outcome. An order might receive the same discount twice, a shipping calculation might become negative, or a permission check might use the wrong account. There may be no exception for an error handler to catch.

      These bugs often start with misunderstood requirements, an incorrectly implemented rule or an overlooked edge case. Clarify rules with concrete examples before implementation: can discounts combine, what happens at a threshold, how is rounding applied, and what should a repeated request do? Review these examples with the people responsible for the product rules.

      Turn requirements into invariants

      An invariant is a rule that must remain true through an operation. For a store whose policy forbids negative shipping charges, that rule should be explicit. Other examples include one redemption per eligible coupon or an order total agreeing with its line items and adjustments. Write rules for the actual business; do not invent universal rules that legitimate refunds or credits violate.

      Check important boundaries, repeated actions, concurrency and partial failure in tests. Enforce appropriate invariants in the domain logic and database, and monitor outcomes in production. A sudden rise in discount amounts or a mismatch between accepted orders and completed payments can reveal a problem that exception counts miss.

      Key takeaways

      • Logic errors can damage data or business outcomes without crashing anything.
      • Translate ambiguous requirements into examples and explicit invariants.
      • Use boundary tests and business metrics; exception handling alone cannot detect incorrect results.

      Database failures

      Database failures have different causes and need different responses. Treating all of them as bad input hides server problems; treating all of them as unexpected server failures gives users no useful way to resolve ordinary conflicts.

      FailureWhat it can meanWhat to investigate
      Connection or pool timeoutThe app cannot acquire a usable connection.Reachability, credentials, pool wait time, leaked connections and database capacity.
      Constraint violationA write conflicts with a unique, foreign key, required-value or check constraint.The relevant business rule, concurrent changes and the input contract.
      Query or schema errorMalformed SQL, an absent table or a deployment/schema mismatch.The query and migration state; retrying a typo will not fix it.
      Slow query or lock timeoutWork or waiting exceeded its budget.The query plan, contention, transaction duration and load.

      Connection pools are bounded resources

      A pool reuses established connections and limits how many operations can use them concurrently. Waiting for a pool slot is different from executing a slow query. Always release connections, keep transactions appropriately short and account for the total connections across application replicas. Increasing every pool size can overload the database rather than solve the bottleneck.

      Validation cannot replace constraints

      Two signup requests can both check that an email is available and then attempt to insert it. Only one can succeed when a unique constraint protects that value. Keep database constraints even when the application performs friendly checks, and handle their failures deliberately. A referenced author can also disappear between an application check and a later write.

      Deadlocks and transaction retries

      A deadlock occurs when transactions form a cycle of waiting for one another's locks. PostgreSQL detects this and aborts a transaction. Short transactions and consistent lock ordering reduce the risk. For retryable deadlock or serialization failures, retry the complete transaction, including the decisions that produced its queries, with bounded attempts. Keep external side effects safe from duplication. See PostgreSQL's transaction retry guidance.

      An empty query result is different: ordinary SELECT queries can return zero rows successfully. Some single-row driver helpers report a special “no rows” condition. The application decides whether that means a missing resource or a perfectly valid empty list. The database lesson covers the underlying constraints and transactions.

      Key takeaways

      • Separate connection, constraint, query and concurrency failures before deciding what to do.
      • Validation improves feedback; database constraints still protect against concurrent writes.
      • Retry whole transactions only when appropriate; an empty result is not automatically an error.

      External services and uncertain outcomes

      Email providers, payment services, identity providers and object stores are dependencies with their own availability, limits and failure modes. DNS failures, connection problems, slow responses and outages can interrupt otherwise correct application code.

      Classify the failure before reacting. A temporary connection failure may justify another attempt. A revoked integration credential needs an operator to fix it. A user's invalid login is an expected authentication outcome. Your own invalid provider API key is a server configuration problem, so it should not become a message telling the user to change their password.

      Providers may also reject excess traffic with 429 Too Many Requests, sometimes including a Retry-After delay. Reduce the request rate and respect the delay where supplied. If the provider's shared quota is exhausted, that does not automatically mean this particular user exceeded your application's quota. See the HTTP definition of 429.

      A timeout leaves a question

      The remote operation may have completed while its response was lost. Treating a timeout as proof that nothing happened can duplicate a charge, email or order. Use the provider's idempotency mechanism or reconcile the operation's status before repeating a side effect.

      Offload suitable work through durable background jobs. That gives delayed work a recovery path, but does not guarantee immediate delivery. Tell the user whether work was accepted, remains pending or has completed.

      Key takeaways

      • Plan for network failures, rejected credentials, quotas and provider outages.
      • A timeout does not tell you whether the remote operation completed.
      • Protect repeated side effects and describe asynchronous progress honestly.

      Validation errors at the boundary

      Validate input before it reaches work that assumes a particular shape or meaning. Check types, formats, required fields and limits: a date must be acceptable, a quantity must fit the allowed range, and a collection must not exceed its maximum size. Invalid input can come from mistakes, outdated clients or deliberate abuse.

      Frontend validation improves the experience, but callers can bypass it. The backend enforces the contract. Validate path parameters, query parameters and relevant headers as well as request bodies: a GET request with no body still has inputs. Validating an ID also does not prove the caller is allowed to access that resource.

      Give safe, actionable field feedback: for a catalog that limits book names to 500 characters, explain that limit when a user sends 700 characters. Do not echo arbitrary input or entire request bodies into the error. Use your documented policy for 400 and 422 responses consistently, as discussed in Validations & Transformations.

      Key takeaways

      • Validate types, formats, required fields and limits on the backend.
      • Requests without bodies still need parameter checks and authorization.
      • Return safe field-level guidance so callers can correct rejected input.

      Configuration errors: fail before serving traffic

      A feature works locally because its API key exists in a development environment file. The code is deployed, but the production configuration is missing that key. Without an early check, the first user to reach the feature discovers the mistake through a failed request.

      Load and validate mandatory configuration during startup: presence, types, allowed values and basic consistency. Report which setting needs attention without printing its secret value. If the application cannot function safely, stop initialization before accepting traffic. Optional features can instead remain explicitly disabled when their configuration is absent.

      This works together with deployment health gates. A rollout can keep the previous healthy version serving while a new version fails its checks, if that behavior is configured. A startup exception alone does not guarantee a safe rollout. Check the deployment policy, readiness behavior and compatibility with any schema changes.

      Startup validation is also not a permanent guarantee. A correctly shaped credential can be rejected by its provider or revoked later. Continue handling runtime failures, and validate configuration changes when they are loaded or rotated.

      Key takeaways

      • Validate required configuration before the application starts serving users.
      • Failing startup protects availability only when the rollout preserves healthy capacity.
      • Hide secret values and handle credentials or settings becoming invalid at runtime.

      Health checks and proactive detection

      A health endpoint returning 200 proves only that its particular check passed. It does not prove that checkout, email delivery or every database query works. Give each check a clear question and connect its result to an appropriate action.

      CheckQuestionTypical use
      LivenessCan this process still make progress?Detect a stuck process that needs restarting.
      ReadinessCan this instance accept traffic now?Withhold traffic during initialization or an inability to serve requests.
      StartupHas initialization completed?Give startup work a bounded window before normal health decisions apply.

      Keep liveness focused on the process. Making a shared database outage fail every instance's liveness check can trigger a restart storm without fixing the database. Readiness may consider essential dependencies; an optional recommendations service should not automatically remove every otherwise usable instance from traffic. Kubernetes' probe documentation illustrates these distinct responsibilities.

      Check useful work separately

      Use deeper monitoring to check database connectivity, representative query performance and important invariants. A lightweight query tests a narrow capability; it does not verify the integrity of the whole database. Keep checks bounded and avoid repeatedly running expensive queries in a frequently polled health endpoint.

      Synthetic workflows can test an email sent to a controlled inbox or an authentication exchange with a dedicated test identity. Use supported sandbox or non-chargeable checks for payment integrations. Isolate test data, limit frequency and avoid real customer side effects. A check that succeeded five minutes ago is useful evidence, not a promise that the next operation will succeed.

      Key takeaways

      • Liveness, readiness and startup checks answer different operational questions.
      • Keep probes cheap; do not restart healthy processes merely because a shared dependency failed.
      • Use controlled synthetic workflows and deeper monitoring to check actual capabilities.

      Observe failures and business health

      Monitoring tells you when behavior crosses an important threshold. Observability gives you enough evidence to investigate what happened. Together they should cover HTTP requests, database operations, external calls, background work and the business results those operations produce.

      SignalExamplesWhat it helps reveal
      FailuresUnexpected errors, dependency timeouts, failed jobs.Which operations are failing and where.
      PerformanceResponse-time percentiles, throughput, database pool waits.Slow paths, contention and growing demand.
      CapacityMemory, CPU, queue depth and oldest job age.Saturation or a backlog that workers cannot clear.
      Business outcomesCompleted orders, successful logins, failed payments, discount totals.Incorrect or incomplete work even when responses look healthy.

      Rising latency or resource use can be an early warning, but interpret it alongside traffic and normal patterns. A drop in successful orders needs context: did demand fall, did requests fail, or did a logic change reject valid purchases? Track both counts and rates rather than judging one isolated number.

      Structured logs record named fields such as the operation, safe error category, duration and request ID. Traces connect work across services. Use correlation IDs to connect an incident to its evidence, while keeping secrets out of that evidence. Alert on actionable symptoms, assign an owner and make the relevant recovery instructions easy to find.

      Key takeaways

      • Track errors, latency, throughput and resource pressure together.
      • Monitor business outcomes to catch failures that still return successful HTTP responses.
      • Connect alerts to useful context, an owner and a recovery path.

      Immediate responses and safe retries

      First ask whether repeating the same operation can help. Invalid input needs correction. A broken query or revoked credential needs a fix. A temporary network failure may recover. An unknown outcome needs investigation before repeating a side effect. “Recoverable” describes an operation in context; it is not a property of every error from one service.

      Bound the time and the work

      Set timeouts for dependency calls and an overall deadline for the operation. Include connection acquisition and network work in the budget. Stop retrying when attempts or the time budget are exhausted, and propagate cancellation where supported so abandoned requests do not keep consuming resources.

      Exponential backoff increases the delay between attempts, for example from one second to two and then four. Cap the delay and add jitter so many clients do not retry together. Respect a provider's Retry-After instruction; if it exceeds the current request's budget, defer suitable work or return a clear failure rather than waiting indefinitely.

      Retries add load and can repeat side effects. Coordinate retry ownership: if every layer retries independently, a single user request can multiply into many downstream attempts. Use idempotency for repeated writes and avoid retrying invalid requests unchanged. See AWS's explanation of retry risks, backoff and jitter.

      More attempts are not always recovery

      If all database connections are busy, an immediate retry loop adds more waiting work. Investigate leaked connections, slow queries and excessive concurrency. Limit admission or reduce load while the bottleneck recovers; retries cannot create capacity.

      For a delayed verification email, a durable job can own the retry policy and eventual failure reporting. Its retry budget must also account for the verification token's expiry. Background execution makes waiting possible; it does not make indefinite retries useful.

      Key takeaways

      • Retry only failures that can recover, and only when repeating the operation is safe.
      • Use deadlines, capped attempts, backoff, jitter and provider retry guidance.
      • Assign retry ownership and avoid adding work to an already overloaded dependency.

      Containment and graceful degradation

      Containment limits how far a failure spreads. Graceful degradation keeps useful functionality available when a feature cannot operate normally. If recommendations fail, a product page may still show its main details. If checkout cannot confirm payment, it must not pretend that the purchase completed just to keep the page looking successful.

      A circuit breaker temporarily stops calls to a dependency after a configured failure pattern, then allows limited probes to check for recovery. Separate concurrency limits or worker pools prevent slow optional work from occupying every resource needed by critical work. These capacity boundaries are often called bulkheads.

      Timeouts and bounded queues keep waiting work from growing without limit. Separate processes and message queues can isolate failures and decouple timing, but they do not remove shared database limits or make a growing backlog harmless. Apply backpressure when the system cannot accept work at the incoming rate.

      Choose fallbacks by what they preserve

      Cached product descriptions may be acceptable within a freshness policy. Cached authorization decisions or stale inventory may violate the operation's rules. If a required security check is unavailable, fail closed instead of granting access. If a cache fails, sending every request to the database can also overload the supposed fallback.

      Design and capacity-check the fallback before depending on it. Explain reduced or pending functionality to the user, and retain enough evidence to reconcile incomplete work. The caching lesson distinguishes disposable cached results from state that the application relies on for correctness.

      Key takeaways

      • Limit the spread of failures with deadlines, bounded capacity and dependency isolation.
      • Use fallbacks only when their freshness, permissions and capacity satisfy the operation.
      • Degrade optional features honestly; never turn a failed security check into permission.

      Recovery without losing data

      Recovery should restore correct service while preserving data. The right action depends on what failed and what already changed. A database rollback cannot undo an email already sent or an operation committed by another service. Reconcile those outcomes or use an explicit compensating workflow where the business supports one.

      Automatic recovery needs guardrails

      Restarting a stuck process, retrying a safe job or switching to a healthy replica can help. None is a universal fix: restarting does not repair incorrect logic, and clearing a cache can send a flood of misses to the database. Use bounded recovery attempts, backoff and alerts when the system cannot restore itself. Preserve pending work and expect job redelivery after crashes.

      Manual recovery needs a runbook

      Document how to recognize the incident, who owns it, which preconditions make a mitigation safe, how to perform it and how to verify recovery. Include rollback or escalation criteria. Practice in a controlled environment so an incident does not become the first attempt at restoring a backup or disabling a broken feature. Confirm both service health and affected business records afterward.

      Backups must be restorable

      Choose recovery targets: how much recent data loss is tolerable and how long restoration can take. These are the recovery point objective (RPO) and recovery time objective (RTO). Take protected backups and test restoration. Where supported and configured, transaction-log replay can restore a database to a selected point in time.

      A backup file existing is not evidence that the full application can recover from it. Validate restored records, required configuration and dependencies. Before resuming writes, account for operations completed elsewhere during the outage so recovery does not duplicate them or overwrite newer state.

      Key takeaways

      • Recovery must preserve correctness across partial database and external-service changes.
      • Bound automatic recovery and document, practice and verify manual procedures.
      • Define recovery targets and test restores; a backup alone is not a recovery plan.

      Propagate errors with useful context

      Handle an error where you have enough context to make a meaningful decision. A repository knows which database operation failed. A service knows what that operation means to the business. The HTTP boundary knows how to express the result to the caller.

      1. Repository: preserve the underlying cause and classify known database outcomes using structured driver codes and known constraints.
      2. Service: interpret those outcomes in the operation's context, such as a missing book, a duplicate catalog entry or an unavailable dependency.
      3. Handler: validate incoming data and pass application failures toward the request's error boundary.
      4. Error boundary: record safe diagnostic context and produce the agreed public response.

      Exception-based languages can throw and wrap errors; languages with explicit error values return them through the call chain. Preserve the original cause while adding useful operation context. A stack trace shows execution history, but does not replace the business meaning of the failure.

      Catch locally when you can recover, translate a known outcome or clean up resources. Avoid catching an error merely to ignore it or replace it with a vague message that destroys its cause. Ensure cleanup runs on failure as well as success. Logging the same stack trace at every layer also creates noise; choose a clear owner for the final failure event.

      Central policy still needs local knowledge

      A global handler cannot infer the correct business meaning from every raw database error. Translate known failures into application-level categories where their meaning is clear, and keep repositories independent of HTTP response formatting.

      Key takeaways

      • Preserve causes and add context as failures move through application layers.
      • Recover or translate where the necessary knowledge exists; format HTTP responses at the boundary.
      • Clean up resources and avoid swallowing errors or repeatedly logging the same failure.

      The global error handler

      A global error handler gives request failures a consistent final boundary. It reduces repeated response-building logic and provides a safe default for unexpected exceptions. Depending on the framework, this might be middleware or another central exception-handling facility.

      Known application errors have deliberate responses. Unexpected failures receive a generic server-error response, while diagnostic details stay in protected internal records. This separation is the central approach described by the OWASP Error Handling Cheat Sheet.

      Response elementPurpose
      HTTP statusDescribe the broad outcome using HTTP semantics.
      Stable application error codeLet clients recognize a known failure without parsing human wording.
      Public messageExplain the problem and any useful next step without exposing internals.
      Safe field detailsIdentify correctable input problems where appropriate.
      Request or correlation IDConnect a user's report to internal diagnostic evidence.

      Keep the shape and policy consistent across routes. Share translations for recognized errors, but leave an unknown failure unknown rather than guessing that it must be the client's fault. This policy can be implemented by several small components; it does not require one enormous function.

      The boundary has limits

      Request middleware cannot catch every failure in a separate worker, every unobserved asynchronous task or a process that crashes. Give jobs and other entry points their own error boundaries. If response headers have already been sent, the server cannot replace the response with a new status and error body; streaming protocols need their own failure behavior.

      An unrecoverable process failure may require controlled shutdown and a supervised restart. Do not blindly keep serving from potentially invalid state. A global handler standardizes recoverable request failures; it neither repairs logic bugs nor proves the entire process is healthy.

      Key takeaways

      • Centralize public error policy, response shape and the safe fallback for unknown failures.
      • Use stable application codes and correlation IDs alongside HTTP statuses and useful messages.
      • Workers, fatal process errors and streams need boundaries beyond ordinary request middleware.

      Choose HTTP responses from the operation's meaning

      The layer where a failure originated does not determine its HTTP status. A database conflict can be an expected application outcome; malformed SQL is a server bug. Apply the public contract using the meaning of the operation and what the caller can safely learn.

      StatusTypical meaning
      400 Bad RequestMalformed or otherwise invalid request under the API's contract.
      422 Unprocessable ContentThe content is syntactically valid but its instructions cannot be processed.
      401 UnauthorizedValid authentication credentials are missing; include the appropriate authentication challenge.
      403 ForbiddenThe server refuses the requested action.
      404 Not FoundThe target resource is absent or its existence is intentionally concealed.
      409 ConflictThe request conflicts with the resource's current state.
      429 Too Many RequestsThe caller exceeded a request-rate limit.
      500 Internal Server ErrorAn unexpected server condition prevented completion.
      503 Service UnavailableThe service is temporarily unable to handle the request.

      These distinctions follow HTTP semantics and the definition of 429. Document the choices your API makes instead of letting each endpoint invent a different policy.

      A book catalog example

      • Name too long: a 700-character name violates the catalog's 500-character rule. Return the documented validation status with a safe message about that field.
      • Duplicate name: if this particular catalog requires unique names, a recognized uniqueness conflict can become 409. Book names are not inherently unique across every real catalog.
      • Missing book: a lookup for book 123 finds no accessible resource. The service produces a not-found outcome and the boundary returns 404. An empty search result can still return 200 with an empty collection.
      • Invalid author reference: an author ID in a create-book body cannot be used. Depending on the documented contract, this can be a 422 validation outcome or a 409 state conflict. If the request directly addresses a missing author resource, 404 may be appropriate.

      Do not translate every unique or foreign key violation automatically into a client error. An unexpected constraint failure can reveal an application bug. Use known driver codes and constraint mappings instead of fragile checks against human-readable database messages. Authorization and privacy also affect how much resource information the response should reveal.

      Key takeaways

      • Map application meaning to HTTP status; the originating layer is not enough.
      • Missing individual resources differ from empty collections, and conflicts differ from server bugs.
      • Translate recognized constraints deliberately and document validation and conflict responses.

      Public messages and account enumeration

      Public messages should help callers use the API without exposing SQL, constraint names, stack traces, credentials or internal paths. An unknown failure can say “Something went wrong” and include a support reference. Keep the underlying cause in protected diagnostics. Hiding details reduces information exposure; it does not replace parameterized queries or authorization.

      Authentication needs deliberate ambiguity

      If login says “email not found” for one address and “password incorrect” for another, an attacker can discover which accounts exist. Use a shared response such as “Invalid email or password” for failed credentials, without distinguishing a nonexistent, disabled or locked account.

      Wording alone is insufficient if response status, shape, redirects or processing time reveal the difference. Use established authentication flows that avoid obvious timing discrepancies. Review registration and password-reset responses too; a reset flow can acknowledge the request generically without confirming that an account exists. Combine this with abuse controls rather than treating generic messages as a complete defense. See OWASP's authentication response guidance.

      This is where public error policies need context. A helpful duplicate-entry message in an internal catalog is not automatically appropriate for a public signup form. Revisit the privacy requirements from Authentication & Authorization when applying a shared error format to identity-related routes.

      Key takeaways

      • Return deliberately written public messages and keep internal diagnostics private.
      • Authentication failures must avoid revealing account existence through messages or other differences.
      • A shared error format still needs context-sensitive disclosure rules.

      Logs that help without exposing users

      Logs often leave the application process for collection, storage and analysis. Treat them as sensitive records. Capture the operation, safe error category and correlation ID; prefer an opaque user ID over an email when identity is necessary. User IDs still require protection.

      Exclude passwords, API keys, bearer tokens, session cookies, reset codes and payment-card data. Avoid logging complete bodies or authorization headers. Redact nested exception metadata too; a provider or database error can contain sensitive values even when your own message does not.

      Use structured fields and safe encoding to prevent untrusted text from forging log entries. Restrict access, protect transport and storage, and set retention deliberately. Use severity consistently: expected input rejection is different from an unexpected service failure. The OWASP Logging Cheat Sheet covers data exclusion and log protection.

      Key takeaways

      • Keep enough safe context to investigate an error without recording secrets or unnecessary personal data.
      • Redact exception metadata as well as your own messages, and prevent log injection.
      • Protect log access, transport, storage and retention as part of the error-handling design.
