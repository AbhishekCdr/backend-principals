      Lesson 15

      Graceful Shutdown

      Stop taking new work, give existing work a bounded chance to finish, release resources and exit. A reliable backend plans its departure as carefully as its startup.

      Why shutting down is part of correctness

      A customer is paying for an order when a deployment replaces the server handling the request. The replacement instance may already be healthy, but the old instance still has work in progress. Starting the new server does not finish the old server's requests or transfer its memory to the replacement.

      Graceful shutdown is a controlled transition from serving work to exiting: stop accepting new work, let accepted work finish within a deadline, clean up resources, then terminate. Think of a restaurant closing its entrance while allowing seated customers time to finish their meals. Closing time still has a limit; the restaurant cannot wait forever.

      A limit to the guarantee

      Graceful shutdown reduces avoidable interruptions. It does not guarantee exactly-once processing or prevent every duplicate payment. A provider may complete a charge before the server loses its connection or exits without returning a response. Retrying that operation still requires idempotency, durable transaction state and reconciliation.

      Planned deployments are only one reason a process stops. Scaling down, maintenance and operator actions can also request shutdown. Crashes, machine failures and forced termination may leave no cleanup opportunity, so recovery must also work after an abrupt exit. Connect this topic to fault tolerance and safe job retries.

      Key takeaways

      • Graceful shutdown stops new work, drains existing work, releases resources and exits within a deadline.
      • A healthy replacement instance does not finish requests already running on the old instance.
      • Retries and crash recovery still need idempotency and durable state.

      The process life cycle

      Your application runs inside an operating-system process. Its life cycle includes startup, normal operation and termination. The application can expose more useful operational states than simply “running” or “stopped.”

      StateWhat the application doesAccept new business work?
      StartingValidate configuration, initialize dependencies and prepare listeners.No, until initialization succeeds.
      ReadyServe requests and process jobs normally.Yes.
      DrainingWithdraw from routing, stop work intake and finish accepted operations.No, after the coordinated admission cutoff.
      Cleaning upRelease resources that no active operation still needs.No.
      ExitedThe process has terminated; the supervisor observes its outcome.No.

      Keep the transition into shutdown coordinated and safe to request more than once. Two signals must not launch two competing cleanup routines or reset the deadline indefinitely. If startup fails halfway through, release the resources already acquired even though the application never became ready. The same ownership rules apply to startup failure and normal shutdown.

      Key takeaways

      • Model startup, readiness, draining, cleanup and exit as distinct states.
      • Run one shutdown sequence even when multiple stop requests arrive.
      • Clean up partially initialized applications as well as fully running ones.

      SIGTERM, SIGINT and SIGKILL

      On Unix-style systems, signals notify processes of events. They can come from the kernel, another process or terminal activity. The following signals commonly matter for shutdown; platform-specific behavior should be checked for other operating systems.

      SignalMeaningApplication response
      SIGTERMA termination request, commonly sent by a supervisor.Can be handled to begin graceful shutdown.
      SIGINTAn interrupt; Ctrl+C normally sends it to the terminal's foreground process group.Can usually enter the same shutdown path.
      SIGKILLForced termination.Cannot be caught, blocked or ignored; no application cleanup handler runs.

      Both SIGTERM and SIGINT normally terminate a process unless its handling changes that behavior. Registering appropriate handling is what provides a cleanup opportunity. SIGINT can also be sent programmatically; it does not require a keyboard. See the Linux signal reference.

      A signal does not negotiate extra time. The supervisor defines any grace period and escalation. For example, PM2's documented stop flow sends SIGINT by default, then SIGKILL if its configurable timeout expires. Do not assume every process manager starts with SIGTERM or gives the same amount of time.

      Use your runtime's signal notification or lifecycle facility to trigger normal shutdown code. Low-level POSIX signal handlers have strict restrictions on safe operations; arbitrary logging, database calls and cleanup should not run directly inside such a handler. See signal-handler safety.

      Key takeaways

      • Handle SIGTERM and SIGINT through one coordinated shutdown path.
      • SIGKILL provides no cleanup opportunity; SIGINT is not restricted to keyboard input.
      • Check your supervisor's actual stop signal and deadline.

      One coordinated shutdown sequence

      The exact APIs differ across frameworks, but the sequence should protect work before removing the resources it uses. For a service with HTTP handlers and background workers, a typical plan is:

      1. Enter draining once. Record the reason and establish the overall deadline.
      2. Withdraw from traffic. Mark the instance unready and coordinate removal from routing.
      3. Stop new work intake. Stop admitting new requests, scheduling tasks and claiming jobs.
      4. Drain accepted work. Wait for active requests and jobs; keep their dependencies available.
      5. Apply the deadline policy. Cancel remaining work cooperatively and use bounded forced cleanup if necessary.
      6. Release dependencies. Close clients, pools and owned resources after their users stop.
      7. Flush telemetry and exit. Allow a short flush window and report the actual shutdown outcome.

      Some steps overlap. An HTTP request may finish while routing updates propagate, and independent worker pools may drain concurrently. What matters is the dependency relationship: a worker that still needs the database must finish before that database pool closes.

      If an accepted request needs to enqueue a durable job, leave its producer connection available until the enqueue finishes. Local workers can stop claiming jobs while other healthy workers process queued work. An HTTP framework's shutdown method does not automatically track every goroutine, timer or detached task your application started.

      Key takeaways

      • Stop producers of new work before waiting for the active work to finish.
      • Keep shared dependencies alive until all their users have stopped.
      • Track application-owned tasks explicitly; HTTP shutdown alone is not whole-process shutdown.

      Draining HTTP requests

      An in-flight request has been accepted and has not yet finished. During draining, let these requests complete while preventing the instance from accumulating more work. A request that is halfway through validating an order or writing a response should not lose its connection just because a deployment began.

      Closing the listening socket only stops new connections. Existing HTTP/1.1 keep-alive connections can carry more requests, and HTTP/2 can carry multiple streams on one connection. Use your server's protocol-aware shutdown facility and verify how it handles existing connections, new requests on them and active response bodies.

      Illustrative request timeline
      Request A accepted -------- processing -------- response completed
Request B accepted ------------ processing -------- response completed
                        |
                   drain begins
                   no new business work admitted
                                                         |
                                                  active count = 0
                                                  release dependencies

      A load balancer may still send a request while its routing information is updating. Decide how that request is handled before it has side effects. A temporary rejection can be appropriate, but clients and proxies must follow a safe retry policy. A broken connection or retryable response is not permission to repeat a non-idempotent operation blindly.

      Key takeaways

      • Drain requests already accepted while preventing an unbounded stream of new work.
      • Closing a listener alone does not handle keep-alive requests or HTTP/2 streams.
      • Define safe behavior for traffic that arrives during routing changes.

      Readiness, routing and deployments

      Shutdown is a coordination problem between the application, its supervisor and the traffic infrastructure. Readiness answers whether an instance should receive new traffic; liveness answers whether it needs recovery. Planned draining should withdraw readiness without pretending the process has crashed. See health checks and failure containment.

      Bring replacement capacity online before retiring old capacity. Then coordinate routing removal and the admission cutoff so stale routes do not cause unnecessary failures. If propagation needs a waiting window, measure it and count it within the shutdown budget. A fixed sleep by itself neither proves routing has updated nor proves work has finished.

      In the normal Kubernetes Pod termination flow, the grace period defaults to 30 seconds. A configured preStop hook consumes that same budget before the container's stop signal is sent. Terminating endpoints become unready for regular traffic, and processes still running after the grace period face forced termination. Routing and local shutdown proceed concurrently, so do not assume instantaneous traffic removal. See the Kubernetes termination flow.

      Also verify that signals reach the application in the deployed container. A shell wrapper may intercept or fail to forward them. Docker's exec-form ENTRYPOINT or CMD avoids an unnecessary shell parent; wrappers and init processes need deliberate forwarding behavior. See Docker's signal-handling guidance.

      Key takeaways

      • Coordinate readiness, routing removal and request draining with replacement capacity.
      • Include routing delays and lifecycle hooks in the platform's termination budget.
      • Verify signal delivery through the real container entrypoint or process manager.

      Choose one bounded shutdown budget

      The shutdown deadline balances completing legitimate work against deployments that cannot finish. Choose it using request and job durations, dependency timeouts and operational requirements. Thirty or sixty seconds may be a useful example, but neither is universally sufficient. Unbounded work needs a cancellation, checkpoint or handoff strategy.

      Example phaseIllustrative budgetPurpose
      Routing withdrawalFirst 3 secondsAllow the configured traffic path to stop selecting this instance.
      Drain and cancellationUp to second 23Finish work, then cancel remaining operations with time left to settle.
      Cleanup and telemetryUp to second 27Release resources and flush bounded diagnostic buffers.
      Platform marginRemaining 3 secondsLeave room before a hypothetical 30-second forced-stop deadline.

      These are planning numbers, not recommended defaults. All phases share one overall deadline; giving each of five sequential phases a fresh 30 seconds does not fit a 30-second platform limit. Sub-deadlines should reserve time for later phases and never extend the overall budget.

      Keep the signal notification separate from the context used to drain. If the signal cancels a context, passing that already-cancelled context into shutdown can cause it to return immediately. Create a fresh bounded shutdown context. Cancel active work when its drain allowance expires; cancellation is cooperative and cannot force arbitrary code to stop.

      Key takeaways

      • Use one overall deadline with time reserved for cleanup and a margin before forced termination.
      • Select budgets from measured workload behavior, not a universal 30-second rule.
      • Use a fresh shutdown context and define what happens when cooperative cancellation is insufficient.

      Database connections and transaction outcomes

      Closing your application's database pool releases its client connections. It does not shut down the shared database server or stop other applications from using it. Networked databases commonly use TCP connections, but local sockets and embedded databases are other possibilities. Shutdown behavior belongs to the actual client and driver you use.

      Let request and job owners finish their database operations before closing their pool. A transaction should commit only when its business operation is complete and valid; otherwise it should roll back. Shutdown is not a reason to commit every open transaction. A pool-close call is also not a substitute for explicit transaction ownership.

      Losing a client connection does not normally corrupt a transactional database. PostgreSQL rolls back a transaction still open when the session terminates. However, detecting a disconnect can take time, and a statement running in autocommit mode may finish and commit before the disconnect is noticed. See PostgreSQL's termination semantics.

      Unknown outcome is different from failure

      If a COMMIT succeeds but its reply is lost, the client may not know whether the operation completed. The same uncertainty occurs with external payment APIs. Use a stable operation identifier, check durable state and reconcile the result before deciding whether to retry. Atomic database transactions alone do not make an external charge and a local order update atomic.

      When a database update must reliably cause a later job, an outbox can record both the change and the intent to publish in one database transaction. Another worker publishes that intent after a restart if necessary. The consumer still needs duplicate-safe processing; see background job reliability.

      Key takeaways

      • Finish transaction owners before closing their client pool; do not shut down a shared database.
      • Disconnects can leave the client uncertain about a committed operation without corrupting the database.
      • Use durable operation state, idempotency and reconciliation across retries and restarts.

      Background workers and queued jobs

      A worker must stop claiming new jobs before it waits for active jobs to finish. Keep its broker, database and external-service clients available while those jobs need them. A task may need the database to save its result and the broker to acknowledge completion; closing either too early turns a planned shutdown into an avoidable failure.

      Job stateShutdown behavior
      Still waiting in a durable queueLeave it available for healthy workers; do not empty the shared queue.
      Running and able to finish in timeFinish, persist the result and acknowledge according to the queue's protocol.
      Running beyond the drain allowanceCancel cooperatively, checkpoint if supported and arrange safe redelivery.
      Completed but acknowledgement lostExpect possible redelivery and recognize work already completed.

      Acknowledging before successful processing risks losing work. A lease or visibility timeout may let another worker retry a job after the original worker disappears. Do not make a job available to another worker while the old handler can still mutate shared state unless your concurrency controls and idempotency make that safe.

      Stop local recurring schedulers too. For work that cannot fit into any practical shutdown window, design resumable chunks or a durable handoff. An in-memory “fire and forget” task has no automatic recovery just because the HTTP response was already sent.

      Key takeaways

      • Stop job intake, then drain active handlers while their dependencies remain available.
      • Acknowledge successful durable work and expect redelivery when completion is uncertain.
      • Long jobs need cancellation or resumability, and retries need idempotency.

      WebSockets, streams and long-lived work

      Some connections are designed to stay open for hours. Waiting for every WebSocket or streaming response to end naturally would make shutdown impractical. These protocols need a deliberate closing and reconnect strategy rather than the same expectations as a short HTTP request.

      • WebSockets: stop accepting new sessions, notify existing peers through the protocol's close procedure and bound the wait for completion.
      • Server-sent events: end the stream deliberately and let the client reconnect; retain replay information if the application promises resumable delivery.
      • Long downloads or uploads: choose whether to finish within a deadline or interrupt with a documented resume/retry mechanism.
      • Detached tasks: register their lifetime with the application so shutdown can wait, cancel or hand them off.

      A replacement instance needs access to the durable state required to resume a session. Closing a socket does not transfer subscriptions, unacknowledged messages or an upload's progress to another server. Clients should reconnect with backoff and jitter so a deployment does not make every client reconnect at precisely the same instant.

      Key takeaways

      • Long-lived connections need a bounded protocol-specific close procedure.
      • Reconnection and resumability require explicit client behavior and shared durable state.
      • Track detached work independently of ordinary HTTP request draining.

      Clean up in dependency order

      Resource cleanup includes closing files and clients, completing protocol handshakes, releasing owned leases, removing temporary files and flushing buffered output. During normal operation, forgotten file descriptors or sockets can exhaust process limits. At process exit the operating system reclaims memory and descriptors, but it cannot finish application-level business work or flush data that existed only in a user-space buffer.

      Dependencies must outlive their users
      HTTP handlers ----> database pool
       |                  ^
       v                  |
queue producer      background workers ----> broker client

Stop new requests and job claims
        ↓
Wait for handlers and workers to finish
        ↓
Close clients and pools they used
        ↓
Flush remaining telemetry, then exit

      Reverse initialization order is useful when initialization followed dependency order. The stronger rule is stop a resource's users before closing the resource. “Close HTTP, then database, then workers” is wrong when workers still need that database. Independent resources can be closed concurrently if their cleanup has no dependencies on one another.

      Clean up only resources this instance owns. Closing a Redis client does not mean clearing shared caches, deleting shared queue data or releasing another instance's lock. Keep diagnostic output available while cleanup runs. If one cleanup operation fails, record it and attempt independent remaining cleanup within the budget instead of silently abandoning everything.

      Key takeaways

      • Stop all users of a dependency before closing that dependency.
      • The OS reclaims process resources, but application cleanup still matters for buffers, protocols and durable work.
      • Release only owned resources and preserve diagnostics through cleanup.

      A practical framework walkthrough

      Framework helpers perform pieces of shutdown; your application coordinates them. The following is pseudocode, showing responsibilities rather than a runnable implementation for a particular framework. Every wait and cleanup operation must respect its assigned share of the remaining deadline.

      Conceptual lifecycle coordinator
      initialize configuration and dependencies
register stop notifications
start HTTP service, workers and schedulers
publish readiness

wait for stop notification or fatal startup/runtime failure
enter draining once; establish overall shutdown deadline
withdraw readiness and coordinate routing cutoff
stop new HTTP work, job claims and scheduler triggers
notify long-lived sessions that the instance is closing

wait for active work within its drain allowance
if work remains:
    request cancellation and wait a bounded time for it to settle
    record unfinished work and apply the documented forced-stop policy

after users of a resource have stopped:
    close that owned resource within the remaining cleanup budget
flush telemetry within its reserved allowance
exit with the recorded outcome

      In Go, signal.NotifyContext can notify the coordinator by cancelling a context when a registered signal arrives. Use a separate, fresh timeout context for shutdown. The returned stop function unregisters the signal behavior; deciding whether later interrupts force an exit is part of your signal policy.

      http.Server.Shutdown closes listeners and idle connections, then waits for active connections to become idle. Its context bounds that wait. An expired context returns an error; it does not itself force all remaining handlers to stop. WebSockets and other hijacked connections require separate handling. Also, ListenAndServe returns http.ErrServerClosed when shutdown begins, so the main function must wait for shutdown to finish instead of exiting then.

      sql.DB.Close prevents new queries through that handle and waits for queries already processing. It has no context parameter, so query deadlines and the surrounding shutdown policy still matter. Call it after HTTP handlers and workers no longer need the pool. Check the worker library's own drain, timeout and retry semantics rather than assuming its close method covers every resource.

      Key takeaways

      • Use framework helpers inside one application-level lifecycle coordinator.
      • In Go, wait for Shutdown to finish even after ListenAndServe returns ErrServerClosed.
      • Deadline expiry, WebSockets, worker lifetimes and dependency cleanup need explicit policies.

      Observe the shutdown itself

      Shutdown deserves the same logging and monitoring as normal request handling. Otherwise, a stuck deployment may reveal only that a process vanished. Record the stop reason, deployment or instance identifier, active request and job counts, stage durations and whether the deadline was exceeded.

      Illustrative lifecycle log sequence
      shutdown_started        reason=SIGTERM active_requests=4 active_jobs=1
work_intake_stopped      readiness=false
http_drain_completed    active_requests=0
worker_drain_completed  active_jobs=0
dependencies_closed
shutdown_completed      outcome=graceful duration_ms=1840

      If the deadline expires, record unfinished counts and the affected stage rather than reporting a graceful success. Compare shutdown duration and forced-termination frequency across deployments. Keep fields bounded in metrics, and keep credentials, payment details and request payloads out of logs. A telemetry exporter needs a timeout too; a broken logging service must not hang exit forever.

      Report success or failure through the application's documented exit-code policy. Avoid an immediate exit call before asynchronous cleanup and telemetry flushing complete. A final log line is useful evidence, but successful shutdown also needs confirmation that the process actually exited.

      Key takeaways

      • Log the stop reason, stage durations, remaining work and final outcome.
      • Distinguish graceful completion from timeout or forced termination.
      • Keep telemetry available through cleanup, then flush it within a bounded window.

      Verify shutdown under real work

      Pressing Ctrl+C on an idle local server proves little about its behavior during a deployment. Test with controlled traffic and an isolated environment using the same supervisor or container entrypoint as production. The useful assertion is what happens to accepted work and new traffic, not merely whether a “shutting down” message appears.

      ScenarioWhat to verify
      Stop during a slow but bounded requestThe accepted request completes; new traffic goes to healthy instances.
      A dependency hangsThe overall deadline holds, cancellation is attempted and the outcome is recorded honestly.
      Keep-alive, HTTP/2 or WebSocket trafficNew work stops correctly and long-lived connections follow their close policy.
      A worker still needs the databaseIts result and acknowledgement complete before shared clients close.
      Repeated stop signalsCleanup is not started twice and the shutdown budget does not restart.
      Startup fails after opening a poolOnly acquired resources are released; the instance never becomes ready.
      Commit or payment succeeds but response is lostA retry resolves the existing operation without duplicating its effect.
      Forced termination before cleanupDurable jobs and application state recover without relying on shutdown hooks.

      Revisit these checks when adding a worker, a new connection type or another resource owner. A shutdown sequence that was correct for one HTTP server may become incorrect after a background service starts using its database pool. Graceful shutdown remains reliable only when it follows the application's actual work and dependencies.

      Key takeaways

      • Test shutdown during active requests and jobs, through the real deployment entrypoint.
      • Exercise deadlines, repeated signals, partial startup and protocol-specific connections.
      • Verify abrupt-exit recovery and duplicate-safe retries as well as the graceful path.
