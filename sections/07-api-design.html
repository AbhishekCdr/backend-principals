      Lesson 07

      API Design

      An API is a contract that other people build on. Design its resources, routes, methods, payloads and responses before writing the implementation. Consistent choices let consumers spend less time guessing and more time building useful features.

      Design the contract before the implementation

      API design decides how a consumer asks for work and understands the result. The contract includes successful behavior, validation failures, permissions, defaults and retry behavior. It should be understandable without reading the server's source code.

      Start with user journeys, wireframes and product requirements. A project-management screen might need to list projects, create a task, archive an organization or clone a project. These interactions reveal the resources and operations your API needs. Public APIs, integrations and background jobs may have no screen, so include their use cases too.

      1. UnderstandIdentify users and their goals

        Read designs and discuss requirements. Establish who can perform each operation and what information they need.

      2. ModelIdentify resources and relationships

        Organizations contain projects; projects contain tasks. Define their identities, lifecycle and ownership alongside the storage model.

      3. SpecifyWrite requests and responses

        Choose methods, paths, schemas, defaults, status codes and error behavior. Walk through examples in an API client or an OpenAPI document.

      4. ReviewTry the contract as a consumer

        Check empty results, bad input, retries and missing permissions. Then implement and verify the behavior against that contract.

      Three different kinds of guidance

      HTTP defines protocol semantics, REST defines architectural constraints, and an API style guide defines choices such as plural nouns or camelCase. Keep these distinct. Consistency helps consumers, but it does not replace documented behavior.

      Key takeaways

      • Start with user needs and operations, then design concrete request/response contracts.
      • Describe failures, permissions and defaults alongside successful responses.
      • Distinguish HTTP requirements, REST constraints and team naming conventions.

      Where REST comes from

      Tim Berners-Lee proposed the Web at CERN in 1989 and developed its first browser/editor and server in 1990. The Web is a system built on the Internet, not the beginning of the Internet itself. Its early development brought together resource identifiers, HTTP and HTML. W3C's history of the Web.

      As the Web grew, shared interfaces, caching and intermediaries became essential to scaling it. Roy Fielding described REST, Representational State Transfer, in his 2000 dissertation. REST is an architectural style, not a specification that mandates JSON, plural route names or a particular framework.

      ConstraintMeaning
      Client–serverSeparate interface concerns from server responsibilities so the parts can evolve independently.
      StatelessEach request carries the information needed to understand it, without relying on stored conversational context from earlier requests.
      CacheableResponse semantics indicate whether reuse is allowed; appropriate caching reduces repeated work.
      Uniform interfaceUse resource identities, representations, self-descriptive messages and hypermedia controls.
      Layered systemClients can interact through proxies, gateways and caches without knowing every component behind them.
      Code on demandOptionally extend client behavior by transferring executable code, such as scripts.

      These constraints concern interactions across the system. REST's layered-system constraint is distinct from organizing application code into controllers, services and repositories. Fielding's REST chapter explains the rationale and tradeoffs.

      Stateless does not mean no database

      Servers still store resource state: users, projects and tasks. Stateless interactions avoid depending on a remembered conversation to interpret the next request. Request-local context from Lesson 06 is also compatible with this: it exists during the current request.

      Key takeaways

      • REST is an architectural style for scalable interactions, not simply “JSON over HTTP.”
      • Its constraints are client–server, statelessness, caching, a uniform interface, layers and optional code on demand.
      • Persisted resources and context for the current request are compatible with stateless interactions.

      Resources, representations and state

      A resource is a concept your API identifies, such as a project, a collection of tasks or the progress of a background operation. Its representation is the data transferred about it. The same project could be represented as JSON for an API consumer or HTML for a browser. Browsers can consume JSON too; the format is not determined solely by whether the caller is another server.

      Resource state includes attributes such as a task's title and completion status. Application state describes the client's progress through an interaction. In REST's uniform interface, links and available actions in representations guide those transitions (hypermedia as the engine of application state, or HATEOAS). Exchanging representations supports this interaction; it is more than copying database rows.

      A project-management example

      ResourceExample public fieldsRelationship
      Organizationid, name, status, descriptionContains projects.
      Projectid, organizationId, name, status, descriptionBelongs to an organization; contains tasks.
      Taskid, projectId, title, statusBelongs to a project.

      Finding nouns in requirements is a useful starting heuristic. A resource does not have to map one-to-one to a database table, however. A response may combine several tables or omit internal fields. Develop the API contract and persistence model together rather than exposing every database column automatically.

      Many practical APIs called REST APIs use resource-oriented HTTP and JSON while leaving hypermedia navigation out. This lesson focuses on designing those HTTP contracts clearly; route naming alone does not establish all of REST's architectural properties.

      Key takeaways

      • A resource is the identified concept; a representation is the data exchanged about it.
      • The uniform interface includes identification, representation-based manipulation, self-descriptive messages and hypermedia.
      • Model organizations, projects and tasks around consumer needs, not just database tables.

      URLs, naming and versioning

      An example API URL
      https://api.example.com/v1/organizations/org-5/projects?page=2&limit=20
      PartMeaning
      httpsThe scheme; use HTTPS for production traffic.
      api.example.comThe host within the authority. An authority can also include a port.
      /v1A chosen major API version prefix.
      /organizations/org-5/projectsA path identifying the projects collection within an organization.
      ?page=2&limit=20Query parameters selecting a portion of the collection.

      A fragment such as #details is interpreted by the client and is not sent in the HTTP request target. It cannot be used to select a backend operation. An API subdomain and a /v1 prefix are common choices, not requirements; an API can also live under /api on the main host.

      Choose a readable path convention

      • Use plural collection names consistently: /books and /books/book-42.
      • Use lowercase static path segments and hyphens between words, such as /project-templates.
      • Use a human-readable slug when appropriate: Harry Potter can become harry-potter.
      • Define slug uniqueness, changes and redirects. A title-derived slug is not automatically a stable identity.
      • Preserve opaque IDs exactly; do not lowercase arbitrary identifiers or tokens.

      Underscores are legal URI characters, and encoded spaces can occur in URLs. Hyphenated lowercase names are a readability convention. Paths can be case-sensitive, so consistency matters. URI character rules.

      Nesting can express relationships, but avoid paths that reproduce every level of the database. A stable /projects/project-9 can coexist with an organization's project collection. For breaking contract changes, plan a version and migration policy; not every new optional field needs a new version.

      Key takeaways

      • Use consistent plural collection paths, readable names and stable resource identifiers.
      • Fragments stay on the client; query parameters and paths reach the server.
      • Pluralization, lowercase paths and version prefixes are design choices, not REST mandates.
      • Keep nesting purposeful and plan how consumers migrate across breaking changes.

      Choose HTTP methods by their meaning

      The method and path together identify an operation. GET /organizations lists organizations, while POST /organizations can create one. They share a URL because they act on the same collection in different ways.

      MethodIntended operationExample
      GETRetrieve a representation without requesting a state change.Read a project or list tasks.
      POSTProcess submitted data according to the target's semantics.Create a project, clone one, or request an email.
      PUTCreate or replace the state at a known target URI.Replace a resource's client-writable representation.
      PATCHApply changes described by a patch document.Change a project's description.
      DELETERemove the target resource's association with its current functionality.Delete a task; physical data retention is an implementation concern.
      HEADRetrieve GET-like response metadata without response content.Check headers without downloading the representation.
      OPTIONSDiscover communication options for a target.Includes use in CORS preflight; it is not limited to CORS.

      PUT and PATCH are different contracts

      Use PUT for replacement semantics and PATCH for a defined partial modification. Replacing a public representation does not mean clients must supply server-owned fields such as createdAt, nor every physical database column. Define writable fields and what omission means. PATCH likewise needs an explicit patch format, not just the method name.

      The choice follows the operation, not whether the frontend is a single-page or multi-page application. Query parameters are useful for GET selections; headers and the path also carry request information. Avoid relying on GET request bodies, which have no generally defined semantics. HTTP method semantics.

      Key takeaways

      • Method + path expresses the operation; collection URLs can support both GET and POST.
      • PUT replaces target state; PATCH applies a specified change; POST supports creation and other processing.
      • Document writable fields and omission behavior rather than treating PUT and PATCH interchangeably.
      • HEAD retrieves metadata without content; OPTIONS describes communication options.

      Idempotency and safe retries

      An operation is idempotent when repeating the same request has the same intended effect on server state as performing it once. This describes the requested effect, not identical response bodies or status codes. Another client may change a collection between two GETs, and a repeated DELETE may report that the resource is already absent.

      MethodIdempotent by HTTP semantics?Reason / example
      GET, HEAD, OPTIONSYes; these are also safe methods.The client is not requesting a resource mutation.
      PUTYes.Replacing the same target with the same state converges on that state.
      DELETEYes.The intended result remains that the target is removed.
      PATCHNot guaranteed.Assigning a value can be idempotent; incrementing a counter or appending an item may not be.
      POSTNot guaranteed.Repeated creation or clone requests can create multiple resources.
      PATCH is not automatically idempotent

      “Set status to active” can have the same effect repeatedly. “Increase the estimate by one” changes the result on every call. The patch format and operation determine retry behavior; PATCH itself does not promise idempotency. PATCH specification.

      Logging a request does not make a safe read unsafe: safety concerns the effect requested by the client. Similarly, deleting a resource with a first response of 204 and a later response of 404 can still be idempotent. An API can instead document 204 for an already absent target.

      When the network fails after a write

      A lost response does not tell the client whether the operation succeeded. If an API supports idempotency keys for POST, retry with the same key and the same payload. The server must associate the key with the caller and operation, prevent concurrent duplicate execution, reject conflicting payloads and document how long the result is retained. A random header alone provides no such protection.

      For competing edits, conditional requests such as If-Match with an ETag can protect against overwriting a newer version. Idempotency and concurrency control solve different problems. See the HTTP lesson for method properties and conditional requests.

      Key takeaways

      • Idempotency concerns repeated intended effects, not identical responses.
      • GET, HEAD, OPTIONS, PUT and DELETE are idempotent; POST and PATCH are not guaranteed to be.
      • Retry creation and custom actions only according to the API's documented deduplication contract.
      • Use version conditions when you need to prevent lost updates from concurrent edits.

      Design the organization CRUD contract

      Use https://api.example.com/v1 as the example base URL. These routes cover creation, reading, partial updates and deletion. Braces denote path parameters to replace with real identifiers, not literal text to send.

      OperationMethod and pathExample success contract
      CreatePOST /organizations201 with the created representation and its Location.
      ListGET /organizations200 with a paginated collection.
      Read oneGET /organizations/{organizationId}200 with one organization.
      UpdatePATCH /organizations/{organizationId}200 with the updated representation.
      DeleteDELETE /organizations/{organizationId}204 with no response body.

      Create only from writable fields

      Request — server defaults status to active
      POST /v1/organizations
Content-Type: application/json

{
  "name": "Organization 1",
  "description": "Our engineering workspace"
}
      Response — created resource and its address
      HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": "org-1",
  "name": "Organization 1",
  "status": "active",
  "description": "Our engineering workspace",
  "createdAt": "2026-10-02T09:00:00Z",
  "updatedAt": "2026-10-02T09:00:00Z"
}

      In this contract, IDs and timestamps are generated by the server or database. The public response includes those fields without exposing internal columns. Other APIs may allow client-assigned IDs, but that is a separate, explicit design choice.

      Define how partial updates work

      Request — update a description with JSON Merge Patch
      PATCH /v1/organizations/org-1
Content-Type: application/merge-patch+json

{
  "description": "Updated workspace description"
}

      With JSON Merge Patch, omitted members remain unchanged and a null value removes a member. Arrays are replaced as a whole. Apply the schema and business rules to the resulting state: deleting a required name or changing a read-only ID should fail. Return the updated public representation with 200, or document 204 if the operation returns no content. JSON Merge Patch specification.

      Read and delete use the same resource address

      A GET for an existing org-1 returns its representation. In this example, a completed DELETE returns 204, and a subsequent GET returns 404. Define deletion's effects on related projects and tasks, including any retention or recovery rules. A 204 response still has a status and headers; its body is empty.

      Key takeaways

      • Collection routes support list/create; item routes support read/update/delete.
      • For creation, return the intended public resource and identify its address with Location.
      • Define the patch media type, missing-field behavior, null behavior and writable fields.
      • Document deletion's effect on related data as well as its HTTP response.

      Pagination: return a bounded portion

      A list endpoint should not grow into an unbounded download as the database grows. Pagination limits database work, serialization, network transfer and client rendering per response. A user viewing twenty items rarely needs every record on the first screen.

      For this example, use page=1 and limit=20 when omitted, with a maximum limit of 100. Accept positive integers and reject invalid values. Query values arrive as text, so parse and validate them deliberately. These numbers are this API's policy, not REST rules.

      Request — two organizations from the first page
      GET /v1/organizations?page=1&limit=2
      Response — abbreviated list representations
      {
  "data": [
    { "id": "org-5", "name": "Organization 5", "status": "active" },
    { "id": "org-4", "name": "Organization 4", "status": "active" }
  ],
  "total": 5,
  "page": 1,
  "limit": 2,
  "totalPages": 3
}

      Suppose five organizations are ordered newest first. With a limit of two, the pages are:

      PageReturned organizationsMetadata
      1Organization 5, Organization 4.total: 5, totalPages: 3.
      2Organization 3, Organization 2.The same total and page count.
      3Organization 1.The last page can contain fewer than the limit.

      Offset pagination uses offset = (page − 1) × limit, with totalPages = ceil(total / limit). Here, total counts records matching the current filters that the caller is allowed to see, not every record in a multi-tenant database. In this contract, an out-of-range page returns 200 with an empty data array.

      Know when page numbers are not enough

      Inserts and deletes between calls can shift offsets, causing duplicates or skipped items. Large offsets and exact counts can also be expensive. Cursor pagination instead returns an opaque continuation token, often with hasMore or a next link. It works well for feeds and large collections, but still needs stable ordering and defined behavior when data changes. Exact totals are optional if the interface does not need them.

      Key takeaways

      • Bound list responses; document defaults, valid ranges and maximum page size.
      • With five records and a limit of two, page sizes are two, two and one.
      • Totals must match filters and the caller's authorized scope.
      • Use cursor pagination when large offsets or shifting collections make page numbers unsuitable.

      Sorting, filtering and empty lists

      Make list behavior predictable even when optional query parameters are absent. For this API, default to createdAt descending, then id descending as a unique tie-breaker. A database query without an explicit order does not promise a stable sequence; ordering by a non-unique timestamp alone is also insufficient for deterministic pagination.

      ParameterExampleContract
      sortBynameAllowlisted fields: name or createdAt; default createdAt.
      sortOrderascasc or desc; default desc. Retain a documented ID tie-breaker.
      statusarchivedExact match against an allowed status; omitted means no status filter.
      nameOrganization 4Exact name match in this example; document case sensitivity.
      Combine filters and ordering
      GET /v1/organizations?status=active&name=Organization%204&sortBy=name&sortOrder=asc

      State whether filters combine with AND or OR; this example uses AND. Apply authorization and filters before counting and paginating the results. Map allowed sort fields to known database expressions and bind filter values safely. Do not insert arbitrary query text into SQL, even when it is called a sort parameter.

      Empty is a valid result; invalid input is a different result

      200 OK — valid filter with no matching organizations
      {
  "data": [],
  "total": 0,
  "page": 1,
  "limit": 20,
  "totalPages": 0
}

      A valid collection with no matches returns an empty collection, not a missing-resource error. But status=banana violates this API's status enum and should receive a validation error. A missing /organizations/org-missing can return 404; so can a nested collection whose required parent does not exist. “List endpoints never return 404” is too broad.

      Key takeaways

      • Specify a default sort and a unique tie-breaker; allowlist client-selectable sort fields.
      • Document filter matching and combination rules, then count and paginate the matching authorized records.
      • Valid filters with no matches return 200 and an empty collection.
      • Invalid filter values produce validation errors; missing resources or parents can produce 404.

      Custom actions: archive, clone and send

      Some operations are more naturally expressed as commands than basic field edits. POST supports processing with application-specific semantics. A readable action endpoint can make that intent explicit; the suffix is a chosen API convention, not prescribed REST syntax.

      OperationExample routePossible success response
      Archive an organization.POST /organizations/{organizationId}/archive200 with the archived organization, or 204 without content.
      Clone a project.POST /projects/{projectId}/clone201 with the new project and its Location.
      Request an email delivery.POST /email-deliveries201 for a created delivery resource, or 202 for accepted asynchronous processing.

      Archive is a domain operation

      Archiving may affect related projects, tasks and notifications. Define those effects and the permissions required. A dedicated archive endpoint can expose that workflow clearly. A PATCH changing status can also be valid if its documented semantics include the same workflow. Internal complexity alone does not determine the HTTP method.

      Whichever contract you choose, prevent a generic status update from bypassing archive rules. Do not automatically delete related data unless the product's archive behavior calls for it. Document what happens if the organization is already archived and whether retries can duplicate notifications.

      Clone creates a new identity

      Request — optional documented overrides
      POST /v1/projects/project-2/clone
Content-Type: application/json

{
  "name": "Project 2 copy"
}

      Specify whether tasks, membership and other related data are copied, and whether the operation is atomic. On synchronous creation, return 201 and identify the new project. The new ID must distinguish the clone from its source. A missing source can return 404; a forbidden clone must not proceed merely because the caller knows the source ID.

      For long-running actions, 202 means accepted, not completed. Give the consumer a way to observe progress, such as an operation resource. For actions that create records or send messages, explicitly document retry and deduplication behavior.

      Key takeaways

      • POST can express custom processing; action paths are a documented convention.
      • Archive can be an action or a state transition; enforce its business rules on every supported path.
      • A synchronous clone creates a resource, so 201 can be appropriate even for a custom action.
      • 202 means work was accepted; document completion tracking, side effects and retry behavior.

      Apply the same contract to projects and tasks

      Consumers should be able to recognize the organization patterns when they encounter another resource. Use the same collection/item distinction, pagination vocabulary and response conventions. Add only the differences required by the resource's behavior.

      OperationProjectsTasks
      CreatePOST /projectsPOST /tasks
      ListGET /projectsGET /tasks
      Read oneGET /projects/{projectId}GET /tasks/{taskId}
      UpdatePATCH /projects/{projectId}PATCH /tasks/{taskId}
      DeleteDELETE /projects/{projectId}DELETE /tasks/{taskId}
      Create a project within an existing organization
      POST /v1/projects
Content-Type: application/json

{
  "name": "Project 1",
  "organizationId": "org-1",
  "description": "Improve onboarding"
}

      This contract defaults the project status to planned. Validate that org-1 exists and that the authenticated caller can create projects there. A foreign key checks a relationship's existence; it does not establish the caller's permission.

      List projects within an organization using a documented filter such as GET /projects?organizationId=org-1, or a nested collection such as GET /organizations/org-1/projects. You do not need both unless consumers need both. If the parent ID is in the path, avoid requiring the same value in the body without defining how conflicting values are handled.

      A task's create input similarly includes projectId, its title and any other required fields. Check access to that parent, then use the same conventions for creation, listing, partial updates and deletion. Do not add every CRUD endpoint automatically if the product does not permit that operation.

      Key takeaways

      • Reuse method, route, pagination and response patterns across resources.
      • Validate parent IDs and the caller's authorization; knowing an ID is not permission.
      • Use nesting or parent filters deliberately and avoid ambiguous duplicate parent identifiers.
      • Expose operations required by the product, not every possible table mutation.

      Consistent payloads and sensible defaults

      Use the same name for the same concept: description should not become desc in the next endpoint. This example uses camelCase for JSON fields and query parameter names. JSON itself only requires object member names to be strings; it does not mandate camelCase. Choose a convention and apply it consistently. JSON object syntax.

      InputExample defaultWhen the client supplies a value
      page1.Require a positive integer.
      limit20.Require an integer from 1 to 100.
      sortBycreatedAt.Validate against that endpoint's allowed sort fields.
      sortOrderdesc.Accept only asc or desc.
      Organization status on creation.active.Allow an override only if the contract and business rules permit it.
      Project status on creation.planned.Apply its documented lifecycle rules.

      Defaults should make ordinary requests convenient without hiding invalid input. Apply a default when a field is absent according to the schema; do not silently replace an invalid value with something else. Also distinguish omitted, null and empty-string values.

      Only require information the operation needs. If an organization needs only a name, make optional description and default status behavior explicit. Never infer permissions or ownership from a convenience default. Accept allowed fields deliberately and choose whether unknown or read-only input fields are rejected or ignored; avoid automatic unrestricted binding.

      Key takeaways

      • Keep names, casing and envelopes consistent; camelCase is a convention, not a JSON requirement.
      • Document defaults and bounds, and reject invalid supplied values.
      • Distinguish omission, null and empty values in create and update schemas.
      • Require necessary input and explicitly control which fields clients can write.

      Status codes and useful error responses

      Choose the status from the operation's outcome, not from the HTTP method alone. POST can return 200 for completed processing, 201 for creation or 202 for accepted work. A DELETE can return 200 with a result or 204 without one; asynchronous deletion can return 202.

      StatusTypical use
      200 OKA successful read, list, update or action returning content.
      201 CreatedA resource was created; identify it, commonly with Location.
      202 AcceptedThe request was accepted for processing that has not completed.
      204 No ContentThe operation succeeded and there is no response content.
      400 Bad RequestMalformed input or invalid parameters under the API's validation policy.
      401 UnauthorizedValid authentication credentials are required; include an appropriate WWW-Authenticate challenge.
      403 ForbiddenThe caller is not permitted to perform the operation.
      404 Not FoundThe target is missing, or the API intentionally conceals its existence.
      409 ConflictThe operation conflicts with current resource state, such as a uniqueness rule.
      412 Precondition FailedA supplied condition such as If-Match did not hold.
      422 Unprocessable ContentA possible policy for well-formed content whose instructions cannot be processed.
      429 Too Many RequestsA rate limit was exceeded.
      500 Internal Server ErrorAn unexpected server failure; return a safe public message.

      This lesson's example uses 400 for validation failures. APIs that distinguish semantic body errors with 422 should document that policy consistently. Do not return 200 for every error and expect consumers to infer failure from an arbitrary message string.

      Give clients a stable error shape

      Problem Details is a standard error representation. Its common fields describe the problem type, title, status and occurrence-specific detail; an API can add structured field errors and a request ID. Consumers should use documented machine-readable identifiers, not parse human prose. Problem Details for HTTP APIs.

      Example — reject an invalid status filter
      HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "One or more query parameters are invalid.",
  "errors": [
    {
      "field": "status",
      "code": "INVALID_STATUS",
      "message": "status must be active or archived"
    }
  ],
  "requestId": "req-7f21"
}

      Here, errors and requestId are API-specific extensions. Keep response status and body status aligned. Log internal diagnostics with the request ID, while excluding stack traces, SQL details, credentials and other sensitive information from public responses.

      Key takeaways

      • Return status codes according to outcomes: completion, creation, acceptance or failure.
      • 204 has no response body; 202 does not assert that the work has completed.
      • Use a consistent validation policy and stable machine-readable error information.
      • Problem Details provides a standard shape; keep sensitive diagnostics in server logs.

      Document, review and evolve the contract

      An OpenAPI description makes the HTTP contract readable by people and tools. It can describe paths, methods, parameters, schemas, security requirements and responses independently of the server's programming language. Tools such as Swagger UI can present an interactive interface over that description. OpenAPI specification.

      Insomnia or Postman collections are useful for trying concrete requests. Keep them consistent with the documented contract, and keep both in step with the implementation. Examples should include empty lists, validation failures, authentication failures, conflicts and asynchronous outcomes as well as the successful path. An interactive page alone does not prove correctness.

      Review the API as its next consumer

      • Resources: are the identities and relationships clear without knowing the database schema?
      • Operations: do method semantics match the requested effect, and are custom actions documented?
      • Inputs: are writable fields, required values, defaults, null behavior and validation rules explicit?
      • Collections: are pagination limits, deterministic ordering, filters, totals and empty results defined?
      • Security: does every item, list and action respect the authenticated caller's scope?
      • Outcomes: are response fields, status codes, errors and completion tracking predictable?
      • Retries: can callers tell which operations are idempotent and how duplicate writes are prevented?
      • Change: do consumers have an upgrade path for breaking changes, with updated documentation?

      Keep the vocabulary consistent as resources are added. A consumer who has integrated the organization endpoints should recognize the project and task patterns. Reserve implementation choices for the server while making everything a consumer must rely on part of the contract.

      Key takeaways

      • Design concrete requests and responses before implementing handlers and business logic.
      • Maintain OpenAPI documentation and useful examples together with the code.
      • Review security, failures, retries and compatibility as part of API usability.
      • A good contract lets consumers predict behavior across resources with minimal guesswork.
