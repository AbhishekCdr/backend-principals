      Lesson 19

      Concurrency & Parallelism

      Follow a request through CPU execution, I/O waits and scheduling. Understand which work can overlap, which work can run in parallel and which shared state needs protection.

      What happens while a request waits?

      A handler parses a request, sends a database query and waits for its result. While that result is unavailable, this request may have no useful application computation to perform. A concurrent server can let other requests make progress during that interval instead of requiring every request to finish before the next begins.

      Illustrative serial request budget, not a universal backend profile
      Five non-overlapping I/O waits × 50 ms = 250 ms waiting
Application CPU execution              =  10 ms
Total elapsed time                    = 260 ms

Waiting fraction = 250 / 260 ≈ 96.2%
Application CPU fraction = 10 / 260 ≈ 3.8%

      Those percentages describe one example request's elapsed time. They do not prove that the whole machine is idle or that memory is unused: other processes, the kernel and the database can be working, and the waiting request still retains state and buffers. Real request costs depend on the workload and must be measured.

      CPU frequency is also not an instruction-throughput guarantee. A 3 GHz clock counts cycles; instructions per cycle vary with hardware and code. The important observation is the opportunity to overlap useful work with waiting, rather than a fixed number of “wasted instructions.”

      Concurrency can improve resource use and completed throughput, but it does not make a remote dependency answer sooner. Additional work can also create contention. Connect these concepts to latency, throughput and capacity.

      Key takeaways

      • Another request can make progress while one request awaits an external result.
      • Waiting can free execution capacity while memory and other resources remain occupied.
      • Measure the actual workload; one request's timing is not the machine's utilization.

      Concurrency and parallelism describe different things

      Concurrency means multiple activities have overlapping lifetimes and can make progress without each finishing first. Parallelism means some work actually executes simultaneously on available execution resources. A program can be concurrent on one execution lane and can use several lanes for parallel work.

      In a simplified single-lane timeline, only one request uses that lane at a time, while network operations may progress elsewhere. Suppose A and B arrive together, A needs 5 ms of initial CPU work and B needs 10 ms:

      RequestInitial CPUI/O waitFinal CPUCompletion
      A0–5 ms5–45 ms45–50 ms50 ms
      B5–15 ms15–50 ms50–55 ms55 ms

      The CPU intervals do not overlap, but both requests are in progress together. With two suitable execution lanes, their initial computation could also overlap. A task whose I/O becomes ready may still wait for scheduling before its next computation runs.

      This is an application-level model, not a claim that a physical core executes exactly one instruction at a time. Modern CPUs have features such as instruction-level parallelism, vector execution and simultaneous multithreading. For backend design, distinguish overlapping task lifetimes from the execution resources available to run their computation.

      Key takeaways

      • Concurrent tasks overlap in lifetime; parallel work executes simultaneously.
      • I/O overlap can help even when application computation uses one execution lane.
      • Being ready to run does not guarantee immediate CPU access.

      CPU-bound and I/O-bound work

      A workload is CPU-bound when available computation substantially limits its progress, and I/O-bound when waiting on input/output substantially limits it. These describe bottlenecks under particular conditions, not permanent categories attached to an entire application.

      WorkTypical componentUseful direction to investigate
      Waiting for a database or HTTP serviceNetwork, dependency and possibly pool waitingOverlap independent work and inspect downstream latency and capacity.
      Reading or writing filesStorage work plus copying and processingUse suitable I/O APIs and measure storage and execution separately.
      JSON parsing, validation or compressionApplication computationBound input size, profile costs and reduce or offload expensive work.
      Encoding media or verifying cryptographic signaturesComputation, potentially with other bottlenecksConsider optimized implementations and bounded parallel capacity.

      JWT signature verification concerns integrity and authenticity; it is not necessarily decryption. Ordinary APIs can also become CPU-bound because of large JSON payloads, expensive regular expressions, password hashing or excessive allocation. Do not assume CPU work always takes under two milliseconds or that every backend bottleneck is I/O.

      Parallel computation helps when the task can be divided and enough execution capacity exists. More threads do not guarantee improvement: scheduling, synchronization, memory bandwidth and serial dependencies can dominate. Concurrency helps organize both I/O and CPU tasks, while parallelism is one way to execute some of that work faster.

      Key takeaways

      • Classify the measured bottleneck, not the programming language or application category.
      • I/O operations include CPU work around the wait, and ordinary APIs can become CPU-bound.
      • Use overlap for waiting and evaluate parallel capacity for computation without assuming linear speedup.

      Processes, threads and memory

      A process gives a running program an execution and resource context. Separate processes normally have separate virtual address spaces; communication requires an explicit mechanism such as messages, sockets or deliberately shared memory. Multiple native threads within a process normally share its address space and resources.

      Each native thread has its own execution state, including registers and a stack used for call-related state. The process heap and globals can be accessible across threads, although language runtimes may impose additional isolation or access rules. A local variable is not guaranteed to physically occupy a stack slot: compilers can use registers, eliminate it or arrange other storage.

      Shared address space does not imply safe shared updates
      Process A
  Thread 1: execution state + stack ─┐
                                    ├─ shared process resources and heap
  Thread 2: execution state + stack ─┘

Process B: separate address space unless sharing is explicitly arranged

      Sharing an object reference can avoid serialization, but it creates coordination and lifetime obligations. A pointer does not establish ownership, thread safety or valid access. Some runtimes also isolate ordinary objects across execution contexts even when those contexts live in one process. See the POSIX-thread overview ↗.

      Key takeaways

      • Separate processes normally isolate address spaces; native threads share process resources.
      • Each thread retains its own execution state and call stack.
      • Shared memory enables communication but requires explicit coordination and valid ownership.

      Scheduling, blocking and waking up

      The operating system schedules runnable native threads onto available logical processors. It can preempt execution so other work gets a turn. The policy is more complex than a fixed two-millisecond rotation and depends on platform, priorities and operating conditions.

      Conceptual stateMeaningPossible next event
      RunningCurrently executing.Finish, be preempted or wait for something.
      RunnableAble to make progress when scheduled.Receive execution time.
      Waiting / blockedCannot yet continue because a required event or resource is unavailable.Be made runnable when the condition changes.

      In a blocking thread-based database client, waiting for more socket data can park the calling thread. Other runnable threads can execute while it waits. If no runnable work exists, the processor can idle; a well-behaved wait need not repeatedly consume CPU checking the socket.

      Arrival of network data can make waiting work eligible again, but not necessarily run it immediately. Receiving bytes also does not mean a complete database result has arrived: the driver may need further reads, protocol parsing and error handling. Scheduling and the application's I/O protocol are distinct layers.

      For deeper operating-system foundations, see Operating Systems: Three Easy Pieces ↗. Runtime tasks can have an additional scheduler above the OS, which is why a waiting coroutine or goroutine is not always a blocked native thread.

      Key takeaways

      • The OS schedules runnable native threads and can preempt running ones.
      • A blocking wait can park one thread while others execute, without busy-waiting.
      • Readiness, complete protocol results and actual resumption are different events.

      Thread costs and bounded thread pools

      Native threads have creation, memory and scheduling costs. Their stacks may reserve virtual address space whose resident physical use grows as pages are touched. Stack sizes vary by platform and configuration, so neither an eight-megabyte stack nor a fixed committed-memory cost applies universally.

      A context switch saves and restores execution state and performs scheduling bookkeeping. Its cost includes hardware and cache effects and is not one fixed microsecond value. Thousands of sleeping threads are also different from thousands of runnable threads competing for a few processors. Measure runnable queues, memory and switching activity.

      Illustrative memory arithmetic with an explicit assumption
      If 10,000 active workers each retain 1 MiB of actual memory:
  10,000 × 1 MiB = 10,000 MiB ≈ 9.77 GiB

That assumption is not a universal native-thread footprint.
Requests, buffers, libraries and application data add other costs.

      A thread-based server can use a bounded pool instead of creating a fresh native thread for every request. Blocking handlers can then express sequential logic while the OS schedules other workers. The pool still needs limits, queueing policy, acquisition deadlines and protection against slow operations occupying every worker.

      Thread-per-request and pooled blocking designs exist and can be appropriate. Event-driven or lightweight-task designs often reduce per-waiting-task overhead at high concurrency, but the best model depends on libraries, resource limits and workload. A concurrency mechanism should be evaluated with the same capacity measurements as any other component.

      Key takeaways

      • Native threads have variable memory and scheduling costs; reserved and resident memory differ.
      • Bounded thread pools reuse workers and constrain resource demand.
      • Compare complete workloads rather than assuming every thread-based design is inefficient.

      Event loops and operating-system I/O

      Event loops are not specific to JavaScript. Node.js uses one to coordinate JavaScript callbacks, and Python's asyncio uses one to coordinate coroutine tasks. A language can support several concurrency models; the server, runtime and libraries determine which model your backend actually uses.

      An event loop coordinates ready callbacks or tasks, timers and I/O notifications. A handler initiates an operation and arranges how execution should continue when it can make progress. The loop can handle other ready work while that operation is pending.

      A loop does not need to scan every connection continuously. Operating systems provide efficient notification mechanisms: epoll on Linux, kqueue on BSD-derived systems including macOS, and completion-based mechanisms such as IOCP on Windows. A loop can sleep while awaiting events instead of burning a core in a busy polling loop. See libuv's design overview ↗.

      A conceptual iteration, not an exact runtime implementation
      Run eligible callbacks or task continuations.
Determine whether timers or registered I/O can make progress.
Wait for notifications when there is no ready work.
Queue or dispatch the resulting work according to runtime rules.
Repeat while the runtime has work to manage.

      Readiness and completion are different APIs. A readable socket may offer only part of a message; an attempted operation may still need to handle errors or try again. The driver owns protocol state and decides when the application has a complete result.

      There are still costs: task records, buffers, callback dispatch, runtime bookkeeping and ordinary OS scheduling. A single loop thread can itself be preempted by the OS. Event loops do not eliminate all context switches, and a system can run several event loops on different threads or processes. The relevant advantage is how waiting work is represented and resumed.

      Key takeaways

      • Event loops resume ready work using I/O notifications and runtime queues.
      • Efficient pollers can sleep; they do not require constant connection-by-connection scanning.
      • The model still uses memory, runtime work and OS scheduling.

      Python: threads, processes and asyncio

      Python supports both native threads and event-loop concurrency. It does not have one mandatory backend architecture. A synchronous application can run in worker processes or a thread pool; an asynchronous application can run coroutine tasks on an event loop. A deployment can combine these approaches.

      ModelHow requests progressWhat a database wait does
      Synchronous worker processesSeparate processes handle work independently. A basic synchronous worker handles one request at a time.A blocking driver occupies that worker until it can continue; other worker processes can serve requests.
      Native thread poolSeveral OS threads handle work within a process and share its memory.A blocking socket wait can park the calling thread while another thread runs.
      asyncio event loopTasks share a loop thread and yield cooperatively when an awaited operation needs to suspend.An async-compatible driver lets the task suspend while other ready tasks run on the loop.

      Python's threading module provides native-thread concurrency. In a GIL-enabled CPython process, only one thread executes Python bytecode at a time, but many blocking I/O operations release the GIL, so threads can overlap I/O waits. CPU-heavy pure Python work commonly uses separate processes for parallel execution. Native extensions that release the GIL and free-threaded CPython builds have different parallelism behavior. See Python's thread and GIL documentation ↗.

      With asyncio, a loop normally executes one task at a time on its thread. Calling async def creates a coroutine object; awaiting or scheduling it enables execution. Unlike JavaScript, awaiting a Python coroutine does not necessarily yield to other tasks if it can complete without suspending. A blocking database driver or time.sleep() called directly on the loop thread still blocks it. Use compatible async APIs or an appropriate bounded executor for blocking operations. Async syntax alone does not supply CPU parallelism. See the asyncio overview ↗.

      WSGI and ASGI describe the server/application interface

      WSGI exposes a synchronous application interface. Its server configuration determines whether concurrency comes from processes, threads or another supported worker model; WSGI does not mean “one thread per request.” ASGI exposes an asynchronous, event-based interface suitable for async HTTP handling and WebSockets. ASGI servers commonly use an event loop, and synchronous application code can be adapted through threads. Neither interface fixes the total worker or thread count. See the ASGI introduction and WSGI comparison ↗.

      Django illustrates why deployment matters: it supports both interfaces. Its async views under WSGI use a one-off event loop, while an appropriately configured ASGI stack supports asynchronous request handling across the stack. Synchronous middleware can require thread adaptation. Check the framework, server worker configuration, middleware and database driver together before describing a Python backend as threaded or event-driven. See Django's async deployment explanation ↗.

      Key takeaways

      • Python supports threads, processes and event-loop tasks; the deployment selects their combination.
      • Threads can overlap I/O even with the GIL; pure Python CPU parallelism needs suitable execution resources and runtime support.
      • WSGI is a synchronous interface and ASGI an asynchronous interface; neither alone specifies the complete worker architecture.
      • asyncio needs nonblocking libraries or appropriate offloading, and an await does not always suspend.

      Node.js: keep the event loop responsive

      JavaScript callbacks ordinarily execute one at a time within a Node.js event-loop context. Node itself also uses other threads and native mechanisms. Typical asynchronous network I/O uses OS facilities, while selected filesystem, DNS and native operations can use libuv's worker pool. The database performs its own work outside the Node process too.

      A long synchronous callback keeps other JavaScript callbacks in that context from running. That can delay unrelated requests, timers, response processing and cancellation handlers. Large JSON parsing, pathological regular expressions or expensive computations can create this problem even in an ordinary API. See Node's event-loop and worker-pool guidance ↗.

      Declaring a function async or wrapping a calculation in a Promise does not move the calculation to another core. The synchronous part still runs where it is called. Similarly, await computeSynchronously() first evaluates that call; it does not offload its work.

      Reduce unnecessary work, bound inputs, use suitable asynchronous APIs, or move substantial CPU work to a bounded worker pool or separate process. Node's worker_threads ↗ can run JavaScript in parallel, but dispatch, transfer and synchronization have costs. Ordinary objects are not automatically shared across worker isolates; explicit sharing or transfer APIs have their own rules.

      Breaking work into small scheduled chunks may improve responsiveness without making it parallel. Repeatedly awaiting already-resolved Promises is not a guarantee that pending I/O or timers get a turn, because microtask processing can dominate the loop.

      Key takeaways

      • One JavaScript event-loop context runs callbacks serially, while Node uses additional native machinery.
      • Async syntax does not offload synchronous computation or make it nonblocking.
      • Bound callback work and use appropriate, bounded parallel workers for substantial CPU tasks.

      What JavaScript await actually suspends

      Calling a JavaScript async function returns a Promise. Its body begins executing synchronously until it suspends at await or completes. Await waits for an awaitable value within that function; it does not block the whole thread while the value is pending. The continuation resumes through Promise job scheduling, normally described as microtasks.

      JavaScript module example: synchronous prefix, then continuation
      const events = [];

async function task() {
  events.push("before await");
  await Promise.resolve();
  events.push("after await");
}

const done = task();
events.push("caller continues");
await done;

// events: ["before await", "caller continues", "after await"]

      Even an already-fulfilled Promise schedules the code after await for a later continuation. That does not promise which unrelated timer or network callback will run next. If the awaited Promise rejects, the await expression throws within the async function, so ordinary try/catch can handle it; unhandled failure rejects the function's returned Promise.

      Await is supported inside async functions and at the top level of JavaScript modules. It is not generally valid at the top level of a classic script. It also does not automatically return the HTTP response: the surrounding handler must still send or return the result. See await semantics ↗ and async functions ↗.

      Key takeaways

      • JavaScript runs an async function's synchronous prefix before its first suspension.
      • Await suspends the function's continuation, with Promise-based success and failure handling.
      • Top-level await belongs to modules, and suspension does not automatically send a response.

      Think of suspension as saved execution state

      A state machine is a useful model for an async function with several waits. The system must retain enough information to know what comes next and which local values survive suspension. That may be represented through compiler-generated state, Promise continuations, runtime objects or a combination. It is not a requirement that every language literally rewrites the function into the same switch statement.

      Conceptual progression for two dependent operations
      State 0: start fetching the user
         suspend until a result or error is available
State 1: keep the user; start fetching their dependent data
         suspend until a result or error is available
State 2: combine the values and complete

At each suspension: retain required locals and continuation state.
At failure: follow the function's error path, not necessarily the next success state.

      The saved state consumes memory even while no CPU executes the function. Native threads preserve execution using thread state and stacks; stackful runtime tasks also retain stacks; stackless async designs retain the state needed across suspension points. These are different representations of a suspended computation, not “memory versus no memory.”

      A task can resume only when it is eligible and the scheduler gives it execution time. A loop blocked by a long callback cannot run its other continuations meanwhile. Returning from a callback, suspending a coroutine, finishing a function and completing an HTTP response are separate events that should not be confused.

      Key takeaways

      • Suspension retains the values and continuation needed to resume later.
      • A state machine is a mental model; exact implementation varies by compiler and runtime.
      • Saved computations still consume memory and need scheduled execution to progress.

      Sequential awaits versus overlapping operations

      An async function can still issue operations sequentially. If it awaits a user lookup before starting an order lookup, those operations do not overlap within that function. Other requests can progress meanwhile, but that is a different source of concurrency.

      Sequential operations through an illustrative Promise-based database API
      async function loadSequential(db, userId) {
  const user = await db.getUser(userId);
  const orders = await db.getOrders(userId);
  return { user, orders };
}

      If both reads are independent and already authorized, they can be started before waiting for both results. Here the calls start the operations; Promise.all combines their completion.

      Overlap two independent operations
      async function loadConcurrent(db, userId) {
  const [user, orders] = await Promise.all([
    db.getUser(userId),
    db.getOrders(userId)
  ]);
  return { user, orders };
}

      In an idealized model, waits of 40 ms and 60 ms contribute about 100 ms sequentially versus about 60 ms when they overlap. Actual behavior depends on connection availability, server capacity and consistency requirements. A single database connection or transaction may serialize operations, and dependent or ordered operations cannot simply be overlapped.

      Promise.all does not provide CPU parallelism or a concurrency limit. If one input rejects, the combined Promise rejects without automatically cancelling the other operations. Define error and cancellation behavior and avoid starting thousands of calls merely because an array makes it convenient. See Promise.all semantics ↗.

      Key takeaways

      • Two sequential awaits do not automatically overlap their underlying operations.
      • Start independent, authorized work together only when downstream capacity and consistency permit it.
      • Promise.all coordinates results; it neither limits concurrency nor automatically cancels sibling operations.

      Similar syntax, different runtime contracts

      Async/await is not one universal execution model. Learn when a call begins work, how it is scheduled, what can suspend it and where its computation runs. Surface syntax alone cannot answer those questions.

      EnvironmentImportant distinctionPrimary reference
      JavaScriptAn async call runs its synchronous prefix immediately and returns a Promise.Async functions ↗
      Python asyncioCalling async def normally creates a coroutine object; it must be awaited or appropriately scheduled to execute.Coroutines and tasks ↗
      Rust asyncA future makes progress when polled; wakeups inform an executor that further progress may be possible.Futures and wakeups ↗
      GoThe go statement starts a goroutine, and ordinary-looking blocking calls interact with the runtime and OS mechanisms.Goroutines ↗
      Java virtual threadsThe runtime schedules lightweight virtual threads over underlying platform threads.Virtual threads ↗

      A synchronous database driver called directly inside an async handler can still block its event-loop thread. The keyword does not transform an arbitrary library into a nonblocking driver. Some runtimes provide supported ways to run blocking code in an executor or thread pool; those pools also need limits.

      Python's threading behavior also depends on the implementation and build. In GIL-enabled CPython, the GIL limits simultaneous Python bytecode execution; native extensions can release it, separate processes provide another option, and free-threaded builds change the contract. Do not treat “Python threads can never run in parallel” as a universal rule. See Python's threading documentation ↗.

      Key takeaways

      • Verify call, scheduling and suspension semantics for the actual runtime and driver.
      • Async syntax cannot make a synchronous blocking library nonblocking by itself.
      • Runtime and build choices affect available parallelism and supported execution models.

      Go's scheduler: goroutines, threads and execution slots

      A goroutine is a runtime-managed execution task with a stack that starts small and can grow. It is not a separate OS thread. Go can multiplex many goroutines over native threads and schedule runnable work while another goroutine waits. Goroutines still consume memory and scheduling resources; creating them without bound is not free.

      Runtime termRole
      GA goroutine: the computation and its execution state.
      MAn OS thread that may execute Go, runtime or syscall work, or be idle.
      PRuntime resources and permission needed to execute user Go code; the number is governed by GOMAXPROCS.

      The scheduler matches runnable goroutines with the resources and threads that can execute them. It has run queues, scheduling policies and preemption mechanisms. A goroutine switch involves preserving execution state and runtime bookkeeping; describing it as “just changing one pointer” hides the work. See Go's runtime notes ↗.

      GOMAXPROCS bounds simultaneous execution of user Go code; it is not a cap on the total number of OS threads. Some threads can be blocked in system calls while others run. Its default depends on runtime version and available CPU constraints, so check the deployed environment rather than assuming it always equals physical cores. See the runtime reference ↗.

      Goroutines can therefore provide concurrency and, when resources permit, parallel execution. They still ultimately execute on OS-managed threads. Runtime scheduling complements OS scheduling rather than replacing it.

      Key takeaways

      • Goroutines are lightweight runtime tasks multiplexed over OS threads.
      • G, M and P describe computation, native threads and user-code execution resources.
      • GOMAXPROCS limits simultaneous user Go execution, not all native threads or all work in the system.

      Go HTTP handlers and network waiting

      Go's HTTP server lets handlers use ordinary sequential-looking code while other requests progress. Network operations supported by the runtime can park the waiting goroutine and arrange for it to become runnable when the socket can make progress. Go also uses network polling machinery, so goroutines and event-driven I/O are not mutually exclusive ideas.

      A blocking system call can occupy an OS thread; the runtime can arrange for other goroutines to execute elsewhere. The exact behavior depends on the operation and library. A goroutine does not make an arbitrary CPU-heavy loop, native call or driver instantly interruptible.

      Be precise when reading server source. The documented net/http.Server.Serve behavior creates a service goroutine per accepted connection, which then reads requests and calls the handler. That statement is not the same as one fresh goroutine per HTTP/1.1 request: a persistent connection can carry several requests. HTTP/2 adds stream handling and different concurrency behavior. See the HTTP server contract ↗.

      Database calls can wait to acquire a pool connection, send data, receive data and iterate results. The wait is not confined to the source-code line that first issues a query. Carry request deadlines through supported APIs, release rows and connections correctly, and bound downstream work. A large number of cheap goroutines can still exhaust a database pool or retain substantial response memory.

      Request handlers can access shared application state concurrently, so the concurrency model does not remove the need for synchronization. See Go's goroutine explanation ↗ and request and worker lifetime management.

      Key takeaways

      • Go combines runtime task scheduling with native threads and network polling.
      • Connection goroutines, HTTP requests and protocol streams are distinct concepts.
      • Use deadlines, resource cleanup and downstream limits even when goroutines make concurrency easy.

      Shared-state races and lost updates

      Two tasks increment a shared counter that starts at zero. A conceptual increment reads the current value, calculates a replacement and writes it back. If those steps are not protected as the required atomic operation, the tasks can overwrite one another's updates.

      StepTask ATask BShared counter
      1Reads 00
      2Reads 00
      3Computes 10
      4Computes 10
      5Writes 11
      6Writes 11

      The expected value after two valid increments is two, but this interleaving leaves one. This is an illustrative lost update, not a promise about the exact machine instructions generated for every language. Some operations are atomic; some unsynchronized programs have undefined or otherwise restricted behavior under their language memory model.

      A data race involves conflicting unsynchronized memory accesses under the relevant language's rules. A broader race condition means correctness depends on an uncontrolled ordering or timing. Not every logical race requires simultaneous native thread execution or a shared-memory data race. See the Go memory model ↗.

      Synchronization must establish both the required ordering and the visibility of writes. Sleeping for a guessed duration or observing that a test usually passes does not establish either property. Identify the invariant and the complete operation that needs protection.

      Key takeaways

      • Read-modify-write sequences can lose updates when their steps interleave without suitable protection.
      • A data race and a logical race condition are related but different concepts.
      • Define the invariant and use real ordering and synchronization guarantees, not timing guesses.

      Single-threaded async code can race too

      A JavaScript function can check a shared value, suspend at await, then resume after another function has changed that value. No two JavaScript statements need to execute simultaneously for the overall check-then-act operation to become incorrect.

      Unsafe illustrative function: the check and update straddle a suspension
      let balance = 100;

async function withdraw(amount) {
  if (balance < amount) return false;
  await processWithdrawal(amount);
  balance -= amount;
  return true;
}

const results = await Promise.all([withdraw(100), withdraw(100)]);
// Both can pass the check before either update.
// results can be [true, true], with balance ending at -100.

      With an asynchronous processWithdrawal implementation, the first call sees 100 and suspends. The second call also sees 100 and suspends. Later, one subtracts 100 and the other subtracts another 100. The early condition did not reserve capacity or protect the later change.

      The external action can already have happened twice before the local variable exposes the problem. Protecting only the final subtraction is therefore insufficient. Moving a subtraction before await also introduces recovery questions if the external operation fails. The complete workflow needs an ownership, atomicity and failure policy appropriate to its storage and side effects.

      Similar races appear in inventory reservations, duplicate job creation, cache refreshes and unique-resource allocation. Look for assumptions that were true before a suspension but may not be true when execution continues. A single-threaded event loop serializes individual execution segments, not the entire logical workflow across awaits.

      Key takeaways

      • Check-then-act workflows can interleave across awaits on one event-loop thread.
      • Protect the full invariant and external effect, not only the final local assignment.
      • Revisit every assumption that must survive a suspension point.

      Locks, atomic operations and database coordination

      A mutex provides exclusive entry to a protected critical section. For a counter, protect the whole read-modify-write operation and ensure every competing access follows the same rule. In Python, a context manager releases a threading lock even when the body raises:

      A process-local threaded counter
      import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    with lock:
        counter += 1

      Use primitives appropriate to the scheduler: blocking a loop thread on a native lock can prevent the task holding the resource from progressing. Async-aware locks suspend tasks according to their runtime. Locks can also deadlock when tasks acquire resources in conflicting orders. Keep ownership clear, establish consistent ordering and avoid unnecessary long critical sections.

      An atomic increment can suit a simple counter, but does not automatically protect a multi-step business invariant. A local mutex also cannot coordinate independent application replicas updating shared database state. Put durable constraints and conditional changes at the authority that owns that state.

      Illustrative atomic conditional debit of positive integer credit units
      UPDATE accounts
SET balance = balance - $1
WHERE id = $2
  AND $1 > 0
  AND balance >= $1
RETURNING balance;

      Validate the amount and account access before this operation and handle an empty result as failure to apply the change. A separate SELECT followed by UPDATE is not made safe merely by adding a transaction without appropriate locking, isolation or conflict handling. More complex changes can need row locks, version checks or retryable transactions. See PostgreSQL's transaction-isolation semantics ↗.

      External payments, messages and database changes still need explicit idempotency and recovery; a local lock does not make them one atomic transaction. See durable retries and outbox and distributed workflow boundaries.

      Key takeaways

      • Use suitable locks or atomic operations to protect the entire invariant and establish ordering.
      • Process-local synchronization does not protect shared database state across replicas.
      • Use conditional database operations or appropriate transaction coordination and handle conflicts explicitly.

      Message passing and ownership

      Another design gives one task ownership of mutable state. Other tasks send requests or messages to that owner rather than modifying the state directly. A counter owner, for example, receives increment messages and applies each update through its own execution path.

      Conceptual single-owner counter
      Producer A ── increment message ──┐
                                 ├─ bounded mailbox → owner → counter state
Producer B ── increment message ──┘

Only the owner changes the counter.
Replies describe the result after the owner applies the operation.

      Go channels can support this style and provide synchronization under documented rules. A channel is not a blanket race-prevention guarantee. If a message contains a pointer and senders keep mutating the pointed-to object, shared-state races can remain. Define whether a message transfers ownership, copies data or grants shared immutable access.

      Mailboxes and channels also have capacity, blocking, shutdown and ordering behavior. A slow owner can become a bottleneck, and a full queue needs backpressure or an explicit overflow policy. Waiting for a reply can deadlock if the participating tasks depend on one another in a cycle. See Go's channel synchronization rules ↗.

      This pattern can simplify reasoning about an invariant, but it does not by itself persist state across process loss. A durable broker and recovery design serve different responsibilities from an in-process channel. Select the mechanism from the required lifetime and failure contract.

      Key takeaways

      • A single owner can serialize state changes through messages.
      • Ownership and aliasing rules still matter when messages carry references.
      • Channels need bounded capacity and lifecycle policies; they are not automatically durable queues.

      Bound concurrency and own task lifetimes

      Cheap tasks make it easy to create more pending work than the system can finish. Each waiting request or task may retain inputs, buffers, timers, stack or continuation state, database demand and eventual response data. A million lightweight tasks can still exhaust memory or overload a dependency.

      Use limits matched to the scarce resource: bounded worker pools, semaphores, connection budgets, request admission or bounded queues. Decide whether callers wait, receive a rejection or submit durable deferred work. A task-count limit and a queue-length limit address different parts of the backlog.

      Define who waits for child tasks, observes their failures and requests cancellation. Request completion or disconnection should have a deliberate effect on spawned work; detached tasks do not become reliable background jobs automatically. An owned task group or equivalent structured lifetime can make cleanup and error propagation easier to reason about.

      Cancellation is generally cooperative. A deadline does not forcibly interrupt every native call or stop already-committed external effects. Close owned resources, propagate supported cancellation signals, and wait for work to settle according to the policy. Unobserved failures and tasks abandoned forever are resource problems as well as correctness problems.

      The same principles apply across threads, async tasks and goroutines. See shutdown and cancellation and queueing, headroom and downstream capacity.

      Key takeaways

      • Limit pending work as well as active execution and downstream connections.
      • Give child tasks an owner for completion, error handling and cancellation.
      • A timeout or cancelled task does not automatically undo external effects.

      Choose and verify the execution model

      Start by separating useful computation from waiting, then identify the resource limiting progress. Use a model supported by the actual runtime, drivers and operational environment. Thread pools, event loops and runtime-managed tasks can coexist in one backend.

      Test correctness separately from performance. Force relevant interleavings with controlled barriers or mock operations, assert invariants and exercise failure and cancellation paths. Repeatedly adding sleeps until a test passes only hides timing assumptions.

      Race detectors can help find supported shared-memory data races in executed paths. Go's race detector ↗ is one example, but a clean run is not proof that every schedule or logical workflow is safe. The single-threaded async check-then-act race still needs a business-invariant test.

      Measure latency distributions, completed throughput, memory and resource pressure under representative load. Profiles explain CPU work and appropriate traces or wait measurements explain elapsed blocking. Concurrency organizes overlapping progress; parallelism supplies simultaneous execution when useful. The combination should satisfy the workload's correctness and capacity requirements rather than maximize a thread or task count.

      Key takeaways

      • Choose mechanisms from measured computation, waiting and runtime behavior.
      • Use controlled correctness tests and appropriate race tooling without treating them as complete proofs.
      • Compare useful throughput, latency, memory and failure behavior at realistic load.
