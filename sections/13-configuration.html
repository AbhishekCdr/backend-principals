      Lesson 13

      Configuration Management

      Configuration controls how the same application connects, behaves and uses resources in different environments. Organize settings, secrets and feature controls so that changes are deliberate, validated and easy to trace.

      Configuration is application behavior

      Configuration management is the process of organizing, storing, delivering, validating and maintaining application settings. Database passwords and API keys are only one part of it. Ports, timeouts, logging levels, session lifetimes and feature flags also change what the backend does without requiring a different implementation of its business logic.

      Consider an e-commerce backend. Its configuration identifies the database, selects a payment provider's test or live environment, limits database connections and controls access to a new checkout flow. The same code can behave very differently when any of those values change. A non-secret setting can be just as consequential as a secret: a wrong payment endpoint or an excessive order limit can still cause serious problems.

      A configuration change is a behavior change

      Moving a value out of source code does not make changing it harmless. Give important settings clear ownership, validation, change history and a recovery plan.

      Scattered constants, undocumented overrides and different settings on different instances make incidents difficult to reproduce. A systematic configuration path lets you answer: which values took effect, where did they come from, and which version was this instance using? Centralizing that policy does not require storing every setting in a single physical service.

      Key takeaways

      • Configuration includes operational behavior and business controls as well as secrets.
      • Non-secret settings can still affect security, correctness and availability.
      • Make effective values, their sources and their change history understandable.

      Types and characteristics of configuration

      CategoryTypical settingsWhat they control
      Application settingsListening port, log level, request limits, timeouts.How the server starts and handles work.
      Database connectionsHost, port, database name, credentials, TLS and pool settings.Where data lives and how the application accesses it.
      External servicesAPI endpoints, credentials, retry limits and callback URLs.Integration with email, payments, identity and other providers.
      Feature flagsCheckout version, rollout percentage, eligible cohorts.Which implemented behavior is enabled for which users.
      Security settingsSigning keys, allowed origins, session expiry and authentication policies.Identity, trust and access-related behavior.
      Performance and observabilityWorker concurrency, cache limits, metrics destinations, trace sampling.Resource use and diagnostic visibility.
      InfrastructureReplica counts, resource limits, network and deployment settings.The environment in which application processes run.
      Business rulesOrder limits, eligibility thresholds, supported regions.Product policy that is intentionally adjustable.

      Classify each setting along several dimensions: sensitivity, environment or tenant scope, change frequency, owner and whether it can change while the process runs. A port usually belongs to startup configuration; a rollout flag may change frequently; a signing key is sensitive and needs a coordinated rotation process.

      Record a setting's type, unit, allowed values, default and purpose. A name such as requestTimeoutMs is less ambiguous than timeout. Distinguish optional values from mandatory ones, and identify combinations that must remain consistent.

      Not every database value is application configuration. Individual orders are business data. A customer-editable pricing rule may need an audited domain model rather than a deployment environment variable. Keep adjustable policy separate from the code that enforces the policy.

      Key takeaways

      • Identify application, connection, feature, security, infrastructure and business settings.
      • Document sensitivity, scope, ownership, type, units and update behavior for important values.
      • Choose a domain model for business data instead of turning every value into an environment variable.

      Choose storage by responsibility

      Storage choices depend on who changes a value, who may read it, how often it changes and how the application receives updates. The source of truth and the delivery mechanism can differ: a secret manager may own a credential while a deployment injects it into a process.

      SourceUseful roleImportant limit
      Environment variablesSupply deployment-specific values to a process.Values need parsing; changing deployment settings does not automatically update running processes.
      Configuration filesGroup structured settings and version non-secret defaults.Files need explicit loading, validation and appropriate permissions.
      Key-value configuration storesShare settings across instances and support controlled updates.Access control, availability and update consistency still need design.
      Secret managersControl access to sensitive values and manage their lifecycle.The application still needs an identity, retrieval policy and safe handling after delivery.
      Feature-management servicesEvaluate flags and targeting rules.Define evaluation context, safe defaults and provider-failure behavior.

      A common hybrid keeps ordinary defaults in version control, deployment overrides in the environment and sensitive credentials in a secret manager. Use the systems already provided by your platform when they meet the requirements. Adding several new services merely to load a handful of settings also adds operational failure points.

      Key takeaways

      • Separate where a value is managed from how it reaches the application.
      • Choose storage based on sensitivity, access patterns and update needs.
      • Hybrid storage is normal; keep its loading and ownership rules simple.

      Environment variables and dotenv files

      Environment variables belong to a process's environment and are normally supplied when that process starts. A shell, service manager or deployment platform can provide them. A dotenv loader reads a file and populates the application process's environment; it does not update the parent shell or create global operating-system settings for every program.

      Illustrative local settings — no credentials
      APP_ENV=development
PORT=8080
LOG_LEVEL=debug
DB_POOL_MAX=10
REQUEST_TIMEOUT_MS=10000
CHECKOUT_V2_ENABLED=false

      Node.js exposes environment values through process.env. Values loaded from a dotenv file remain strings: "10" is not yet a number, and "false" is not a Boolean. An absent key is different from an empty value. Parse these deliberately; testing the truthiness of a nonempty "false" string would incorrectly enable a feature. See Node.js environment-variable documentation.

      Use the loader supported by your runtime or project, and document whether existing process values override file values. Dotenv syntax and override behavior vary by implementation. A filename such as .env.production is not automatically loaded unless your setup explicitly supports that convention.

      Commit a safe example file documenting required names and non-secret defaults. Keep real credentials out of version control, images and logs. An environment variable is a delivery mechanism, not an encrypted vault; code with access to the process can still read it.

      Key takeaways

      • Dotenv loads values into the application process, not the entire operating system.
      • Parse strings explicitly and distinguish missing values, empty values and valid false or zero values.
      • Document loading precedence and keep real secrets out of committed example files.

      Configuration files

      Files are useful when related settings form a hierarchy. A server section can hold its port and timeout, while database and logging sections carry their own settings. Non-secret files also let changes pass through ordinary review and version-control history.

      FormatUseful propertiesThings to account for
      JSONCommon tooling and explicit objects, arrays, numbers and Booleans.Standard JSON has no comments; document settings separately or through the schema.
      YAMLReadable nested structures and comments.Indentation and scalar interpretation matter; use a safe parser mode and validate types.
      TOMLTables, explicit value types and comments.Use a supported parser and keep the same application-level validation rules.
      Example non-secret configuration document
      {
  "server": { "port": 8080, "requestTimeoutMs": 10000 },
  "logging": { "level": "info" },
  "database": { "poolMax": 10 },
  "features": { "checkoutV2Enabled": false }
}

      These are illustrative values, not universal production defaults. Parsing confirms the document's syntax; it does not prove that the port is acceptable, that the pool fits the database budget or that the configuration is complete. Files containing secret references also need a defined resolver: writing an environment-variable name into JSON does not interpolate it automatically.

      Key takeaways

      • JSON, YAML and TOML organize settings differently but all require schema validation.
      • Version ordinary defaults and document each setting's purpose and units.
      • Secret references and variable substitution need explicit loader behavior.

      Remote stores and secret delivery

      A remote configuration store gives multiple instances a shared place to retrieve values. Systems such as Consul and etcd provide key-value storage, but operating them safely still requires authentication, access controls, backups and availability planning. A general key-value store is not automatically a complete secrets-management system. See Consul's KV overview.

      Secret-management options include HashiCorp Vault, AWS Secrets Manager, Azure Key Vault and Google Cloud Secret Manager. Their integrations and operating models differ. Choose based on the existing platform and required lifecycle controls rather than assuming every backend needs to operate a separate vault cluster. Vault's overview describes its role in controlling access to sensitive values.

      Understand the storage and retrieval contract

      AWS Parameter Store supports ordinary String and StringList parameters as well as SecureString values protected with AWS KMS. Do not assume every parameter gets the same encryption treatment. AWS Secrets Manager adds purpose-built secret lifecycle features, including supported rotation workflows. See the Parameter Store documentation.

      Encrypted storage does not mean unusable ciphertext in the app

      Managed services commonly decrypt authorized reads on the service side and deliver the usable secret over TLS. For example, AWS Secrets Manager returns a decrypted SecretString. Applications do not generally need their own private key to decrypt each retrieved value. The secret still needs protection in application memory and logs. See GetSecretValue.

      Delivery may happen through the application, a deployment agent or a mounted file. Use a narrowly scoped workload identity where supported to authenticate retrieval. Moving secrets into a remote store should not require hardcoding a new, broadly privileged access token in source code.

      Key takeaways

      • Shared configuration storage and secret lifecycle management have different responsibilities.
      • Verify the chosen parameter type, encryption, access controls and rotation support.
      • Authorized retrieval usually gives the application usable secrets; keep that delivery and use secure.

      Precedence and one effective configuration

      Hybrid storage needs an explicit precedence policy. Otherwise a setting may be present in three places while nobody knows which one the process uses. Define the policy per deployment and make the mapping from external names to application fields predictable.

      One possible policy for ordinary application settings
      Lowest priority: application defaults
                 environment-specific configuration file
                 process environment overrides
Highest priority: approved remote configuration overrides

      This is an example policy, not an industry standard. If a file sets the pool maximum to 10, the environment sets it to 20 and an approved remote override sets it to 30, this policy selects 30. Map the inputs to the same logical field, resolve the winner and validate the effective configuration. Document whether nested objects merge and whether arrays replace earlier arrays; avoid surprising partial replacements.

      Keep protected secrets on their intended source path instead of allowing any ordinary override to replace them. A missing mandatory remote value must not silently fall back to development credentials. An explicitly supplied invalid value should fail validation, not disappear behind a default. Defaults apply to the absence conditions you deliberately support.

      Produce one application-facing configuration object instead of reading raw environment values separately in every handler. Record safe provenance such as source names and version identifiers so operators can investigate overrides without dumping secret values.

      Key takeaways

      • Define precedence, field mappings and merge behavior before combining configuration sources.
      • Reject invalid overrides and missing mandatory secrets instead of hiding them with unsafe fallbacks.
      • Expose one validated configuration view and retain safe information about its sources.

      Validate configuration before startup

      Treat configuration as external input. It can be missing, mistyped or incompatible even when it came from a trusted deployment system. Validate the effective values before opening the application to traffic, as introduced in Error Handling & Fault Tolerance.

      CheckExample
      PresenceA mandatory database endpoint must exist; an empty value is not a usable endpoint.
      Type and parsingParse a Boolean explicitly and require a complete valid integer for a numeric field.
      Range and allowed valuesA listening port fits the application's allowed range; a log level belongs to its supported set.
      UnitsDistinguish milliseconds from seconds and byte limits from item counts.
      Cross-field rulesMinimum pool size does not exceed maximum; an enabled integration has its required settings.
      Environment rulesProduction uses approved endpoints and required transport-security settings.

      Use the project's validation facilities or a suitable schema library, such as Zod in a TypeScript application or go-playground/validator in Go. Static types alone cannot validate values supplied after compilation. Whichever tool you use, keep the schema and defaults near the configuration-loading boundary so business code receives predictable values.

      Catch misspelled keys in owned configuration documents. When reading the process environment, validate the application's declared settings rather than rejecting every unrelated variable inherited from the operating system. Give errors that name the problematic setting and rule, without including a credential or full connection string.

      Check missing mandatory values, valid defaults, invalid ranges, malformed numbers, false Booleans, units and conflicting sources. Also distinguish validation from connectivity: a correctly shaped API key may still be expired, and a valid database address may be unreachable. Initializing required clients and continued runtime error handling remain necessary.

      Key takeaways

      • Validate required values, types, ranges, units and related-field rules before serving traffic.
      • Use safe diagnostics and test defaults, invalid overrides and environment-specific rules.
      • Configuration validity does not guarantee that its dependencies are available or credentials remain valid.

      Development, test, staging and production

      Environments have different priorities. Keep the application implementation consistent while supplying the settings and resources appropriate to each environment. A setting can change behavior already supported by the code; entirely new behavior still requires an implementation.

      EnvironmentPrimary purposeConfiguration implications
      DevelopmentFast iteration and debugging.Local or isolated services, useful diagnostic logging and development credentials.
      TestRepeatable automated checks.Isolated data, controlled inputs and safe substitutes or sandboxes for external side effects.
      StagingExercise deployment and production-like behavior.Compatible dependencies and security paths with separate credentials and test data.
      ProductionServe real users reliably and securely.Real service endpoints, deliberate capacity limits, monitored behavior and restricted access.

      Staging can use less capacity than production to control cost, but record that difference. Tests on a tiny staging database cannot establish how production behaves under peak load. Preserve the features and dependency versions needed to test compatibility, and use suitable capacity when the purpose is performance testing.

      Separate credentials and access boundaries so test jobs cannot accidentally send real customer emails or write to the production database. Names such as “staging” help humans, but they are not security controls by themselves. Configuration changes should be attributable even when the application binary has not changed.

      Key takeaways

      • Use environment-specific configuration to support development, testing and production priorities.
      • Isolate credentials, resources and side effects between environments.
      • Document staging differences; reduced capacity limits what its tests can demonstrate.

      Tune resources and timeouts together

      A larger production connection pool is not automatically better. Pool size must fit database capacity, query duration, traffic and the number of application replicas. Twenty replicas with a maximum of 50 connections each can request up to 1,000 connections, before accounting for workers, migrations or administrative access. Autoscaling changes that combined budget.

      Values such as development 10, staging 2 and production 50 are illustrations, not recommended defaults. A smaller pool may reduce pressure, but does not necessarily reduce the bill of a fixed-price database instance. Choose limits using measurements and the actual hosting model. Worker concurrency, runtime parallelism and cache limits need the same capacity reasoning.

      A timeout belongs to a particular layer

      Client deadlines, proxy timeouts, application deadlines, database pool acquisition and query execution all measure different things. If an image-generation operation takes 80 seconds but an outer layer waits only 60, the caller may give up before work completes. A gateway may return 504 when its upstream times out; another component may close the connection or produce a different error. A configured timeout does not universally imply a 504 response.

      Budget inner work within the overall deadline and propagate cancellation where supported. Use background jobs for appropriate long-running work rather than extending every timeout indefinitely. Define separate security lifetimes too: session idle timeout and absolute expiry are different rules, with values chosen for the application's security and usability requirements.

      Key takeaways

      • Budget connections and concurrency across every replica and worker.
      • Tune from measured needs; a larger pool or smaller number does not guarantee better performance or lower cost.
      • Give timeouts clear scope and units, and coordinate them across the request path.

      Feature flags and controlled rollout

      A feature flag selects between behavior that already exists in the application. Deploy a new checkout implementation with its flag disabled, then enable it for a small group before broadening access. Separating deployment from exposure makes it possible to observe a change and disable the new path without immediately deploying different code.

      Targeting can use an eligible account, a region, a plan or a rollout cohort. Supply only the evaluation context needed for the decision and use trustworthy server-side attributes for consequential rules. OpenFeature describes a targeting key and custom context fields in its evaluation-context specification.

      Keep assignment stable when a user should remain in the same experiment. A random decision on every request can switch checkout behavior halfway through a purchase. Record the chosen variant with the workflow when necessary, and measure outcomes before increasing exposure. A percentage rollout by itself is not a complete A/B experiment: define assignment, metrics and how results will be evaluated.

      Flags do not replace authorization

      Hiding a button or disabling a frontend feature is not permission enforcement. The backend must still authorize the operation. A feature's safe fallback also depends on its purpose; “enabled” is not a safe universal response to a failed flag lookup.

      Give flags an owner, a default, a provider-failure policy and a removal plan. Exercise both paths while they exist. Turning off a flag does not undo data already written by the new behavior, so keep rollback and schema compatibility in the rollout plan.

      Key takeaways

      • Feature flags separate deploying code from exposing its behavior.
      • Use deliberate targeting, stable assignment and outcome measurements for controlled rollout.
      • Retain authorization checks and define flag defaults, ownership, rollback limits and cleanup.

      Runtime changes in distributed systems

      Some settings are read once at startup; others are refreshed through polling, watches or a provider SDK. Define which model each setting uses. Updating a remote value does not automatically reconfigure an existing database client, listener or worker pool.

      Kubernetes illustrates the distinction: ConfigMap values injected as environment variables require a restart to change in the process. Normally projected ConfigMap files are updated eventually, but the application must notice and apply the change; subPath mounts are an exception to automatic file updates. ConfigMaps are intended for non-confidential data. See the ConfigMap documentation.

      Validate a candidate before making it active

      For settings designed to reload, construct and validate a complete candidate configuration, then switch the active view together. Avoid exposing a half-updated combination of related values. Initialize replacement clients safely and retire old ones deliberately. For settings that are difficult to reload correctly, a controlled restart may be simpler.

      Multiple instances may observe a change at different times. Use version identifiers to detect drift and design compatibility across a rollout. If an operation requires a consistent set of settings, keep one version for that operation or use a stronger coordination mechanism appropriate to its rules. A centralized source does not guarantee simultaneous adoption.

      Plan for an unavailable configuration service

      Bound fetch times and retries. A new instance with missing mandatory settings should not start serving requests. An existing instance may retain its last validated configuration under an explicit staleness policy. That policy cannot make expired credentials valid or override a required security revocation. Monitor refresh failures and configuration age.

      Key takeaways

      • Declare whether a setting requires restart or supports an implemented refresh path.
      • Validate complete updates, track versions and account for instances adopting changes at different times.
      • Define fetch budgets and safe staleness behavior without bypassing expiry or revocation.

      Secret access, exposure and rotation

      Keep real secrets out of source code, committed configuration, container images, frontend bundles and logs. Anything sent to a browser must be treated as public, even if it began as a server environment variable. Use only credentials explicitly designed for public clients there.

      Apply least privilege to people, workloads and deployment jobs: grant access to the specific secret and environment needed for the task. Job titles alone are too broad; a backend developer does not automatically need every production credential. Separate read, update and administrative rights, and audit access. These practices are covered in the OWASP Secrets Management Cheat Sheet.

      Plan rotation and revocation. Introduce a replacement, verify consumers can use it, then retire the old credential according to policy. Coordinate signing-key changes with token verification and expiry; an emergency revocation may intentionally invalidate sessions. If a secret leaks, revoke or rotate it promptly. Deleting it from the latest commit does not invalidate copies in repository history or elsewhere.

      Rotation applies to credentials and keys; ordinary settings such as ports need change control, not arbitrary periodic replacement. Test the rotation process as well as initial secret loading.

      Key takeaways

      • Keep secrets out of public artifacts and grant narrowly scoped access.
      • Coordinate replacement, verification and revocation across consumers.
      • Respond to exposure by invalidating the secret, not merely deleting one visible copy.

      A predictable configuration workflow

      A useful configuration pipeline makes the transition from raw settings to a running service explicit. It can be a small startup module using the project's existing facilities; it does not need a new framework or a remote service for every category of setting.

      1. Identify the deployment. Establish its environment, configuration locations and workload identity without embedding privileged bootstrap credentials.
      2. Load the declared sources. Read defaults and files, obtain deployment overrides and retrieve required remote values within a bounded startup budget.
      3. Resolve and validate. Apply documented precedence, parse types and check required values, ranges, units and cross-field rules.
      4. Initialize dependent components. Give clients and services the validated settings they need, keeping sensitive values away from unrelated modules.
      5. Become ready. Record safe configuration version information and accept traffic only when required initialization succeeds.
      6. Manage changes. Review and validate updates, roll them out deliberately, observe outcomes and use the documented rollback or rotation procedure.

      For an e-commerce service, review whether payment mode matches the environment, the database and worker pools fit the combined budget, the checkout flag has a known fallback and the configuration is complete before the service becomes ready. Those checks connect deployment settings to actual user-facing consequences.

      Keep a small configuration reference with each setting's name, purpose, owner, type, unit, default, sensitivity and restart or reload requirement. Use source and version information for troubleshooting instead of printing every value. This makes configuration understandable both during routine development and when someone must diagnose an incident quickly.

      Key takeaways

      • Load, resolve, parse and validate before initializing the application and accepting traffic.
      • Make behavior changes reviewable, observable and recoverable.
      • Document the configuration contract so developers and operators can reason about the effective settings.
