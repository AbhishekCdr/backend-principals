      Lesson 06

      Layers, Middleware & Request Context

      What happens inside the server between receiving a request and sending a response? Handlers, services and repositories divide the work, middleware handles recurring steps, and request context carries information through the journey. These three ideas fit together in one request lifecycle.

      The request lifecycle inside a server

      Earlier lessons followed HTTP across the network, matched routes, decoded payloads and validated input. Now connect those pieces to the application that processes the request. The server listens on a port; its HTTP implementation reads the incoming message and exposes it to application code. A router matches the method and path to a handler.

      A simplified successful request
      Client → HTTP server → middleware → route → handler
                                             ↓
                                          service
                                             ↓
                                         repository ↔ database
                                             ↓
Client ← HTTP response ← handler ← service ← result

      Middleware can also be attached to individual routes. Some requests finish early, such as an authentication failure; some services never need a database. The diagram is a common path, not a requirement that every request visits every component.

      ComponentMain question it answers
      Handler / controllerHow does this HTTP request become an application operation, and how is its result returned?
      ServiceWhat business operation must happen, and which rules apply?
      RepositoryHow do we read or change persistent data?
      MiddlewareWhich shared request/response processing should run here?
      Request contextWhich information and signals belong to this particular request?
      A pattern, not a mandatory folder structure

      A small application can do everything in one handler. Separate responsibilities when it helps you understand, test and change the code. Three layers do not require three services, three processes or a collection of empty wrapper classes.

      Key takeaways

      • The internal lifecycle runs from HTTP input through application work to an HTTP response.
      • Handler = HTTP boundary; service = business operation; repository = persistence.
      • Middleware adds shared processing; context carries information scoped to one request.

      Handlers and controllers: the HTTP boundary

      A handler is the function responsible for a matched route. A controller often groups related handlers. Keep HTTP concerns here so the rest of the application can work with ordinary data. Frameworks may provide request/response objects, a combined context object, or a request argument with a returned response; the exact signature is not universal.

      1. 1. ExtractRead the route's inputs

        Collect the required path parameters, query parameters, headers and body. These sources come from the endpoint's contract: a POST can have query parameters as well as a body.

      2. 2. BindDecode into native values

        Turn JSON text into an object, dictionary or struct. Binding maps decoded fields into the application's input representation. Malformed JSON usually produces a 400 response.

      3. 3. CheckValidate and transform

        Check required fields, types, formats and ranges. Apply deliberate conversions and defaults, then use the resulting validated values. Reject bad input before business side effects.

      4. 4. DelegateCall the service

        Pass application input and the verified caller identity needed by the use case, along with cancellation or tracing information where appropriate.

      5. 5. RespondMap the result back to HTTP

        Select the response status, headers and public response fields. Serialize the result, or delegate a failure to the application's central HTTP error handler.

      Parsing may already happen in middleware or framework binding. This is a framework choice, not a rule that JavaScript is automatic while Go or Python must always parse inside a handler. Successfully decoding JSON also does not prove that it satisfies your API's schema.

      Defaults make downstream input predictable

      Suppose GET /books accepts an optional sort parameter with values name or date. Validate the supplied value and choose date when it is absent. The service now receives an explicit sort choice every time.

      RequestApplication input
      GET /books{ sort: "date" } — documented default.
      GET /books?sort=name{ sort: "name" } — accepted choice.
      GET /books?sort=unknownValidation error — an invalid supplied value is not a missing value.

      Optional filters and sorting controls often make an API easier to use. Required query parameters are still valid when the operation needs them. Likewise, transformation can precede a check when explicit parsing is needed, as with a numeric query string. See Validations & Transformations for the full pipeline.

      Success still needs a response

      Typical choices include 200 OK for a successful read and 201 Created for creation. DELETE does not always require 204: it can return 200 with a result, 202 for accepted but unfinished work, or 204 No Content when completed without a response body. A 204 is still an HTTP response. DELETE request bodies have no generally defined semantics; an identifier in the target URL is usually clearer. HTTP specification: DELETE.

      Key takeaways

      • Extract → bind/decode → validate/transform → call service → map and send the response.
      • Parsing may run upstream; input validation still has to happen.
      • Default missing optional values deliberately; reject supplied values that violate the contract.
      • HTTP status codes, headers and response serialization belong at the HTTP boundary.

      Services: business rules and orchestration

      A service implements a use case such as creating a book, listing a user's bookmarks or sending a notification. It takes application data, applies the relevant business rules, coordinates the work and returns a result or an application error.

      One service method can call several repositories, combine their results, contact another service and arrange an email. Another might only send an email and never access a database. This coordination is called orchestration.

      What belongs here

      Resource ownership checks, account limits, business decisions, transaction boundaries and the sequence of repository or external-service calls.

      What belongs at the HTTP boundary

      Reading raw headers, decoding an HTTP body, choosing a status code, setting response cookies and sending JSON to the client.

      Keeping services independent of HTTP lets a command-line tool, a scheduled job and an API reuse the same business operation. Independent of HTTP does not mean free of side effects: a service can absolutely write data or send messages.

      Validation does not end at the controller

      A valid book ID does not prove that the caller owns that book. A valid order quantity does not prove that stock is available. Services enforce these domain rules and authorization checks, with database constraints or transactions where consistency requires them.

      If several writes must succeed together, coordinate a transaction. An external email cannot be rolled back by the database; decide when it should run and how a failure or retry should behave. Splitting code into layers does not itself make a multi-step operation atomic.

      Key takeaways

      • A service implements a business use case and may orchestrate multiple operations.
      • Pass application data and verified identity rather than raw HTTP request/response objects.
      • Keep domain rules and resource authorization here even when boundary validation passes.
      • Services can have side effects; transaction and retry behavior still need deliberate design.

      Repositories: focused persistence operations

      A repository hides the details of reading and changing stored data. It accepts identifiers, filters or data to persist, constructs the database operation, and returns a predictable result. The store could be relational, document-based or another persistence system.

      OperationInputResult contract
      listBooksOwner, filters, sort and pagination.A collection of books, possibly empty.
      findBookByIdBook ID and any required access scope.One book or an explicit not-found result.
      createBookValidated book fields and its owner ID.The created record or identifier.
      deleteBookBook ID and any required access scope.A defined result such as the number of affected records.

      Avoid a method that returns a single book when an optional ID is present and an array when it is absent. Different return shapes make every caller branch. Optional filters are fine when the result contract stays stable. A focused operation may use joins or several queries; it does not have to mean exactly one SQL statement.

      Carry safe choices into the query

      In the sorting example, map name and date to known database columns. Do not paste arbitrary client text into an ORDER BY clause. Bind data values as query parameters, and retain database constraints as the last line of data integrity. The repository returns data or persistence failures; it does not decide HTTP response codes.

      Key takeaways

      • Repositories encapsulate persistence and expose focused operations with stable result shapes.
      • Separate collection queries from single-record lookups; optional filters are still useful.
      • Use bound values, allowlisted sort choices and database constraints.
      • The service coordinates repository calls; the HTTP boundary maps outcomes to responses.

      Middleware: shared processing between steps

      Authentication, logging and request parsing are needed by many endpoints. Repeating their implementation in every handler creates duplication; even calling the same helper in every handler makes it easy to forget one. Middleware attaches shared behavior to the request pipeline, globally or for a selected group of routes.

      Middleware can inspect input, attach metadata, prepare response headers, continue to the next step, or finish the request immediately. For example, an invalid session can produce a 401 before any book-creation logic runs.

      Continue or finish early
      Request → authenticate
            ├─ valid identity → attach identity → next step → handler
            └─ invalid token  → 401 response → stop application work

      In Express, middleware commonly receives req, res and next. Calling next() continues the chain; next(error) enters error handling. A middleware that neither responds nor continues leaves the request hanging. Once it sends a final response, it should stop its own execution instead of continuing into another response. Other frameworks may use wrappers or an awaited next handler instead. Express middleware guide.

      Key takeaways

      • Middleware centralizes recurring request/response work and can apply globally or per route.
      • Each step either continues processing or ends the request early.
      • req, res, next is an Express-style interface, not a universal middleware signature.
      • Do not leave a request hanging or continue business work after sending an early error.

      Common middleware responsibilities

      ConcernWhat it doesDetail to remember
      CORSHandles preflight requests and sets allowed-origin response headers.A browser access policy; authentication is still required for protected resources.
      Security headersAdds suitable response policies consistently.Choose policies for the content being served; CSP is especially relevant to HTML documents.
      AuthenticationVerifies a session or token and establishes a caller identity.Missing or invalid credentials can stop a protected request with 401.
      AuthorizationChecks coarse route permissions, such as an admin-only endpoint.A 403 can reject a known caller without permission; resource-specific checks remain necessary.
      Rate limitingEnforces a request budget per identity, API key or network source.Excess requests can receive 429; IP-only limits can group many users together.
      Logging / monitoringRecords request ID, method, route, outcome and duration.Redact credentials and personal data; avoid dumping entire bodies and headers.
      Parsing / validationDecodes supported body formats and applies route-specific input rules.Set size limits before consuming large payloads; do not use one schema for every endpoint.
      CompressionEncodes eligible responses with a supported algorithm, such as gzip.Negotiate with the client and set headers before the response is committed.
      Error handlingMaps failures to consistent public responses.Keep internal diagnostics in server logs rather than exposing them to clients.
      CORS is not an API firewall

      Missing CORS permission generally prevents browser JavaScript from reading a cross-origin response. A simple request may still reach the server and cause side effects; a failed preflight prevents the subsequent actual request. Non-browser clients do not enforce this policy and can choose their own Origin header. Keep authentication, authorization and appropriate CSRF defenses independent of CORS. MDN: how CORS works.

      Rate limits also depend on deployment details. Trust forwarded client-IP headers only from configured proxies, and coordinate counters across instances when the limit must apply to the whole service. A per-process counter is only a per-process limit.

      Key takeaways

      • Shared security checks, parsing, logging, compression and error mapping fit naturally in middleware.
      • CORS controls browser access to responses; it does not identify or authorize a caller.
      • Authentication establishes identity; authorization decides access; rate limiting controls volume.
      • Record enough to diagnose failures without logging passwords, tokens or unnecessary personal data.

      Ordering and global error handling

      Middleware order determines which information is available and which work runs before a rejection. Start with dependencies rather than copying a universal sequence:

      • Create request IDs and start timing early enough to observe failures.
      • Apply cheap traffic and size limits before expensive processing.
      • Handle CORS preflight before middleware that demands user credentials.
      • Parse a body before middleware that reads its fields; verify identity before checking its permissions.
      • Validate endpoint input before business side effects. A login route and a protected resource route may need different chains.
      • Arrange response headers and compression before writing the body; record final outcome when the response finishes.

      Placement depends on the execution model

      Express-style error handlers are registered after the routes and middleware whose errors they handle. Errors must reach that chain: asynchronous callbacks may need explicit forwarding, while rejected promises depend on the framework's support. Also, returning from next() does not generally mean an asynchronous response has finished. Express error-handling guide.

      In an onion-style pipeline such as Koa, an outer middleware awaits the next one and resumes on the way back out. An error boundary can wrap downstream work with a try/catch, so it is placed outside that work rather than simply registered last. The principle is to cover the operations that can fail using the framework's actual control flow. Koa's cascading middleware.

      Turn failures into a stable public contract

      Use known application errors to distinguish invalid input, missing resources, denied access and conflicts. Map those to appropriate 4xx responses. Unexpected failures receive a safe 5xx response and an internal diagnostic linked to the request ID. Not every failure is 400, and a raw database error should not be sent to the client.

      Example public validation error
      HTTP/1.1 400 Bad Request
Content-Type: application/json

{
  "error": {
    "code": "INVALID_SORT",
    "message": "sort must be name or date",
    "requestId": "req-7f21"
  }
}

      A central error handler only handles failures connected to its execution chain. It cannot automatically catch unrelated background-job failures or process crashes. After response headers or body bytes have been sent, it may also be too late to replace them with a new JSON error response.

      Key takeaways

      • Order middleware by dependencies: parse before consuming input, authenticate before checking identity-based access.
      • Error handlers go after relevant middleware in Express; outer wrappers can catch downstream errors in onion-style pipelines.
      • Forward asynchronous errors correctly and observe response completion explicitly.
      • Return stable, safe error codes and messages; keep diagnostic details linked to a request ID in logs.

      Request context: state scoped to one request

      A request passes through many functions. Some information is useful across these boundaries: who the caller is, which request this is and when its work should stop. A request context carries that information for this one execution. A middleware can establish it upstream and later handlers or services can read it.

      Context valueCreated or established byUsed by
      Verified user ID, roles or scopesAuthentication middleware.Authorization checks and operations performed for that user.
      Request ID / tracing metadataRequest-entry middleware or trusted tracing infrastructure.Logs, diagnostics and downstream request correlation.
      Request loggerLogging middleware.Code that records events with consistent request fields.
      Deadline / cancellation signalServer request lifecycle or timeout policy.Database calls, external requests and other cancellable work.
      Concurrent requests remain separate
      Request A → context { requestId: "A", userId: "user-17" }
Request B → context { requestId: "B", userId: "user-42" }

Each handler reads the context associated with its own request.

      Context is not a global currentUser variable and not a session that lasts across requests. Its storage and propagation depend on the stack: request-local fields, an explicit context argument or an asynchronous context facility. Downstream code only sees it when the application or framework propagates it correctly.

      Nor is every context a mutable dictionary. For example, Go derives contexts carrying values, deadlines and cancellation from a parent; callers pass the derived context onward. Go context documentation. Keep business input explicit and context small so it does not become a hidden container for every dependency, raw payload and secret.

      Key takeaways

      • Context carries metadata and signals for one request across function boundaries.
      • Keep concurrent requests isolated; never store the current user's identity in a shared global variable.
      • Propagate context deliberately; its API and mutability differ between frameworks.
      • Use context for request metadata, while keeping business inputs and dependencies clear.

      Use verified identity, not a client-supplied owner

      Consider a protected POST /books endpoint. A client could put another user's ID in its JSON body. That field is merely a claim; it must not become the authority for who owns the new record.

      1. MiddlewareVerify the session or token

        On success, establish the caller's user ID and relevant permissions in request context. On failure, stop the protected request with an authentication error.

      2. HandlerSeparate input from identity

        Read the book fields from validated input. Read the actor's identity from the trusted authentication result, not from an arbitrary body field.

      3. ServiceAuthorize the operation

        Check that this actor can create the book. For ordinary self-service creation, derive the owner ID from the actor and pass that explicit value to persistence.

      4. RepositoryPersist the authorized data

        Insert the permitted fields and owner ID. For reads, updates and deletes, apply the appropriate ownership or tenant scope as well.

      Reject unexpected ownership fields or ignore them according to a documented input contract. If an administrator can create a book on someone else's behalf, make that an explicitly authorized operation. A body-supplied target user can be input to that operation; it is still not proof of permission.

      Authentication does not create an account on every request

      Registration creates accounts, login establishes a session or issues credentials, and authentication middleware usually verifies an existing session or token. Keep those responsibilities distinct. Attaching a verified identity also does not authorize every operation that identity might attempt.

      Key takeaways

      • Derive the caller's identity from successful authentication, not a user ID supplied in the payload.
      • For ordinary creation, use that verified identity as the owner after authorization.
      • Acting on behalf of another user requires its own permission check.
      • Registration, login, authentication and authorization are related but separate operations.

      Request IDs, deadlines and cancellation

      Follow a request across logs and services

      Generate a request ID near the entry point and attach it to the context. Include it when logging handler, service and repository events. If the service calls another backend, propagate agreed correlation metadata, for example through X-Request-ID. This lets you connect events that belong to the same operation.

      Correlated events
      req-7f21  POST /books          received
req-7f21  book service         authorized user-17
req-7f21  book repository      record created
req-7f21  POST /books          completed with 201

      A correlation ID is not an authentication credential. If clients supply IDs, validate their format and length or replace them before using them in logs. A full distributed tracing system also uses trace and span relationships to distinguish individual downstream calls.

      Bound the lifetime of work

      A deadline says when an operation should stop; cancellation signals that its result is no longer needed. Carry those signals into downstream database and network operations that support them. For example, a request with a two-second budget should not give each of three sequential dependencies a fresh two seconds after the previous one finishes.

      Cancellation is cooperative: code and drivers must observe it. It does not forcibly undo completed work or roll back an already committed write. Release associated timers and other resources when work ends. Go's context API provides parent/child propagation for these signals. Go deadlines and cancellation.

      Work that intentionally outlives the request needs an explicit lifecycle, often a queued job with its own timeout and failure handling. Pass only the metadata it needs instead of retaining an entire HTTP request and its short-lived context.

      Key takeaways

      • A request ID connects logs and downstream activity; it never proves identity or permission.
      • Propagate cancellation and the remaining time budget to operations that support them.
      • Cancellation is cooperative and does not undo committed side effects.
      • Background jobs need their own lifetime, context and error handling.

      Putting the pieces together

      Imagine a signed-in user creating a book. This one example combines all three topics, while keeping each responsibility visible:

      1. EntryEstablish the request pipeline

        Assign a request ID, start timing, apply applicable limits and prepare response policies. The router selects the protected POST /books operation.

      2. MiddlewareEstablish identity and usable input

        Verify credentials and attach the principal to context. Decode the size-limited body before its fields are consumed. Failures stop here.

      3. HandlerTranslate HTTP into a service call

        Validate the book name and other accepted fields, apply defaults, and pass the input plus the verified actor to the create-book service.

      4. ServiceApply the use case

        Check the actor's permissions and relevant business limits. Coordinate persistence and any follow-up work according to the operation's transaction and retry requirements.

      5. RepositoryWrite the record

        Use the authorized owner ID and book data in a safe database operation. Return the created result to the service, which returns the public application result.

      6. ResponseComplete the HTTP lifecycle

        The handler sends 201 with the intended public fields. Logging records the outcome and duration under the request ID. Errors follow the configured error-handling path.

      Check your understanding

      • Where does an invalid sort value fail? At boundary validation, before the service uses it.
      • Where does “this user cannot edit that book” belong? In authorization for that resource, commonly in the service.
      • Who builds the database query? The repository.
      • Can middleware prevent the handler from running? Yes, by ending the request early.
      • Where does the trusted owner ID come from? The verified principal, carried through request context.
      • Does an error handler always go last? Its placement follows the framework's execution model.

      Key takeaways

      • Handler: bind and validate input, call a service, return an HTTP response.
      • Service: enforce business rules and permissions, then coordinate operations.
      • Repository: perform focused persistence operations with predictable results.
      • Middleware: reuse shared processing in a deliberate order, with early exits and error handling.
      • Context: carry verified identity, correlation metadata and cancellation for one request.
