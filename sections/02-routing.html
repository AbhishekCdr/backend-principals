    Lesson 02

    Routing

    HTTP methods express the what of a request — your intent. Routing expresses the where. Put the two together and the server has enough to pick exactly one piece of code to run. That mapping is all routing is.

    method + path static routes path params query params nesting versioning catch-all

    What routing is

    In Lesson 01 we said the method describes intent: fetch data, add data, update data, delete data. But intent alone is not actionable. You also have to tell the server where — which resource you want to perform that action on.

    Take a request with method GET and path /users. The action is “fetch”; the resource is “users”. The server takes those two things together, maps them to a particular handler, runs whatever business logic and database work that handler contains, and returns an array of users.

    The one-line definition

    Routing is mapping URL parameters to server-side logic. That is genuinely all there is to it — everything else in this lesson is variations on how you write the left-hand side of that mapping.

    The method and the path form a compound key

    Look at two requests to the same address:

    Two requests, one path
    GET  /api/books HTTP/1.1   ← fetch the list of books
POST /api/books HTTP/1.1   ← create a book

    The path is identical. What differs is the method. Inside the server, the method and the route are concatenated into a single key which maps to one handler. So GET /api/books and POST /api/books are two entirely distinct routes that can never collide — the method disambiguates them.

    MethodPathHandler does
    GET /api/books Authenticate if needed, read the books, return them.
    POST /api/books Create a book from the request body, then return the collection.

    Key takeaways

    • Method = what. Route = where. Together they select the handler.
    • (method, path) is a compound key, so the same path can host many routes.

    Static routes

    /api/books is a static route — there are no variable parameters anywhere in it. The string never changes. You use exactly /api/books every time you make the request, and it always returns the same kind of response. A constant.

    Dynamic routes and path parameters

    Now the opposite case. Suppose you want to fetch the details of one specific user, identified by their ID.

    Request
    GET /api/users/123 HTTP/1.1

    The server extracts 123 from the path and does whatever it needs to — fetch that user from the database, return their details. On the server side, the route declaration looks roughly like this, in any language or framework:

    Route declaration — pseudocode
    router.get("/api/users/:id", handler)
       ^^^         ^^^^
       method      dynamic segment

    The server is saying: any request whose method is GET and whose path is /api/users/ followed by any string, route to this handler. The :id colon convention marks a dynamic parameter, and you will find it in Java, Python, Node, Go and Rust alike — it is an industry-wide convention rather than a rule of HTTP.

    When GET /api/users/123 arrives, matching proceeds segment by segment: /api matches, /users matches, and 123 drops into the :id slot.

    Everything in a path is a string

    123 looks like a number, but in route paths numbers and special characters alike arrive as strings. Convert deliberately on the server.

    Read it out loud

    GET /api/users/123 reads as: “fetch me some data — the data lives under users — specifically the user whose ID is 123.” That readability is the entire point of REST-style APIs: the URL is a human-readable construct.

    Terminology: :id here is a path parameter (equivalently a route parameter). They are called path parameters because they sit directly after a forward slash — they are part of the path itself.

    Query parameters

    The second, easily confused kind of parameter. Consider a search request:

    Request with a query string
    GET /api/search?query=some+value HTTP/1.1
    ^^^^^^^^^^^ ^^^^^ ^^^^^^^^^^
    path        key   value

    Everything after the ? is the query string, made up of key–value pairs. The path before it is still what the server uses (with the method) to pick a handler.

    Why they exist

    POST and PUT requests have a body — a container for sending arbitrary client-defined values. GET requests, in REST, do not. So how does a GET send values?

    You could try to use path parameters. Technically /api/search/some+value works. But path parameters serve a specific purpose: they carry semantic meaning. /api/users/123 means “the user with ID 123”; the segment identifies a resource. A free-text search term is not a resource identifier. Stuffing it into the path is hard to maintain and defeats the point of a semantic URL.

    The division of labour

    Path parameters identify a resource. Query parameters describe how you want it — metadata about the request: search terms, filters, sort order, pagination.

    The canonical example: pagination

    Say /api/books returns a paginated list. The first request needs no query parameters at all — the server applies its defaults:

    Response with pagination metadata
    {
  "data": [ /* 20 books */ ],
  "meta": {
    "total": 100,
    "limit": 20,
    "currentPage": 1,
    "totalPages": 5
  }
}

    The server sent a chunk of 20 and told the client everything it needs to ask for more: 100 books in total, currently on page 1, 5 pages in all. The client uses that metadata to build the next request:

    Asking for page two
    GET /api/books?page=2&limit=20 HTTP/1.1

    Same route, same handler, different slice of data — and no request body needed. Beyond pagination, the usual residents of the query string are filters, sort fields and sort direction (ascending or descending). Anything that is a preference about the response rather than an identity of a resource.

    Key takeaways

    • Path params sit in the path after a slash and identify a resource: /users/:id.
    • Query params sit after ? as key–value pairs and modify the request.
    • They exist because GET has no body.
    • Pagination, filtering and sorting belong in the query string.

    Nested routes

    Nesting is not really a separate type of routing — it is a practice you will see everywhere, because expressing semantics in REST APIs pushes you towards nesting resources.

    A nested route
    GET /api/users/123/posts/456 HTTP/1.1
    ^^^^^^^^^^ ^^^ ^^^^^ ^^^
    static     param nested param

    Read it as a sentence: “of the user with ID 123, fetch their posts, and specifically the post with ID 456.” The value of nesting is that each level you stop at is itself a distinct route with distinct meaning.

    RouteKindHandler returns
    /api/users Static All users.
    /api/users/123 + one path param The details of user 123.
    /api/users/123/posts + nested resource All posts belonging to user 123.
    /api/users/123/posts/456 + second path param One specific post of user 123.

    Four different routes, four different handlers, four different responses — all built out of the same vocabulary. You will see nesting in essentially any API of more than trivial complexity.

    Route versioning and deprecation

    Notice the v1 in a path like /api/v1/products. That is route versioning, and it is standard practice in REST APIs.

    Consider two versions of the same endpoint:

    GET /api/v1/products

    {
  "data": [
    { "id": 1, "name": "Desk", "price": 210 }
  ]
}

    GET /api/v2/products

    {
  "data": [
    { "id": 1, "title": "Desk", "price": 210 }
  ]
}

    A trivial example — name became title — but the mechanism is what matters. Suppose you were serving a web app, and later you also have to serve a React Native or Flutter client that needs a different response shape. Your options:

    • Change the route — invent /api/new-products. Works, but now your URL space is a graveyard of adjectives.
    • Bump the version — keep the route, serve the new shape under v2. Your intent is explicit: v1 responds like this, v2 responds like that.

    How deprecation actually plays out

    1. Ship v2 goes live alongside v1

      Both versions serve traffic. Nothing breaks.

    2. Announce v1 is deprecated

      Front-end engineers and third-party consumers are told: v1 goes away after this release. They now have a defined migration window.

    3. Migrate Clients move to v2 at their own pace

      Each team migrates within the window rather than in an emergency.

    4. Retire v1 is removed

      Eventually you drop v1 entirely, and v2 becomes the baseline.

    What versioning really buys you

    A stable, repeatable workflow for shipping breaking changes to an API without breaking anybody — and a window in which your consumers can migrate on their own schedule.

    The catch-all route

    Finally: what happens when a request arrives for a route the server does not serve? Say GET /api/v3/products, and there is no v3. There is no handler; nothing caters to that path.

    The convention is that after registering every real route, the server registers a wildcard — * — last. Anything that has fallen through every other match lands there, and that handler returns a friendly message.

    Registration order matters
    router.get("/api/v1/products", ...)
router.get("/api/v2/products", ...)
router.get("/api/users/:id",   ...)
// ... all real routes first ...
router.all("*", notFoundHandler)   ← last: catches the leftovers
    Catch-all response
    HTTP/1.1 404 Not Found
Content-Type: application/json

{ "error": "Route not found",
  "message": "GET /api/v3/products is not a route on this server" }

    Without it, the default behaviour is an empty or null response — unhelpful to whoever is debugging. With it, the client is told plainly that this endpoint does not exist.

    Key takeaways

    • Nesting expresses ownership; every level you stop at is its own route.
    • Version in the path (/api/v1/) so breaking changes get a migration window.
    • Register the * catch-all last, and return a real message instead of null.
    • With static routes, path params, query params, nesting and versioning you can read the routing layer of essentially any backend codebase.
