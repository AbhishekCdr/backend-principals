      Lesson 16

      Backend Security

      Follow data across trust boundaries, challenge assumptions and enforce access deliberately. Security comes from consistent safeguards throughout the system, supported by testing and maintenance.

      Think in boundaries and assumptions

      A backend receives input, queries databases, calls services and returns data to browsers. Each interaction crosses a boundary with different rules. A browser field is not a trustworthy identity, a valid login is not permission to read every record, and a string intended as data can become executable syntax when inserted into another language.

      An attacker can call an API directly, change identifiers, add fields the UI never sends and repeat requests in unexpected orders. Frontend validation, hidden buttons and an obscure admin URL do not restrict those requests. Instead of assuming the happy path, ask three questions:

      1. What boundary is this data crossing? A language, user, tenant, privilege level or service boundary?
      2. Which assumption makes this operation safe? Type, identity, ownership, freshness, size or allowed destination?
      3. Where is that assumption enforced? By the server, at every relevant point of use, with a safe failure path?

      This lesson focuses on application security while recognizing its dependencies on browser, network and operating-system controls. Validation, authorization, safe APIs, least privilege and monitoring complement one another. No checklist or framework guarantees complete security, and no fixed percentage describes how many vulnerabilities a mindset alone prevents.

      Key takeaways

      • Treat client input and client behavior as untrusted, even when your own frontend normally sends them.
      • Identify the boundary, the safety assumption and the server-side control enforcing it.
      • Combine safeguards and maintain them as the application changes.

      SQL injection: keep syntax separate from values

      Injection occurs when untrusted data changes the instructions interpreted by another system. In SQL injection, string concatenation can let a supplied value change a query's structure. Consider a user lookup where the developer inserts an email between quotes:

      Illustrative vulnerable query construction — do not use
      query = "SELECT id, email FROM users WHERE email = '" + email + "'"

Ordinary input:
  alice@example.test

Result:
  SELECT id, email FROM users WHERE email = 'alice@example.test'

Input that changes the predicate:
  ' OR '1'='1' --

Result:
  SELECT id, email FROM users WHERE email = '' OR '1'='1' --'

      The supplied quote ends the string literal, the OR condition is always true, and the comment removes the trailing quote from consideration. In this example the database returns every row. What an attacker actually receives depends on the application's response handling and database permissions. This lookup alone does not prove a login bypass: correct authentication must still verify the password. It does demonstrate that user input has taken control of SQL syntax.

      Parameterized lookup — PostgreSQL-style placeholders, API pseudocode
      statement = "SELECT id, email, password_hash FROM users WHERE email = $1"
user = database.query(statement, [validatedEmail])

verify the submitted password using the password-hashing library
return only the application's allowed response fields

      Bind values through the driver's parameter API. The value is handled as data, not reparsed as SQL syntax; this is not equivalent to manually inserting escaped text. Placeholder syntax varies by driver. Parameters usually cannot stand for table names, column names or sort directions, so choose those from a server-controlled allowlist. ORMs also require care around raw SQL escape hatches. See OWASP's SQL injection defenses.

      Validation remains useful, but banning apostrophes is not a SQL injection defense: legitimate names contain them. A NOT NULL constraint also does not reject an empty string. Blocking multiple SQL statements does not prevent attacks that change a single statement. Give the application only required database privileges and use a separate migration role; losing CREATE or DROP privileges limits damage but does not make unrestricted reads or deletes safe.

      Key takeaways

      • Use bound parameters for values; choose dynamic SQL identifiers and directions from allowlists.
      • Validation, ORM use and multiple-statement restrictions do not replace safe query construction.
      • Limit database permissions and return only intended fields.

      NoSQL injection and unexpected query structure

      A document database can also interpret untrusted input as instructions. A MongoDB query field may accept an operator object as well as a string. If an endpoint expects an email but accepts arbitrary JSON, a value such as {"$ne": null} can change equality into an operator expression when passed through to a query.

      Build the filter yourself — conceptual validation flow
      accept a request containing only the documented fields
require email to be a string with the expected format and bounded length
reject arrays and objects where a scalar email is required
construct the filter as { email: validatedEmail }
execute the fixed filter through the database driver

      Validate types and structure before constructing a query. Do not pass a request body directly as a database filter or update document. Likewise, accepting every supplied property can let users set server-owned fields such as roles or tenant ownership, a problem often called mass assignment. Map explicitly allowed fields into the operation.

      SQL and NoSQL both need these boundaries. A database category is neither a security guarantee nor an inherent reason an application is insecure. See OWASP's NoSQL guidance and the earlier validation lesson.

      Key takeaways

      • Validate scalar types before inserting values into document-database filters.
      • Keep operators, query structure and writable fields under server control.
      • NoSQL avoids SQL syntax, not injection or access-control risks.

      Command injection and argument injection

      A media-processing service might invoke FFmpeg after an upload. If it constructs a shell command by concatenating an uploaded filename, shell punctuation in that filename can alter the command. Pipes, command substitution and command separators have meaning to a shell; the same characters are ordinarily just data in a filename argument passed directly to a process.

      Prefer an application library when it removes the need to launch a command. Otherwise use a fixed executable and an API that accepts an argument array without invoking a shell. Keep executable selection and options under application control. See OWASP's command injection defenses.

      No shell is only part of the boundary

      A program can still interpret a supplied argument as an option, path, URL or special input format. Argument arrays prevent shell parsing; they do not make every argument harmless. Validate the called tool's inputs, use an end-of-options delimiter where supported, and generate storage paths rather than trusting uploaded filenames.

      Restrict processing to owned directories and supported formats, limit file size, dimensions, execution time and resources, and run with minimal privileges. Handling a file normally uses filesystem APIs, not shell commands; do not introduce a shell merely to open, rename or delete it.

      Key takeaways

      • Prefer library APIs; otherwise invoke a fixed executable with arguments and no shell.
      • Validate argument meaning as well as separating arguments from command syntax.
      • Constrain paths, processing resources and operating-system privileges.

      Authentication is a whole lifecycle

      Authentication establishes who is making a request. Production authentication also includes account creation, verification, recovery, session expiration, device management, multifactor authentication and revocation. A login form and a token-signing function cover only part of that lifecycle.

      A maintained authentication framework or provider can reduce implementation and maintenance work. Choose based on requirements, operational ownership, integration, cost and migration constraints. A provider does not automatically enforce your application's resource permissions or make unsafe integration code secure. Avoid inventing cryptography or assuming generated authentication code has already been security-reviewed.

      Social sign-in commonly uses OpenID Connect on top of OAuth 2.0. OAuth is an authorization framework; OpenID Connect defines an identity layer. Validate the configured issuer, audience, protocol state and tokens through the provider's supported integration. Identify an external identity using its trusted issuer and subject, not a client-supplied email alone. See OpenID Connect Core.

      Account linking deserves special care: matching email text does not prove ownership of both accounts. Use a deliberate linking flow that verifies control of the relevant identities. Password reset and email-change flows must not provide easier account takeover paths than login. Prefer generic credential-error messages that avoid revealing whether an account exists, and add reauthentication or MFA for sensitive changes. See OWASP's authentication guidance.

      Key takeaways

      • Authentication includes recovery, linking, session management and revocation, not just login.
      • Use maintained components and still verify their integration and your own authorization.
      • Do not link identities solely because their email strings match.

      Password hashes, salts and offline guessing

      Store a password verifier, not the password itself. Plaintext storage exposes credentials to anyone who obtains database access, including through backups or excessive internal privileges. Password reuse can turn one application's breach into account takeover elsewhere.

      A password-hashing function derives a value from a password, salt and cost parameters. Verification tests a candidate against that stored value. There is no decryption step, but one-way hashing does not stop guessing: an attacker can hash candidate passwords and compare the results. A leaked hash is therefore still sensitive.

      ProtectionWhat it changesWhat it does not solve
      HashingThe database need not store recoverable plaintext passwords.Attackers can still test guesses.
      A fresh random salt for each password hashEqual passwords normally produce different stored verifiers; reusable precomputed tables become ineffective.The salt is not secret and does not prevent per-user guessing.
      A suitable work factorEach guess consumes more time and, for memory-hard algorithms, memory.Weak passwords remain guessable; hardware and parallelism still matter.

      Use a maintained password-hashing library's hash and verify APIs. These normally generate and encode the salt with the algorithm, parameters and verifier. Do not manually concatenate a salt, invent a storage scheme, or generate a new independent salt and compare two encoded hashes at login. The verify API uses the parameters embedded in the stored record. This is why repeated hashing of the same password can legitimately produce different encoded records.

      A rainbow table is a particular precomputation technique, not simply a name for every password dictionary. Salted password hashing blocks reuse of generic precomputed results; it does not make recovery of a weak password impossible. See OWASP's password storage guidance.

      Key takeaways

      • Store salted password verifiers through a maintained password-hashing library.
      • Salts prevent reusable precomputation, while work factors make individual guesses more expensive.
      • Hashes can still be cracked by guessing; use the library's verify API at login.

      Choose and tune password-hashing costs

      General-purpose fast hashes such as plain SHA-256 are unsuitable password verifiers. MD5 is also unsuitable and has additional cryptographic weaknesses. Password-specific algorithms deliberately impose a cost on each guess.

      OWASP recommends Argon2id for new password storage, with a listed minimum configuration of 19 MiB memory, two iterations and parallelism one. Its guidance includes scrypt when Argon2id is unavailable, bcrypt for legacy systems and PBKDF2 for appropriate compliance requirements. Treat these as a starting point and consult the current algorithm guidance when implementing or upgrading storage.

      Benchmark on deployment hardware under expected concurrent login load. Parameters control resource use; they do not promise an exact 400-millisecond duration on every machine. Nor does a 400-millisecond server check limit an attacker to a few guesses per second across all their hardware. Memory cost, parallelism, password strength and the attacker's budget change that calculation.

      Store the chosen parameters with each verifier and upgrade older records after a successful login when appropriate. Apply documented input limits without silently truncating passwords; legacy bcrypt implementations have important length limitations. Online throttling protects your authentication service, while expensive verifiers protect against offline attacks on a stolen database. Neither substitutes for the other.

      Key takeaways

      • Use password-specific hashing, with Argon2id as the current OWASP preference for new systems.
      • Benchmark memory and CPU costs under concurrency; do not promise fixed cracking times.
      • Upgrade stored parameters and combine offline resistance with online abuse controls.

      Server-side sessions

      After successful authentication, a server-side session lets the client present an opaque credential instead of resending its password. The server maps that credential to the user, expiration and revocation state in a database or shared session store.

      1. Generate an unpredictable session token with a cryptographically secure random generator.
      2. Store its association with the authenticated user and the required lifetime metadata.
      3. Deliver it through the application's protected credential transport, commonly a cookie.
      4. Validate the session on each protected request and obtain the user identity from that trusted lookup.

      Measure randomness in bits of entropy, not character count. For example, 32 uniformly random bytes provide 256 bits and occupy 64 characters when hex-encoded. Padding a predictable identifier does not add entropy. Use the session framework's supported generator and configuration. IP addresses and user-agent strings can assist risk detection or device displays, but neither proves identity and both can change.

      Regenerate session identifiers after login and privilege changes to prevent session fixation. Enforce server-side idle and absolute expirations, invalidate sessions on logout or compromise, and keep any replicated or cached revocation state consistent with the promised revocation delay. Multiple application instances can share a session store; horizontal scaling does not require JWTs. See OWASP's session management guidance.

      Key takeaways

      • A session token is a bearer credential: generate it securely and validate its server-side state.
      • Entropy is measured in bits; token length alone does not establish unpredictability.
      • Rotate identifiers at authentication boundaries and enforce expiration and revocation.

      Cookies, sites and origins

      Cookies are a browser credential transport, not a session architecture. They can carry an opaque session token or a JWT. For a typical first-party session, a deliberately configured cookie might have the following shape; the value below represents a generated token.

      Illustrative first-party session cookie
      Set-Cookie: __Host-session=GENERATED_SESSION_TOKEN; Path=/; Secure; HttpOnly; SameSite=Lax
      AttributeProtection or behavior
      HttpOnlyPrevents JavaScript from reading the cookie. It does not stop scripts from making authenticated requests.
      SecureRestricts transmission to HTTPS in normal production use.
      SameSite=StrictExcludes the cookie from cross-site requests, including an initial navigation from another site.
      SameSite=LaxAlso permits cross-site top-level navigations using safe methods, such as following a GET link.
      SameSite=NoneAllows cross-site use subject to browser policy; requires Secure.
      __Host- prefixRequires Secure, Path=/ and no Domain attribute in supporting browsers, restricting the cookie to its host.

      Site and origin differ. An origin includes scheme, hostname and port. A site normally combines scheme and registrable domain. Thus https://app.example.test and https://api.example.test are different origins but the same site. SameSite is not a rule that only your exact frontend origin may send requests.

      Choose cookie scope and SameSite behavior for the actual deployment and login redirects. None can be necessary for legitimate cross-site integrations; it needs appropriate CSRF defenses, and browsers may still restrict third-party cookies. Lax does not enable cross-site fetch requests merely because frontend and backend are on different sites. Set attributes explicitly rather than relying on browser defaults. See MDN's Set-Cookie reference.

      Key takeaways

      • Use Secure and HttpOnly for browser session cookies, with deliberate scope and SameSite settings.
      • Same-site and same-origin are different boundaries.
      • HttpOnly reduces token theft through JavaScript but does not neutralize XSS or CSRF.

      JWTs: decode, verify and authorize separately

      A common signed JWT has three base64url-encoded components separated by dots: a header, a claims payload and a signature or MAC. Other JWT representations exist, including encrypted tokens. A normal signed JWT is not encrypted; its payload is readable by anyone holding the token. Store only claims the recipient needs. See the JWT specification.

      ClaimMeaning and validation concern
      subSubject identifier, interpreted in the trusted issuer's identity space.
      iss / audIssuer and intended audience; ensure the token was issued by the expected authority for this service.
      expExpiration time; require and enforce it for expiring authentication tokens.
      nbfEarliest valid time, when present.
      iatIssuance time. It does not by itself define or enforce expiration.

      Decoding only reads the content. Verification must use an explicitly allowed algorithm and a trusted key, then enforce the required claims, token purpose and lifetime. Do not let an untrusted token choose an arbitrary algorithm or key source. Symmetric algorithms use a shared secret; asymmetric algorithms use a private signing key and public verification key. Follow JWT best current practices through a maintained library.

      A valid signature establishes integrity and authenticity under that key; it does not prove every claim is appropriate for this endpoint or still current. An old admin claim may outlive a role change. Continue to enforce resource authorization and the application's revocation policy. A JWT is a token format: systems using JWTs can still keep server-side state.

      Key takeaways

      • Decoding a JWT is not verification, and signing does not hide its payload.
      • Validate algorithms, trusted keys, issuer, audience, token purpose and expiration.
      • Verified claims still need authorization and a strategy for changed permissions or revoked access.

      Revocation, refresh tokens and browser storage

      A self-contained access token can remain valid until expiration even after the user logs out or loses a permission. Deleting the browser's copy does not invalidate a stolen copy. Immediate revocation requires an additional mechanism, such as a server-side session, token denylist, account version check or token introspection. Define the maximum delay your system permits.

      Short-lived access tokens reduce the exposure window. A refresh token lets an authorized client obtain replacements, but it is itself a valuable credential. Protect it in transit and storage, keep revocable server-side grant state, and use a supported replay-defense design. Rotation invalidates the old refresh token and retains its relationship to the replacement so reuse can trigger revocation. OAuth's security guidance requires rotation or sender constraint for public-client refresh tokens. See RFC 9700.

      Browser storageMain tradeoff
      localStorage or sessionStorageAccessible to same-origin JavaScript, including injected scripts. They are not secure vaults for long-lived bearer credentials.
      JavaScript memoryAvoids persistence across reloads but remains exposed to compromised code in the running application.
      HttpOnly cookieRestricts JavaScript reads, but automatic cookie transmission requires CSRF defenses.
      Server-held tokens behind a browser sessionReduces browser token exposure while requiring a server-side session and its operational controls.

      A stolen refresh token may obtain new access tokens; short access-token lifetime alone is not enough. Refresh rotation must also handle concurrent legitimate refreshes deliberately. Choose a maintained session or token flow that meets your clients' needs rather than assuming either stateful sessions or JWTs are universally superior.

      Key takeaways

      • Specify revocation behavior explicitly; deleting a local token does not revoke stolen copies.
      • Protect refresh tokens, detect replay and retain revocable grant state.
      • Browser storage changes exposure to XSS and CSRF; it does not remove both risks.

      Rate limiting and account takeover defenses

      Login, recovery and verification endpoints need abuse controls. Brute force tries many passwords against an account; password spraying tries a small set across many accounts; credential stuffing reuses credentials leaked elsewhere. These patterns need overlapping defenses.

      ControlBenefitLimit to consider
      Per-IP throttlingRestricts concentrated traffic from one address.Many legitimate users can share an IP; attackers can distribute traffic.
      Per-account throttlingRestricts distributed guessing against one account.Rigid lockouts can let an attacker deny access to the account owner.
      Service-wide capacity controlsProtects expensive hashing and downstream resources.A single low global limit can block all legitimate logins during an attack.
      Risk-based challenges and MFAAdds friction or another proof for suspicious activity.Needs accessible recovery and does not replace ordinary rate controls.

      Set thresholds from expected traffic and risk rather than copying “five failures means a 24-hour lock.” Use bounded delays, appropriate challenges, alerts and recovery flows that do not disclose account existence. Where available, phishing-resistant authentication such as passkeys can reduce reliance on reusable passwords. See OWASP's automated-attack guidance.

      Distributed instances need coordinated counters where limits are meant to be shared. Trust forwarded client-IP headers only from configured trusted proxies; a client-supplied X-Forwarded-For value is not authoritative. Consider request size, concurrency and cost as well as request count, and return a consistent rate-limit response such as 429.

      Key takeaways

      • Combine IP, account and service-level controls for different abuse patterns.
      • Design lockouts and global limits so attackers cannot easily deny service to legitimate users.
      • Protect expensive work and use trusted proxy configuration when identifying clients.

      Object-level authorization and tenant isolation

      Authentication establishes an identity. Authorization decides whether that identity may perform this action on this resource. A permission such as “read invoices” does not necessarily allow reading every invoice. Changing /invoices/5 to another ID must never bypass the resource's access policy.

      Broken object-level authorization (BOLA) occurs when an application fails to enforce those resource permissions. Insecure direct object reference, or IDOR, describes a closely related access-control failure involving user-controlled references. Numeric IDs, UUIDs and strings all need authorization. See OWASP's BOLA explanation.

      Example policy: an owner may read their own invoice within an authorized tenant
      SELECT id, total, status
FROM invoices
WHERE id = $1
  AND tenant_id = $2
  AND owner_id = $3;

$1 = validated requested invoice ID
$2 = tenant verified through the authenticated user's membership
$3 = authenticated user ID from trusted server context

      This owner-only policy is an example, not a universal rule. Shared resources, organizational roles and delegated access need their own relationship checks. Centralize policy decisions, then enforce them at every access path. Query scoping, a service policy check and properly configured database row-level security are possible tools; the number of layers alone does not determine whether authorization is correct.

      Apply permissions to updates, deletes, exports, batch operations and related-object creation too. For a write, make the permission condition part of the mutation or otherwise protect against changes between checking and using the resource. Assign owner and tenant fields from authorized context instead of trusting them in the request body.

      A scoped lookup can return 404 for both missing and inaccessible records when hiding existence is part of the policy. A 403 is still appropriate when acknowledging existence is acceptable. Avoid inconsistent bodies or timing that undermine the intended concealment. Random identifiers can reduce easy enumeration, but changing integers to UUIDs never fixes missing authorization.

      Key takeaways

      • Authorize the particular action, object and tenant, not merely the route or login.
      • Enforce policy on reads and writes using trusted identity and membership context.
      • UUIDs and concealed error responses supplement access checks; neither replaces them.

      Function-level authorization and default denial

      Broken function-level authorization (BFLA) lets someone invoke an operation their identity should not be allowed to use. An admin page hidden from ordinary navigation still needs an enforced admin policy on its APIs. A user can discover or guess a URL and call it directly. See OWASP's BFLA guidance.

      Access-control failureExampleRequired boundary
      HorizontalA customer reads another customer's private invoice.Object ownership, sharing and tenant permissions.
      VerticalA customer invokes an administrator's refund or export function.Authority to perform the privileged operation.

      These categories are useful mental models, not mutually exclusive implementation layers. An admin role does not automatically grant global access: a tenant administrator may still be restricted to one organization. Express the intended authority clearly, through roles, capabilities, attributes or relationships rather than assuming all users with one role have the same scope.

      Adopt deny by default: an operation is forbidden unless policy explicitly allows it. Centralize the rules so they are reviewable, while enforcing them wherever access occurs, including alternate endpoints and background actions. A policy error must not silently become an allow decision. Changes to authorization require tests for both permitted and denied cases. See OWASP's authorization recommendations.

      Key takeaways

      • Hidden URLs and buttons do not protect privileged functions.
      • Check both operation privileges and resource scope, including for administrators.
      • Centralize policy, enforce it on every relevant path and deny unless explicitly allowed.

      XSS: untrusted content becomes browser code

      Cross-site scripting, or XSS, lets attacker-controlled content execute in the context of a trusted application. That code can read accessible page data, modify what the user sees, make authenticated requests or steal JavaScript-accessible credentials. HttpOnly cookies restrict direct cookie reads but do not prevent those authenticated actions.

      TermWhat it describesExample
      Stored XSSAttack content persists and reaches later viewers.A saved comment is rendered as unsafe HTML.
      Reflected XSSAttack content arrives in a request and is reflected unsafely into a response.A search term becomes executable page markup.
      DOM-based XSSClient-side code moves untrusted data into a dangerous browser sink.A URL fragment is assigned to an HTML-parsing API.

      Persistence and execution location are different dimensions, so these descriptions can overlap. A Markdown discussion board illustrates the risk: a user writes content, the system stores it, a renderer creates HTML, and other users' browsers parse the result. Raw HTML features, unsafe links or plugins can introduce executable behavior unless the rendering pipeline controls them.

      Removing literal script tags is insufficient. Event-handler attributes and dangerous URL contexts are among the other ways content can become active. Script elements inserted through some APIs may be inert, but that does not make arbitrary innerHTML safe. Understand the actual browser sink and use the corresponding defense. See OWASP's XSS prevention guidance.

      Key takeaways

      • XSS executes attacker-controlled code with the application's browser privileges.
      • Stored, reflected and DOM-based describe related ways unsafe content reaches execution.
      • HttpOnly cookies and removal of script tags do not eliminate XSS.

      Render safely and add a content security policy

      Choose the defense for the output context. Ordinary text should remain text: use the framework's escaped text rendering or a suitable text sink. An HTML attribute, a URL and a JavaScript expression are different contexts; a generic “sanitize input” function cannot safely cover all of them.

      Plain text belongs in an ordinary element's text content
      commentElement.textContent = userComment;

      When rich HTML is actually required, use a maintained allowlist-based sanitizer with a deliberate tag, attribute and URL policy. For Markdown, review raw HTML support and plugins, and sanitize the final generated HTML before an unsafe rendering sink. Do not modify sanitized output in ways that restore dangerous markup. React's dangerouslySetInnerHTML bypasses normal text escaping; it does not sanitize the supplied HTML. See OWASP's sanitization guidance.

      Sanitizing content at ingestion may be useful, but does not permanently make that stored value safe in every future output context. Maintain the rendering boundary and keep sanitizers and renderers updated. Storing raw text is not itself XSS; rendering it through an unsafe path is the problem.

      Content Security Policy (CSP) adds browser-enforced restrictions on script and resource loading. A carefully configured policy can block many injection paths. Nonce-based policies need unpredictable nonces generated for each response and applied only to trusted scripts; hash-based policies allow specified script contents. Avoid weakening the policy with broad allowances just to silence violations. Report-only rollout helps find compatibility issues but does not block anything. See OWASP's CSP guidance.

      Key takeaways

      • Use escaped text for plain content and a maintained sanitizer when rich HTML is required.
      • Match defenses to the final output context, including Markdown plugins and raw-HTML rendering.
      • CSP is an additional containment layer; report-only policies do not enforce restrictions.

      CSRF: a credential is not proof of intent

      Cross-site request forgery tricks a browser into making an unwanted request using credentials it attaches automatically. For example, a user is logged into a service and visits another page that submits a form to it. If the browser attaches the session cookie and the server accepts the request without checking its intent, a state-changing operation may succeed. The attacker need not read the response.

      CSRF still matters for modern cookie-authenticated applications. Framework protections can help only when enabled and correctly integrated. SameSite reduces exposure, but “Lax means immune” is incorrect: unsafe state changes behind GET endpoints and untrusted same-site subdomains are examples of remaining risk.

      • Keep GET and other safe methods free of requested state-changing actions.
      • Use the framework's supported CSRF protection on state-changing endpoints, typically a session-bound synchronizer token or an appropriately signed, session-bound double-submit design.
      • Check allowed request origins using a deliberate Origin/Referer policy, including how missing headers and trusted proxies are handled.
      • Configure SameSite and cookie scope as additional controls; Fetch Metadata checks can further restrict unwanted browser request contexts.
      • For sensitive actions, require appropriate reauthentication or explicit transaction confirmation.

      CSRF tokens must be validated by the server, not merely included in forms. A design using authorization headers that the browser does not automatically attach changes the CSRF threat, but cookie-based refresh or login endpoints still need consideration. XSS can often defeat CSRF controls by executing within the trusted application. See OWASP's CSRF prevention guidance.

      Key takeaways

      • CSRF exploits automatically attached credentials; the attacker may never need the response.
      • Use supported CSRF protection, origin checks and deliberate cookie settings.
      • Modern frameworks and SameSite defaults do not justify ignoring CSRF.

      CORS governs browser response access

      Cross-Origin Resource Sharing lets a server tell a browser which origins may read certain responses. It is a browser security mechanism, not user authentication or a firewall that ensures every request came from your frontend.

      Some cross-origin requests are sent without a preflight, including eligible form submissions. If CORS response headers are absent, the browser may still have sent the request and the server may already have performed its side effects; the script is prevented from reading the response. Other requests require a successful preflight before the actual request is sent.

      Use an explicit allowlist of trusted origins for credentialed access. Do not blindly reflect any supplied Origin or assume a wildcard supports credentialed response access. Direct HTTP clients do not enforce browser CORS rules. Continue to authenticate, authorize and defend state-changing actions on the server. See MDN's CORS guide.

      Key takeaways

      • CORS controls browser access to responses; it does not authenticate callers.
      • A browser-blocked response does not mean the request never reached the server.
      • Use deliberate origin allowlists and independent authorization and CSRF defenses.

      Secrets, logs and security headers

      Misconfiguration can undermine otherwise correct code. Keep secrets out of source control, frontend bundles, images and diagnostic output. Use protected deployment configuration or a secret manager with least-privilege access. Environment variables are a delivery mechanism, not automatic encryption or protection against process access and accidental logging.

      If a credential enters a repository, revoke or rotate it promptly and investigate its exposure. Deleting the latest file does not remove copies in history, forks or logs. Validate required security configuration at startup and fail safely when it is missing. See configuration and secret management.

      Disable public debug interfaces and detailed exception responses in production. Log severity is not a redaction mechanism: secrets are unsafe at info level too. Keep passwords, bearer tokens, API keys and unnecessary personal data out of every log level. Restricted diagnostic logs may contain carefully handled stack traces; client responses should not expose them. Use safe error responses and controlled telemetry access and retention.

      Response policyWhat it helps control
      Content-Security-PolicyPermitted scripts and other browser resource behavior.
      CSP frame-ancestorsWhich ancestors may embed a page, reducing clickjacking exposure.
      X-Frame-OptionsAn older framing restriction, useful where appropriate alongside a compatible policy.
      Strict-Transport-SecurityDirects browsers to use HTTPS for the configured host policy; plan rollout and subdomain scope carefully.
      X-Content-Type-Options: nosniffRestricts MIME sniffing; also serve correct content types.
      Referrer-PolicyControls how much referrer information leaves a page.

      Clickjacking tricks users into interacting with an embedded interface. Embedding alone does not grant the outer page unrestricted access to a cross-origin frame's contents. Use the appropriate framing policy rather than relying on hidden URLs. Security middleware can provide useful defaults, but configure them for the application and verify actual responses through proxies. See OWASP's HTTP header guidance.

      Key takeaways

      • Protect secrets throughout their lifecycle and rotate exposed credentials.
      • Disable public debugging and redact sensitive data at every log level.
      • Configure and verify browser security headers for the application's actual deployment.

      Verify the boundaries and keep learning

      Review a request from entry to side effect: validate its shape, authenticate the caller, authorize the operation and resource, use safe database or process APIs, and render the result for its specific context. Valid input can still request an unauthorized action; a parameterized query can still expose another tenant's data. Each control has a different job.

      Automated scenarioRequired result
      User A requests or modifies user B's private objectNo unauthorized data or mutation, including through batch and export paths.
      A member invokes an admin function or changes tenant IDsOperation and tenant policies deny access.
      A query value contains punctuation or an unexpected objectIt remains bound data or fails schema validation; query structure stays fixed.
      A token is altered, expired, revoked or intended for another audienceAuthentication rejects it according to the configured policy.
      A comment contains active markupIt renders as intended safe content without executing attacker code.
      A state-changing cookie-authenticated request lacks valid CSRF proofThe server rejects it before changing state.
      A password or token appears in an error pathIt does not leak into responses or logs.

      Run relevant regression tests in CI and update them as policies change. Passing tests proves the covered cases, not the absence of every vulnerability. Review dependencies, framework defaults and configuration changes too. Test deployed browser behavior where cookies, CSP and CORS interact with the real frontend and proxy setup.

      Audit privileged actions, policy changes and suspicious patterns with actor, action, resource, result, timestamp and a correlation identifier. Protect audit access and integrity. A denied request is not automatically a confirmed breach: distinguish mistakes from repeated probing, and use actionable alerts with an incident-response path.

      Continue with the PortSwigger Web Security Academy for guided labs, the OWASP Top 10 for broad risk categories, and the OWASP Cheat Sheet Series for implementation guidance. Explore additional boundaries such as SSRF, file uploads, path traversal and dependency security as they become relevant to your application. Practice in dedicated labs or systems you are authorized to test.

      Key takeaways

      • Test denied actions, malformed input and security-state changes as deliberately as successful requests.
      • Use protected audit evidence and actionable alerts without treating every denial as a breach.
      • Maintain controls and tests over time; OWASP and PortSwigger provide deeper guidance and practice.
