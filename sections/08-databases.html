      Lesson 08

      Databases & PostgreSQL

      Backend data must survive restarts, remain valid and support many users at once. Learn how schemas, relationships, migrations and queries turn that requirement into a working persistence layer, then use indexes and triggers to support the operations your APIs need.

      Persistence, memory and storage

      Persistence means data survives the program that created it. A to-do app should still know which tasks are complete after the process stops and the user comes back. A variable in application memory alone cannot provide that guarantee.

      A database is an organized collection of data; a database management system (DBMS) is the software that manages it. Files and browser storage can provide persistence too, but they offer different lifetimes and guarantees. Session storage, for example, is scoped to a browser tab's session; browser-managed storage is not a substitute for the server's authoritative records.

      StorageStrengthTradeoff
      RAMFast access for active data.Usually volatile and more expensive per unit of capacity.
      SSD / HDDNon-volatile storage with greater affordable capacity.Access is generally slower than RAM; durability still depends on the system's write guarantees.

      This is not a strict divide between databases and caches. PostgreSQL uses memory buffers as well as persistent storage. Redis keeps its working data in memory and can also persist it using snapshots or an append-only file. Choose guarantees deliberately rather than assuming “cache means no persistence” or “database means every read touches disk.” Redis persistence options.

      Key takeaways

      • Persistence keeps data beyond the lifetime of the process that created it.
      • A database holds organized data; a DBMS manages storage and access.
      • Memory and disk work together; understand the actual durability guarantees of the chosen system.

      Why use a DBMS instead of a plain file?

      A file works for some small, single-writer workloads. You can give it a format and validate its contents in application code. As requirements grow, you also need efficient lookup, coordinated writes, access control, recovery and constraints. Implementing all of that yourself becomes a storage-system project.

      DBMS responsibilityWhat it provides
      Organization and accessStructures and query operations for finding and changing data.
      IntegrityTypes and constraints that reject invalid stored states.
      Concurrency and transactionsMechanisms to coordinate overlapping operations and commit related changes together.
      SecurityDatabase roles and permissions; application-level authorization is still required.
      Durability and recoveryMechanisms to preserve committed work and recover after failures, alongside a backup and restore strategy.

      The lost-update example

      Suppose an amount starts at 40. Two requests read 40 simultaneously. One adds 20 and writes 60; the other subtracts 20 and writes 20. A last-writer-wins workflow leaves either 20 or 60, although applying both changes should leave 40. Faster parsing does not fix this race.

      A database does not automatically make every read-then-write sequence correct. Use an atomic update such as SET amount = amount + $1, or an appropriate transaction with locking or a version check. A transaction groups work for commit or rollback; its isolation level and the statements inside determine how concurrent operations interact.

      Key takeaways

      • Files can hold structured data, but coordination, integrity, efficient access and recovery need additional machinery.
      • DBMS features reduce the amount of storage logic the application must implement.
      • Prevent lost updates deliberately with atomic operations, locks or version checks; simply using a database is not enough.

      Relational models, document models and PostgreSQL

      Relational databases model data in tables with rows, columns and declared constraints. Keys connect related records, and SQL expresses queries and changes. Document databases such as MongoDB organize records as documents in collections, often allowing more variation in shape. NoSQL also includes key-value, graph and other models; not every NoSQL system is a document database.

      Relational example

      A CRM has customers, contacts and sales opportunities. Relationships, constraints and joins make a relational model useful for these connected records.

      Document example

      A content platform has articles with different combinations of text, media and embedded blocks. A document model can fit those aggregates naturally.

      These are examples, not exclusive assignments. MongoDB supports schema validation, indexes and transactions; flexible schemas still need design. PostgreSQL can store structured columns alongside JSON documents. Neither database category guarantees accurate application data without the right rules. MongoDB schema validation.

      Why this lesson uses PostgreSQL

      PostgreSQL combines relational constraints, transactions, SQL, extensibility and strong JSON capabilities. It is an open-source DBMS and a useful system for learning these concepts. SQL is the language; PostgreSQL is the software executing it. Standard SQL helps portability, but types, functions, extensions and behavior differ across engines. Moving to MySQL or SQL Server is not automatically a small configuration change.

      Choose a database from access patterns, consistency needs, operations and team experience. JSON support alone does not make all document databases unnecessary. This lesson assumes basic familiarity with SELECT, INSERT, UPDATE and DELETE and concentrates on their use in a backend.

      Key takeaways

      • Relational tables and documents organize data differently; both benefit from explicit schema and integrity decisions.
      • PostgreSQL supports relational data and JSON; MongoDB can enforce document validation.
      • SQL knowledge transfers between engines, but database migrations between products require compatibility work.

      Numeric and text types

      Choose a type that describes the value, its valid range and the calculations it must support.

      TypeUse and behavior
      smallint2-byte signed integer, −32,768 to 32,767.
      integer4-byte signed integer, roughly ±2.1 billion.
      bigint8-byte signed integer for larger ranges. Preserve precision when exchanging it with clients.
      numeric(p, s) / decimal(p, s)Equivalent exact decimal types with a declared precision and scale.
      real / double precisionApproximate binary floating-point types, useful when that numerical model suits the computation.
      serial / bigserialSequence-backed shorthand for automatically supplied integer values, not a guarantee of gapless numbering.

      The range order is smallint < integer < bigint. A numeric(10, 2) allows eight digits before the decimal point and two after it; excess fractional precision is rounded and an out-of-range result fails. Binary floats cannot exactly represent many decimal fractions. Use exact decimal values, or a deliberately scaled integer model, for amounts requiring exact decimal arithmetic, and define rounding rules. PostgreSQL numeric types.

      For new sequential keys, identity columns make generation explicit, for example bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY. A sequence normally starts at 1, and rolled-back inserts can leave gaps. Identity generation and primary-key uniqueness are separate properties.

      Text length is a business rule, not a magic number

      TypeMeaning
      char(n)Fixed-length, space-padded character data.
      varchar(n)Variable-length text with a maximum character count.
      textVariable-length text without a declared length limit; implementation limits still exist.

      PostgreSQL has no general performance advantage for an arbitrary varchar(255) over text, and text columns can be indexed subject to index limits. Use a meaningful length constraint when the domain needs one, either through varchar or a CHECK on text. Keep important invariants in the database as well as validating requests. Character values have an implementation limit of about 1 GB, not unlimited storage. PostgreSQL character types.

      Key takeaways

      • Integer capacity increases from smallint to integer to bigint.
      • numeric and decimal are exact decimal types; floating-point values are approximations.
      • Generated IDs need a uniqueness constraint and can have gaps.
      • Use text or a meaningful length bound; 255 is not a universal optimization or domain rule.

      Time, UUIDs, JSON and other types

      TypeWhat it models
      booleantrue or false; SQL NULL is also possible unless prohibited.
      dateA calendar date, such as a task's due date.
      timeA time of day without a date.
      timestampA date and time without time-zone interpretation.
      timestamptzAn instant, normalized internally and displayed using the session time zone.
      intervalA span expressed with components such as months, days and time.
      uuidA UUID value, often used as a resource identifier.
      json / jsonbValidated JSON text or a decomposed representation suited to queries and indexing.
      Arrays, such as text[]Multiple values of a declared element type.
      inet, macaddr, geometric and XML typesSpecialized domains with their own supported operations.
      timestamptz does not keep the original zone

      It identifies an instant, not the original IANA zone name or input offset. Store a separate zone such as Asia/Kolkata when that information is part of the domain. Also, CURRENT_TIMESTAMP is the transaction start time; statement_timestamp() is the statement start time. Date/time types and current-time functions.

      A UUID is not an authorization mechanism. A caller who knows an ID still needs permission to read or change its resource. The schema below uses gen_random_uuid() to generate values and a primary key to enforce uniqueness.

      json preserves input text details; jsonb trades that preservation for a representation that supports efficient processing and indexing. jsonb does not retain whitespace, key order or duplicate object keys. Prefer it for many queryable document fields, but still define and validate their shape. Frequently joined or constrained attributes often belong in ordinary columns. PostgreSQL JSON types.

      Key takeaways

      • Use date for dates and timestamptz for instants; save a separate time-zone identifier when needed.
      • CURRENT_TIMESTAMP stays fixed within a transaction; statement_timestamp follows each statement.
      • UUIDs identify resources but do not authorize access.
      • jsonb supports flexible content and indexing without eliminating schema-design decisions.

      Migrations: version the schema

      A migration is an ordered, version-controlled change to the database. Instead of making untracked edits in a graphical client, put table, constraint, index and trigger changes into files reviewed alongside application code. A migration runner records applied versions so it can apply pending changes rather than replaying every CREATE statement.

      Example project layout
      db/
  migrations/
    20261003090000_create_project_schema.sql
    20261003091000_add_query_indexes.sql
    20261003092000_maintain_updated_at.sql
  seeds/
    development.sql

      With dbmate, dbmate new create_project_schema creates a timestamped migration; dbmate up applies pending migrations. A DATABASE_URL configures the target database. Keep credentials out of version control and verify the target before running changes. dbmate uses schema_migrations to record applied versions, not merely a guess based on the newest filename. dbmate documentation.

      Up and down have limits

      An up migration applies a change; a down migration may reverse its structure. Dropping a populated table and recreating it does not restore the lost rows. A rollback script is not a backup. Some teams use forward fixes in production and reserve destructive downs for disposable environments.

      Apply new changes in new files after a migration is shared or deployed. Test on representative data, consider locks and table rewrites, and keep old and new application versions compatible during rollout. Large backfills may need a separate controlled job. A GUI such as TablePlus is useful for exploration; the reviewed migration remains the repeatable schema change.

      Key takeaways

      • Version schema changes as ordered files and let a migration runner track applied versions.
      • Add a new migration for a new change; avoid rewriting deployed history.
      • Down migrations can undo structure, but cannot magically recover deleted data.
      • Review deployment compatibility, locking, target environment and recovery before applying changes.

      Constraints and enums: make invalid states harder to store

      ConstraintWhat it enforces
      PRIMARY KEYUnique, non-null identification of a row, using one column or a combination.
      NOT NULLThe column must have a non-null value.
      UNIQUENo repeated equal key values; ordinary PostgreSQL unique constraints allow multiple nulls.
      CHECKA condition cannot evaluate to false. Unknown/null does not fail it, so NOT NULL may also be needed.
      FOREIGN KEYNon-null referencing values must match an eligible key in the referenced table.

      A default supplies an omitted value; it does not itself forbid an explicit NULL. Choose nullability from the domain, not a target percentage of columns. Boundary validation gives clients useful errors, while database constraints protect every writer, including scripts and concurrent requests. PostgreSQL constraints.

      Schema migration — up, part 1: allowed states
      CREATE TYPE project_status AS ENUM
  ('planned', 'active', 'completed', 'archived');
CREATE TYPE task_status AS ENUM
  ('pending', 'in_progress', 'completed', 'cancelled');
CREATE TYPE member_role AS ENUM ('owner', 'admin', 'member');

      An enum rejects values outside its declared labels and makes the allowed set visible in the schema. The project default below is planned, matching Lesson 07's API example. Enums suit relatively stable sets; text with a CHECK or a lookup table may suit frequently changing values better. Enum removal or reordering is more involved than adding a label.

      These types validate a stored state, not the legality of every transition. Moving a project from archived to active may require business authorization even though both labels are valid.

      Key takeaways

      • Use keys, required values, uniqueness, checks and foreign keys to enforce database invariants.
      • Defaults and CHECK conditions do not replace NOT NULL.
      • Enums document allowed labels; transition rules and permissions still belong in the use case.

      Users and profiles: one-to-one relationships

      The next SQL blocks form one schema migration, in the order shown. They model the user/project portion of the platform from API Design. An organization-based product would also retain organization relationships and enforce that scope on operations. Here, users can own projects, join projects and receive task assignments.

      Schema migration — up, part 2: users and optional profiles
      CREATE TABLE users (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email text NOT NULL UNIQUE,
  full_name text NOT NULL CHECK (char_length(btrim(full_name)) > 0),
  password_hash text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE user_profiles (
  user_id uuid PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  avatar_url text,
  bio text,
  phone text,
  created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);

      user_profiles.user_id is both its primary key and a foreign key. A user can therefore have at most one profile. This does not force every user to have a profile; that requires an additional creation rule. Nullable profile fields let a user omit a bio, phone number or image.

      Separating optional profile data can be useful for independent ownership, lifecycle or access patterns, but it is not automatically faster or necessary. Keeping these fields in users is also reasonable for a simpler model. Choose the relationship deliberately.

      Stored credentials are not response fields

      password_hash holds the output of the application's password-hashing workflow, never a plaintext password. Select explicit public fields when building API responses. A query that returns every users column can expose password hashes even though the passwords themselves were not stored in plaintext.

      The email constraint enforces the database's equality behavior, not the full application's email-identity policy. Define normalization and case handling consistently, and match the uniqueness rule to that policy. Lowercase snake_case identifiers also avoid PostgreSQL's quoted-name surprises: unquoted names fold to lowercase, while quoted names preserve case.

      Key takeaways

      • A foreign key that is also unique or primary enforces at most one related profile per user.
      • Optional relationships are not mandatory relationships; a profile row may be absent.
      • Keep password hashes private and align email uniqueness with the application's identity policy.
      • Use a consistent identifier convention; unquoted PostgreSQL identifiers fold to lowercase.

      Projects and tasks: one-to-many relationships

      Schema migration — up, part 3: ownership and tasks
      CREATE TABLE projects (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name text NOT NULL CHECK (char_length(btrim(name)) > 0),
  description text,
  status project_status NOT NULL DEFAULT 'planned',
  owner_id uuid NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE tasks (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  title text NOT NULL CHECK (char_length(btrim(title)) > 0),
  description text,
  priority integer NOT NULL DEFAULT 1 CHECK (priority BETWEEN 1 AND 5),
  status task_status NOT NULL DEFAULT 'pending',
  due_date date,
  assigned_to uuid REFERENCES users(id) ON DELETE SET NULL,
  created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);

      Many tasks can share one project_id, so a project has a one-to-many relationship with tasks. Each task has its own primary key. Its project foreign key is required, while assigned_to can be null for an unassigned task. A syntactically valid UUID is insufficient for either reference: the referenced row must exist.

      Choose what happens when a parent is deleted

      ActionEffectExample here
      RESTRICTReject deletion while referencing rows remain.A user owning a project cannot be deleted until ownership or the project is dealt with.
      CASCADEDelete referencing rows along with the parent.Deleting a project removes its tasks; deleting a user removes their profile.
      SET NULLClear the reference; the column must allow null.Deleting an assignee leaves their tasks unassigned.
      SET DEFAULTReplace the reference with its default, which must still satisfy constraints.Useful only when the replacement value is valid for the domain.
      NO ACTIONThe default; reject a remaining violation when checked. Checking can be deferred if the constraint is declared deferrable.Different timing rules from RESTRICT can matter within transactions.

      Cascades are a product decision, not an automatic convenience to apply everywhere. Their effects can span many rows. If a user also owns projects, the owner RESTRICT rule can reject the whole deletion even though another reference says SET NULL. All constraints must hold.

      Key takeaways

      • One-to-many uses a foreign key on the many side, without making that foreign key unique.
      • Foreign keys ensure references exist; CHECK and NOT NULL enforce required valid values.
      • Choose RESTRICT, CASCADE, SET NULL or other delete actions according to the resource lifecycle.
      • Every affected constraint applies; one permissive delete action cannot override another restriction.

      Memberships: many-to-many relationships

      A user may join many projects and a project may have many users. Represent each membership as a row in a linking table. The role belongs to that relationship: someone can be an admin in one project and a member in another.

      Schema migration — up, part 4: a composite key
      CREATE TABLE project_members (
  project_id uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  role member_role NOT NULL DEFAULT 'member',
  created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (project_id, user_id)
);

      The pair (project_id, user_id) identifies a membership. It permits one user in several projects and several users in one project, while rejecting a duplicate membership pair. Deleting either parent removes its corresponding membership rows.

      This schema does not automatically synchronize projects.owner_id with a membership whose role is owner. Maintain that invariant in a transaction if the application requires both representations. It also does not prove that an assigned task user is a project member; validate that business rule or model a suitable additional constraint.

      Schema migration — down, for a disposable example database
      DROP TABLE project_members;
DROP TABLE tasks;
DROP TABLE projects;
DROP TABLE user_profiles;
DROP TABLE users;
DROP TYPE member_role;
DROP TYPE task_status;
DROP TYPE project_status;

      Place the four creation blocks under dbmate's -- migrate:up marker and the teardown under -- migrate:down. Drop dependent tables before the parents and types they reference. This teardown deletes the data; it is not a production recovery plan.

      Key takeaways

      • A linking table models many-to-many relationships and can store relationship-specific attributes.
      • A composite primary key prevents duplicate pairs without an extra synthetic ID.
      • Constraints enforce the rules declared in the schema, not every unstated business invariant.
      • Reverse dependencies when tearing down a schema, and recognize that dropped data is lost.

      Seeding: create useful development data

      Seed data gives development and test environments predictable records before real users exist. Keep test fixtures separate from production migrations. Reference data required by the application, such as a maintained country table, has a different lifecycle from fake users.

      Insert parents before their children. A common table expression (CTE) can use INSERT's RETURNING result to pass newly generated IDs into another insert within the same statement. A CTE is a named query result, not a permanently created table.

      Development-only fixture — run once in a disposable database
      WITH inserted_user AS (
  INSERT INTO users (email, full_name, password_hash)
  VALUES ('learner@example.test', 'Test Learner', 'disabled-fixture-no-login')
  RETURNING id
), inserted_profile AS (
  INSERT INTO user_profiles (user_id, bio)
  SELECT id, 'Learning database relationships' FROM inserted_user
  RETURNING user_id
), inserted_project AS (
  INSERT INTO projects (name, owner_id)
  SELECT 'Backend study project', id FROM inserted_user
  RETURNING id, owner_id
), inserted_membership AS (
  INSERT INTO project_members (project_id, user_id, role)
  SELECT id, owner_id, 'owner' FROM inserted_project
  RETURNING project_id
)
INSERT INTO tasks (project_id, title)
SELECT project_id, 'Review the schema' FROM inserted_membership
RETURNING id, project_id, title, status;

      The password marker deliberately represents a disabled, non-login fixture; it is not a password hash to use for authentication. For login tests, generate a real hash through the application's configured password-hashing library. Never seed a shared production password.

      This fixture is intentionally run once: a second run hits the unique email constraint. Choose a clean-database reset or a deliberate conflict-handling strategy for repeatable tests. Also test missing profiles, unassigned tasks, duplicate input and constraint failures, not just a fully populated successful example.

      Key takeaways

      • Keep development fixtures separate from production schema changes and required reference data.
      • Use returned IDs to create related rows; CTEs can express that dependency within one statement.
      • Define repeat-run behavior and include missing relationships and invalid-input cases in tests.

      Read data with joins and explicit response fields

      A user and their profile live in two tables but can be returned from one query. Think through FROM and JOIN to establish where the data comes from, then choose SELECT fields. SQL syntax still places SELECT first. Short aliases such as u and up make column references clear.

      A bounded list for an authorized user-directory endpoint
      SELECT
  u.id,
  u.full_name,
  u.created_at,
  CASE WHEN up.user_id IS NULL THEN NULL
       ELSE jsonb_build_object(
         'avatarUrl', up.avatar_url,
         'bio', up.bio
       )
  END AS profile
FROM users AS u
LEFT JOIN user_profiles AS up ON up.user_id = u.id
ORDER BY u.created_at DESC, u.id DESC
LIMIT 20;

      LEFT JOIN keeps each selected user even if a profile is absent; profile then becomes null. INNER JOIN would exclude unmatched users, not necessarily empty the entire result. An unrestricted one-to-many join can multiply rows, so consider aggregation or another query when combining projects with many tasks.

      PostgreSQL's to_jsonb can convert a composite row into JSON, but converting an entire row couples the response to every current and future column. Building an explicit JSON object here avoids publishing private profile fields. The users selection also omits email and password_hash. Add further authorization scope as required by the application.

      The repository returns selected values; the service and controller still map and serialize the public response. Neither the language nor the presence of a JSON column eliminates serialization work. For predictable pagination, the ordering includes an ID tie-breaker when creation times are equal.

      Key takeaways

      • LEFT JOIN preserves unmatched rows from the left; INNER JOIN keeps only matched combinations.
      • Select explicit response fields and build intentional nested objects; do not expose password hashes.
      • Use deterministic ordering and bounds, and account for row multiplication in one-to-many joins.

      Parameterized values and safe dynamic SQL

      Bind client-supplied values separately from SQL text. PostgreSQL-style placeholders use $1, $2 and so on; individual drivers may expose another placeholder syntax. The driver binds data with types, not necessarily as strings, and the server does not reinterpret that data as SQL syntax.

      Query template — bind the requested UUID as parameter 1
      SELECT u.id, u.full_name, u.created_at
FROM users AS u
WHERE u.id = $1::uuid;

      Supply the UUID as a separate argument to the driver's execution call. Do not add quote characters around the value yourself or wrap $1 in SQL string quotes. A value containing SQL-looking text remains data; an invalid UUID fails type conversion. A valid UUID still requires a permission check. Parameterization prevents injection, not unauthorized access. PostgreSQL prepared statements and parameters.

      Column names and ASC/DESC are not value parameters

      ORDER BY $1 $2 cannot bind a column and a sort direction. Some editor dialogs perform textual substitution, which is different from genuine value binding. Map validated sort choices to fixed SQL fragments controlled by the application; keep data values bound.

      Accepted API valueApplication-owned SQL fragment
      sortBy=fullNameu.full_name
      sortBy=createdAtu.created_at
      sortOrder=ascASC
      sortOrder=descDESC

      Reject unsupported choices, and never concatenate the raw client string into the query. The same rule applies to dynamic update column names. Most query builders support safe value binding, but their raw-SQL escape hatches still require care.

      Key takeaways

      • Keep SQL structure separate from bound values; let the driver handle value encoding.
      • Placeholders represent values, not identifiers, keywords or arbitrary SQL fragments.
      • Build sort and update structure only from validated choices mapped to trusted fragments.
      • Injection protection does not replace input validation or resource authorization.

      Filtering, sorting and pagination in SQL

      Suppose an authorized directory endpoint accepts letter, sortBy, sortOrder, page and limit. Validate those inputs before query construction. Default to page 1, limit 20 and creation time descending, with a maximum limit of 100. The API page is one-based; the database offset is a count of skipped rows.

      Default-sort query template
      SELECT u.id, u.full_name, u.created_at
FROM users AS u
WHERE ($1::text IS NULL OR u.full_name ILIKE ($1::text || '%'))
ORDER BY u.created_at DESC, u.id DESC
LIMIT $2::integer OFFSET $3::bigint;

      Bind parameter 1 to the validated first letter, or NULL when omitted. This example accepts one ASCII letter, not wildcard input. ILIKE is case-insensitive pattern matching and % means any following characters. If the feature later accepts arbitrary literal prefixes, escape pattern metacharacters such as % and _ deliberately; parameter binding alone does not change their pattern meaning.

      Client requestBound limitComputed offset
      page=1&limit=2020.0.
      page=2&limit=2020.20.
      page=3&limit=2020.40.

      Use offset = (page − 1) × limit, not just page minus one. For a different sort, select an allowed column and direction from the mapping in the previous section. Retain a unique tie-breaker. Optional filters can also be added as fixed query fragments only when present, rather than using the nullable-parameter form above.

      Count template — match the same filter and access scope
      SELECT count(*) AS total
FROM users AS u
WHERE ($1::text IS NULL OR u.full_name ILIKE ($1::text || '%'));

      Counting and fetching in separate statements can observe different committed states. Use a consistent snapshot if the contract requires exact agreement. Cursor pagination and optional totals can be preferable for large or changing collections. For tenant-scoped endpoints, include the same authorization restriction in both queries.

      Key takeaways

      • Validate query inputs, bind filter values and construct sort syntax only from allowed choices.
      • OFFSET is the number of skipped rows: (page − 1) × limit.
      • Pattern matching has its own wildcard rules even when parameters are safely bound.
      • Counts and rows must share filters and permissions; decide whether a consistent snapshot is required.

      Inserts, partial updates and transactions

      A create-user use case validates input and creates a password hash in application code, then inserts the permitted fields. Defaults fill the ID and initial timestamps. RETURNING lets the repository obtain the inserted record without a separate lookup.

      Create template — return only intended account fields
      INSERT INTO users (email, full_name, password_hash)
VALUES ($1::text, $2::text, $3::text)
RETURNING id, email, full_name, created_at;

      Handle the unique email constraint even if the application already checked availability; another request could insert that email between the check and this statement. Map the database error to the documented API behavior without returning raw SQL diagnostics.

      Only update fields present in the patch

      If a profile patch contains bio and phone, build a SET list containing those allowed fields. Leave an omitted avatar URL untouched. An explicit null can clear a nullable field when the API permits it; omission and null are different. This template assumes the user is authorized to edit the profile identified by parameter 3.

      Update template — bio and phone supplied, avatar omitted
      UPDATE user_profiles
SET bio = $1::text,
    phone = $2::text
WHERE user_id = $3::uuid
RETURNING user_id, avatar_url, bio, phone, updated_at;

      An UPDATE that matches no profile returns no rows. Decide whether the use case creates a missing profile, treats it as not found, or requires a separate creation flow. Reject an empty patch or define it as a no-op; do not accidentally generate an empty SET clause. Without the trigger introduced later, this statement does not refresh updated_at.

      When creating a project and its owner membership, use one transaction so both changes succeed together. On failure, roll back and release the connection. A transaction does not make external notifications rollbackable; arrange those after commit or through a reliable delivery workflow. Keep transactions short and handle retryable conflicts deliberately.

      Key takeaways

      • Bind insert values and return only fields appropriate for the caller, never password hashes.
      • Database constraints still matter after application validation, especially under concurrency.
      • Partial updates change supplied fields; define null, omission, empty-patch and missing-row behavior.
      • Use transactions for related database changes, with explicit rollback and failure handling.

      Indexes: support measured access patterns

      A book index helps you find a topic without reading every page. A database index similarly gives the query planner another way to find rows or satisfy ordering. PostgreSQL's default B-tree index is a search structure, not a guarantee that every lookup is constant time or that all index data lives in RAM at one physical location.

      Indexes occupy storage and add maintenance work to writes. A sequential scan can be the best choice for a small table or a query returning much of it. Consider frequent WHERE, JOIN and ORDER BY patterns, inspect actual plans, and avoid adding an index to every column.

      First check what already exists

      • Primary keys and unique constraints create supporting unique indexes automatically.
      • users.email already has an index from UNIQUE; a second identical index is unnecessary.
      • user_profiles.user_id is indexed because it is the primary key.
      • Foreign keys do not automatically create an index on the referencing side.
      • project_members(project_id, user_id) naturally supports lookup by its leading project_id; user-only lookup may need another index.
      Candidate migration — choose these for corresponding frequent queries
      -- migrate:up
CREATE INDEX users_created_at_id_idx
  ON users (created_at DESC, id DESC);
CREATE INDEX projects_owner_id_idx
  ON projects (owner_id);
CREATE INDEX tasks_project_created_at_id_idx
  ON tasks (project_id, created_at DESC, id DESC);
CREATE INDEX tasks_assigned_to_idx
  ON tasks (assigned_to);
CREATE INDEX project_members_user_id_idx
  ON project_members (user_id);

      The tasks composite index supports selecting a project's tasks in creation order and begins with project_id for project lookups. Do not automatically add another project_id-only index. A status-only index may be unhelpful when most rows share that status; a composite or partial index may fit a particular workload better.

      A B-tree can scan forward or backward, so you do not normally need separate ascending and descending indexes for a single column. Mixed directions and leading columns matter for multi-column ordering. ILIKE search may need an expression index or a specialized operator class; an ordinary text B-tree does not automatically optimize every pattern. Indexes and ordering, multicolumn indexes.

      Measure with a query plan

      Read-only plan inspection
      EXPLAIN (ANALYZE, BUFFERS)
SELECT id, full_name, created_at
FROM users
ORDER BY created_at DESC, id DESC
LIMIT 20;

      Compare estimates, actual rows, scans, sorting and buffer activity using representative data. EXPLAIN ANALYZE executes the statement, so use care with writes or expensive queries. A tiny seed table using a sequential scan does not prove the index is broken. PostgreSQL EXPLAIN guide.

      Reverse the example index migration
      -- migrate:down
DROP INDEX project_members_user_id_idx;
DROP INDEX tasks_assigned_to_idx;
DROP INDEX tasks_project_created_at_id_idx;
DROP INDEX projects_owner_id_idx;
DROP INDEX users_created_at_id_idx;

      Ordinary index creation can block writes. For a busy production table, evaluate PostgreSQL's concurrent build option and its restrictions; it cannot run inside a transaction block and needs a migration configured accordingly. An index is an operational change as well as a query aid.

      Key takeaways

      • Index frequent, measured access patterns; account for storage and write-maintenance costs.
      • Primary and unique keys already have indexes; referencing foreign keys do not automatically get them.
      • Consider leading columns, order and selectivity before adding overlapping indexes.
      • Use EXPLAIN with representative data; ANALYZE executes the query.

      Triggers: maintain updated_at deliberately

      DEFAULT CURRENT_TIMESTAMP initializes a value on insertion; it does not run again whenever the row changes. You can set updated_at in every update statement or install a trigger so all writers follow the same rule.

      Timestamp migration — reusable function and table triggers
      -- migrate:up
CREATE FUNCTION set_updated_at()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.updated_at = statement_timestamp();
  RETURN NEW;
END;
$$;

CREATE TRIGGER users_set_updated_at
BEFORE UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER user_profiles_set_updated_at
BEFORE UPDATE ON user_profiles
FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER projects_set_updated_at
BEFORE UPDATE ON projects
FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER tasks_set_updated_at
BEFORE UPDATE ON tasks
FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER project_members_set_updated_at
BEFORE UPDATE ON project_members
FOR EACH ROW EXECUTE FUNCTION set_updated_at();

      NEW is the proposed row value. The BEFORE UPDATE trigger changes its timestamp before the row is stored, and RETURN NEW passes that row onward. BEGIN/END delimit the function body; they do not start a separate SQL transaction. The trigger runs in the updating statement's transaction. PostgreSQL trigger functions.

      This policy uses statement start time, so all rows updated by one statement get the same timestamp. It also fires for updates that assign existing values. If the domain needs only meaningful changes to advance the timestamp, define that condition explicitly. updated_at is not a complete audit history or a timestamp of one particular field's last change.

      Reverse the timestamp migration
      -- migrate:down
DROP TRIGGER project_members_set_updated_at ON project_members;
DROP TRIGGER tasks_set_updated_at ON tasks;
DROP TRIGGER projects_set_updated_at ON projects;
DROP TRIGGER user_profiles_set_updated_at ON user_profiles;
DROP TRIGGER users_set_updated_at ON users;
DROP FUNCTION set_updated_at();

      Key takeaways

      • An insert default does not maintain updated_at on later updates.
      • A BEFORE UPDATE row trigger can change NEW and return it before storage.
      • Choose transaction-time, statement-time or other timestamp semantics intentionally.
      • Triggers run inside the caller's transaction; updated_at does not replace an audit log.

      Connect the database work to the API

      1. ContractIdentify the permitted operation

        Decide which caller can access which records, which inputs are allowed, and what the response should contain.

      2. BoundaryValidate and normalize

        Parse IDs, pagination and filters. Distinguish missing, null and invalid values and obtain the verified caller identity.

      3. ServiceEnforce business rules

        Check ownership and workflow rules, choose any transaction boundary and pass explicit application data to the repository.

      4. RepositoryExecute safe SQL

        Bind values, allowlist dynamic structure, use the appropriate joins and return selected fields. Rely on declared constraints as a final integrity boundary.

      5. ResponseMap the outcome

        Serialize the public result or a safe error. Empty lists, missing items and conflicting writes are distinct outcomes.

      6. MaintenanceMeasure and evolve

        Review query plans and real workloads, add justified indexes, evolve through migrations and test backup restoration.

      Check your understanding

      • Does a valid UUID prove that a user exists? No; a foreign key enforces existence, and authorization is a separate check.
      • Does one profile foreign key guarantee one profile? Only with a uniqueness or primary-key constraint on that reference.
      • Can a parameter contain a sort direction? Not as SQL syntax; select a trusted fragment from validated choices.
      • Does a UNIQUE email need another identical index? No; the constraint already creates its supporting index.
      • Will a default timestamp change on UPDATE? No; use explicit update logic or a trigger.
      • Can a down migration recover deleted records? Not by recreating the schema; data recovery requires a suitable recovery source.

      Key takeaways

      • Model: choose types, keys, relationships, nullability and delete behavior from the domain.
      • Evolve: review migrations and keep disposable test seeds separate.
      • Query: authorize access, bind values and return explicit public fields.
      • Coordinate: use transactions and concurrency controls for consistent changes.
      • Optimize: measure indexes and document automatic behavior such as triggers.
