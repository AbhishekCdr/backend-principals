      Lesson 10

      Background Jobs

      Keep requests responsive while slower work continues elsewhere. Learn how producers, queues and workers hand off tasks, then make that handoff reliable with durable state, acknowledgements, safe retries and clear progress reporting.

      Work outside the request lifecycle

      A background job is work whose completion is decoupled from the original request and response. The API accepts the work, records enough information to carry it out, and responds without waiting for the entire operation to finish. A worker performs the work later.

      This makes sense when the caller can continue before the result is ready: sending an email, resizing an image, encoding a video, generating a report or delivering a push notification. Scheduled maintenance may have no originating HTTP request at all.

      Deferred does not mean unimportant

      Account deletion, verification emails and financial processing can be business-critical even when they happen in the background. The distinction is whether the work must finish before this response, not whether it matters. Deferred work still needs deadlines, correctness guarantees and a recovery path.

      Using async or await does not by itself create a durable background job. An HTTP handler that awaits an email provider still delays its response. Starting an untracked promise or thread and returning may lose work when the process restarts. A separate worker deployment is common, although workers can also use threads or other concurrency models.

      Key takeaways

      • Background work completes independently of the original HTTP response.
      • Deferrable work can still be critical and time-sensitive.
      • Language-level asynchronous code alone does not provide durable job processing.

      The signup email example

      A signup handler validates input, hashes the password and records an unverified account. It also needs to arrange a verification email. Calling the email provider inside the request ties response latency to that provider, whose timeout or outage you cannot control.

      Inline email callQueued email task
      The response waits for the provider.The response waits for durable acceptance of the work.
      A provider error must be reconciled with an account that may already exist.The account can remain unverified while delivery is pending or being retried.
      Retry behavior is tied to the handler or another recovery mechanism.A worker applies the configured retry policy outside the request.
      1. Validate signup input and establish the account's unverified state.
      2. Durably record the verification request and the intent to send its email.
      3. Respond with an accurate account and delivery status.
      4. A worker loads the verification request and calls the email provider.
      5. Record the result; retry eligible failures within the verification deadline.

      “Verification email queued” is different from “email delivered.” Provider acceptance also does not prove that a message reached the recipient's inbox. A backlog or prolonged outage can delay delivery well beyond a few seconds. Keep the account unverified until the user completes verification, and provide a rate-limited resend flow.

      Before sending, check whether the verification request is still valid, expired, replaced or already completed. A retry must not send a superseded link or silently extend its lifetime. These checks connect background processing to the rules in Authentication & Authorization.

      Key takeaways

      • Queueing separates signup latency from email-provider latency.
      • Accepted work, provider acceptance and recipient delivery are different milestones.
      • Delayed verification jobs must respect expiry, supersession and account state.

      Producer, broker and worker

      Think of a task queue as a shared to-do list with rules for claiming, completing and retrying work. It is more than an in-memory array: reliable operation depends on how ownership and task state survive failures.

      Two connected execution paths
      Client → API / producer → durable handoff → response
                                  │
                                  ▼
                             task queue
                                  │ claim a job
                                  ▼
                         worker → task handler
                                  │
                       complete / retry / fail
      ComponentResponsibility
      ProducerCreate the task description and enqueue it. This may be an API, scheduler or another worker.
      Broker / queue serviceStore and deliver messages according to configured persistence, retention and delivery rules.
      Worker / consumerClaim work, validate its payload, run the registered handler and report the outcome.
      Task handlerPerform the specific business operation, such as sending one verification email.

      A broker can manage many queues; the terms are related but not identical. Separate email, reporting and media queues can keep slow video work from delaying verification messages. Workers subscribe or poll according to the system; they do not have to continuously busy-wait.

      The producer usually sends data and a task type, not a live function or request object. Workers already contain the code that maps that type to a handler. They may share a repository with the API while running as independently scaled processes.

      Key takeaways

      • The producer describes work, the broker delivers it and the worker executes it.
      • A broker may host multiple queues with different worker pools.
      • Enqueueing a task is distinct from executing its handler.

      Designing the job payload

      A worker needs enough information to understand the intended operation after the request has ended. JSON is a common transport format; deserialization produces the language's native objects or structs. The job schema is a contract, like an API payload.

      Illustrative task envelope — not a library-specific API
      {
  "jobId": "job-842",
  "type": "sendVerificationEmail",
  "schemaVersion": 1,
  "userId": "user-17",
  "verificationRequestId": "verification-63",
  "requestedAt": "2026-10-12T10:00:00Z",
  "expiresAt": "2026-10-12T10:15:00Z",
  "correlationId": "request-918"
}
      • Stable identity: retain the same logical job or operation identity across retries.
      • Explicit scope: include validated resource and tenant identifiers where applicable.
      • Small payloads: refer to durably stored images, videos or report inputs rather than embedding large files.
      • Versioned data: workers may receive jobs produced by an older deployment.
      • Safe contents: avoid passwords and provider credentials; minimize personal data and restrict access to sensitive verification material.

      Decide whether the worker should use an immutable snapshot or reload current state. A monthly report needs an explicit reporting period and a defined data cutoff; a verification email needs the still-valid verification request. Blindly reloading “whatever is current” can change what the original task meant.

      Validate the envelope at the worker boundary and allow only recognized task types. Treat payloads as data, never arbitrary executable code. Carry correlation identifiers for debugging, not the entire request context or reusable client credentials. See Serialization and Validation.

      Key takeaways

      • Use a small, versioned task contract with a stable operation identity.
      • Store large inputs durably and pass references with the required scope.
      • Validate again in the worker and define snapshot-versus-current-state behavior.

      Queue technology and job libraries

      A job library supplies application-facing handlers, retries and scheduling features. A broker supplies messaging and storage behavior. Choose the combination by its guarantees and your existing stack; these are different layers rather than interchangeable product categories.

      ExampleRole
      CeleryA Python task-processing system that works with supported brokers, including RabbitMQ and Redis.
      BullMQA Redis-backed job library commonly used with Node.js.
      AsynqA Go task library backed by Redis.
      RabbitMQA message broker with producer confirmations and consumer acknowledgement mechanisms.
      Amazon SQSA managed queue service with regional endpoints; using it does not automatically create one globally replicated queue.

      Redis Pub/Sub is not a durable job queue

      Plain Redis Pub/Sub uses at-most-once delivery and does not retain a message for a disconnected subscriber to process later. Redis-backed job libraries use additional data structures and coordination; Redis Streams also has different delivery facilities. Redis Pub/Sub delivery semantics.

      Persistence, replication, acknowledgement timing and retry defaults vary. Configure and test them explicitly. Redis holding pending jobs is important workflow state, unlike a disposable query cache: an eviction policy that silently removes job data is inappropriate. This is the same distinction made in Caching for sessions and rate-limit state.

      Key takeaways

      • Separate the application job library from its broker or storage engine.
      • Plain Pub/Sub does not provide durable task delivery.
      • Verify persistence, retention, retries and deployment guarantees rather than assuming defaults.

      Durable handoff and the transactional outbox

      Creating an account and publishing its job are separate writes. If publication fails after commit, no email is scheduled. Publishing first can expose data that never commits.

      A transactional outbox saves the account and pending message in one database transaction. A relay publishes committed messages and records broker confirmation. The API acknowledges durable intent, not completed delivery. See the transactional outbox pattern.

      Persist intent before acknowledging it
      One database transaction:
  create unverified account
  create verification request
  create outbox message
commit

Relay:
  publish committed message → broker confirmation → mark dispatched

      Crashing between publication and marking dispatch can duplicate messages. Preserve their identity and make consumers tolerate replay. A job table written in the same database transaction can also provide durable handoff.

      Key takeaways

      • Database updates and broker publication have a failure gap.
      • An outbox durably couples a change to its intended follow-up.
      • Relay retries can duplicate messages; consumer idempotency remains necessary.

      Acknowledgements, leases and visibility timeouts

      Claiming a job should not automatically mean its work is complete. Reliable queues retain enough state to recover uncompleted work. Producer confirmation establishes broker acceptance; consumer acknowledgement reports processing completion. Those are separate guarantees. RabbitMQ confirmations and acknowledgements.

      With SQS, receiving a message temporarily hides it for a visibility timeout. The worker explicitly deletes it after successful processing. If it is not deleted before that timeout, it can be delivered again. The worker can extend visibility while legitimately processing a longer task. Other systems use different acknowledgement, lock or lease mechanisms. SQS visibility timeout.

      SettingQuestion it answers
      Execution timeoutHow long may this attempt run?
      Visibility / lease durationHow long does this worker retain its claim?
      Retry delayWhen is another attempt eligible?
      Job deadline / retentionWhen is the work obsolete, or no longer retained by the queue?

      A lease expiring does not necessarily stop the original worker. Two attempts can overlap. Acknowledging before required effects are safely recorded can lose work; crashing after an effect but before acknowledgement can repeat it. Timeouts and acknowledgements help recovery, but do not create exactly-once business effects.

      At-least-once delivery permits repeated deliveries. Message retention and failure policies still apply; it is not a guarantee that every business operation eventually succeeds. Design the handler for duplicates as well as failures.

      Key takeaways

      • Broker acceptance and completed processing are different acknowledgements.
      • Visibility or lease expiry allows uncompleted work to be retried.
      • Plan for redelivery and overlapping attempts, even when using timeouts.

      Retries, backoff and failed jobs

      Retry errors that may resolve with time: a network timeout, temporary service outage or provider throttling. Invalid payloads, unsupported task versions and permanent business rejections need a different path. Retrying every error forever consumes capacity without making the operation more likely to succeed.

      Exponential backoff increases the delay between attempts. Add jitter, a bounded random variation, to avoid many workers retrying together. Cap attempts and delays, honor provider retry guidance, and stop when the task's deadline makes further execution inappropriate. BullMQ retry and backoff options.

      Example policy — five total attempts, before jitter
      Attempt 1: run when eligible
Attempt 2: wait 1 minute after failure
Attempt 3: wait 2 minutes after failure
Attempt 4: wait 4 minutes after failure
Attempt 5: wait 8 minutes after failure

Total waiting before the last attempt: 15 minutes
Plus queue delay and the time spent executing each attempt

      That policy cannot assume a 15-minute verification link will still be useful at the final attempt. External services can stay unavailable for much longer than a few retries. Choose the policy from the task deadline and failure mode, not an assumed maximum provider outage.

      When retrying stops

      Exhausted or permanently failing jobs should enter a visible failed state or dead-letter queue where supported and configured. Alert on them, retain enough context to diagnose the cause, then replay deliberately after fixing it. A dead-letter queue stores failures; it does not repair them. Replay must still respect expiry and idempotency.

      Report failures using the library's expected error mechanism. Catching an exception, logging it and returning success can cause the queue to acknowledge unfinished work. Avoid multiplying retries across the HTTP client, handler and job library without a shared attempt budget.

      Key takeaways

      • Retry transient failures with bounded backoff and jitter.
      • Count total attempts separately from retries and include queue time in deadlines.
      • Surface permanent failures and exhausted jobs for diagnosis and controlled replay.

      Idempotency: make repeated attempts safe

      A job is idempotent when repeating the same logical operation produces the same intended business outcome as completing it once. It may have side effects; those effects must not multiply on redelivery. This extends the reasoning from HTTP method idempotency to worker execution.

      Imagine a worker sends an email successfully, then crashes before recording success. The queue retries it. A database rollback cannot unsend the email, just as it cannot undo an external file deletion or payment. Transactions protect operations inside their scope; they do not automatically make an entire distributed workflow idempotent.

      OperationPossible protection
      Create a weekly reportUse a unique user-and-reporting-period identity so a replay reuses the existing result.
      Apply a database change onceAtomically record a unique operation ID with the change in the same transaction.
      Call an external providerReuse a stable provider idempotency key where supported; verify its scope and retention window.
      Delete an assetTreat an already-absent intended asset as completed, while still checking ownership and the target version.

      A separate “has this job run?” read followed by an unprotected write can race between workers. Use an atomic constraint or conditional transition. Recording “done” before an external call risks losing the effect; recording it afterward leaves a duplicate window. If the provider cannot deduplicate, define how you detect, reconcile or tolerate that ambiguity.

      Queue-level deduplication can reduce duplicate submissions but is not a universal exactly-once guarantee for side effects. Keep the business identity stable across retries and deliberate replays. See BullMQ's idempotent-job guidance.

      Key takeaways

      • Idempotency preserves the intended result when the same operation runs again.
      • A transaction cannot roll back effects in unrelated external systems.
      • Use stable business keys and atomic protections; handle ambiguous provider outcomes explicitly.

      One-off, delayed and recurring tasks

      Task typeTriggerExample
      One-offA particular event or request.Send a welcome email after one registration.
      DelayedA specific eligibility time.Begin deletion after an explicitly offered grace period.
      RecurringA schedule that produces repeated runs.Generate a daily report or clean up expired records.

      A one-off task can still have multiple execution attempts. A delayed task becomes eligible after its delay; worker availability determines when it actually starts. A scheduler creates recurring jobs, while workers execute them. Those are separate responsibilities.

      Push notifications as one-off jobs

      A mobile app registers for remote notifications and sends its registration or device token to the backend. A worker uses that token and the notification content to call a push service, such as FCM or APNs. Platform infrastructure delivers the message to the device; the provider accepting it is not proof that a user saw it. Keep token records current and handle invalid tokens rather than retrying them forever. FCM's delivery architecture.

      Scheduling is more than a cron expression

      • Time zone: define what “midnight” means and how daylight-saving changes are handled.
      • Missed runs: decide whether an outage causes catch-up runs, one combined run or skipped work.
      • Overlaps: decide what happens if yesterday's run is still executing when the next becomes due.
      • Duplicates: coordinate schedulers and give each logical run a stable identity, such as user plus reporting period.

      Celery's periodic-task documentation, for example, calls out scheduler duplication and overlapping runs. Scheduling is not a guarantee of exactly one execution at an exact instant. Celery periodic tasks.

      A cleanup job may reclaim expired sessions in batches. Authentication must still reject an expired or revoked session immediately according to its policy; the next cleanup run is not the mechanism that decides whether the session remains valid.

      Key takeaways

      • One logical task can be retried; a schedule creates multiple logical runs.
      • Specify time zones, missed-run behavior, overlap rules and run identity.
      • Cleanup reclaims storage; it must not be the only enforcement of expiry or revocation.

      Chains and parallel task dependencies

      Some jobs need the output of earlier jobs. Others can run at the same time. Model those dependencies explicitly so that a failed step can be retried without repeating every successful step in the workflow.

      One possible learning-platform video workflow
      Upload durably completed and validated
                 │
                 ▼
           Encode video
                 │
           ┌─────┴───────────┐
           ▼                 ▼
    Generate thumbnails   Generate subtitles
           │                 │
           ▼                 │
    Resize thumbnails        │
           └───────┬─────────┘
                   ▼
       Publish when required outputs are ready

      This is an illustrative dependency graph. Subtitles or thumbnails may be derived directly from the original upload in another design, so they need not universally wait for encoding. Follow actual input dependencies, not an arbitrary sequence of names.

      Do not enqueue processing against an upload that has merely started. With direct object-store uploads or presigned URLs, confirm the expected object is durably available and validate its ownership and input properties first. A quick response that starts an upload is not proof the video has finished uploading.

      Persist workflow progress and output references. Decide whether a failed optional subtitle job blocks publication or results in a partial outcome. Even “parent” and “child” terminology varies: in BullMQ flows, a parent normally waits for its children, so parent does not universally mean the step that runs first.

      Key takeaways

      • Run independent jobs in parallel and gate dependent jobs on required outputs.
      • Begin processing only after the referenced input is durably available and validated.
      • Persist progress and define how failures affect downstream steps.

      Batch work and account deletion

      A batch processes many items with the same kind of operation. A dispatcher might create one report job per user, or chunk a large cleanup into bounded groups of records. Creating many independent jobs is often called fan-out; collecting their results is fan-in. A batch can be part of a larger chain.

      Account deletion is a workflow

      1. Authenticate and authorize the request, then durably record the deletion intent.
      2. Apply the documented access policy, such as disabling access and revoking sessions, and return a pending status.
      3. After any explicit grace period, process owned records and assets in bounded, restartable steps.
      4. Record each completed step and reconcile failures before declaring the workflow complete.

      Shared projects may require ownership transfer rather than deletion. A grace period needs a real cancellation or recovery flow; an already-disabled login must not be the only way to cancel. Workers must check whether the request was canceled or superseded before continuing destructive steps. Do not promise that all data is permanently gone at the moment work is queued.

      An account-deletion workflow is not automatically a batch; its per-record cleanup steps can be batched. A giant transaction spanning database rows, object storage and external APIs is neither practical nor globally atomic. Prefer short transactions and durable checkpoints, with each repeated step safe to resume. A checkpoint is useful only if repeating work around that checkpoint cannot corrupt the result.

      Weekly reports for thousands of users need bounded fan-out and concurrency. A scheduler can create work incrementally rather than materializing an unlimited number of huge job payloads at once. Track per-item results so a few failures do not force every successful report to rerun.

      Key takeaways

      • Batch large workloads into bounded, individually trackable pieces.
      • Account deletion needs durable intent, access rules and accurate progress reporting.
      • Use resumable steps across systems; a local rollback cannot undo every external change.

      The API contract for unfinished work

      Return a response that describes what is true now. 202 Accepted is appropriate when a requested operation has been accepted but remains unfinished. Include a way to inspect progress; the original HTTP response will not later transform into a completion response. HTTP 202 semantics.

      Example: POST /v1/reports
      HTTP/1.1 202 Accepted
Content-Type: application/json
Location: /v1/jobs/job-842
Cache-Control: no-store

{
  "jobId": "job-842",
  "status": "pending",
  "statusUrl": "/v1/jobs/job-842"
}
      Later: GET /v1/jobs/job-842
      HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "jobId": "job-842",
  "status": "succeeded",
  "resultUrl": "/v1/reports/report-29"
}

      A status resource can expose pending, running, succeeded, failed or canceled states according to your contract. A successful status lookup may return 200 with "status": "failed"; the lookup succeeded even though the background operation did not. Poll with a sensible interval or use a separate notification mechanism.

      A signup can still return 201 Created if the account was actually created, while reporting email delivery as pending. If neither a durable job nor durable intent was recorded, do not claim the work was accepted. Map that failure to an appropriate error and make retried submissions safe.

      Protect job status and result URLs with authorization. An opaque job ID is not permission to read another user's report. Specify result retention and expose safe error descriptions rather than stack traces or provider secrets. These are ordinary API design responsibilities even when execution is asynchronous.

      Key takeaways

      • Report acceptance separately from completion, commonly using 202 plus a status resource.
      • 201 can describe an already-created account while its follow-up work remains pending.
      • Authorize status and result access and define failure and retention behavior.

      Scaling, ordering and provider limits

      Queues absorb bursts, but do not remove work. If jobs arrive faster than workers complete them for a sustained period, the backlog grows. Adding workers helps only while the database, broker, CPU, memory and downstream services can support the additional concurrency.

      ControlPurpose
      Worker concurrencyLimit how many tasks run simultaneously.
      Separate worker poolsKeep long reports or video processing from starving small urgent jobs.
      Rate limitingRespect the provider's total request budget across workers.
      BackpressureSlow, defer or reject new work when capacity cannot meet the contract.
      Ordering scopeSerialize operations for a specific entity only when the domain requires it.

      A concurrency limit is not a rate limit. Ten fast workers can issue thousands of requests per minute. A per-worker limit also multiplies as workers are added, so account-wide provider quotas often need coordinated enforcement. Provider throttling should feed into retry and capacity decisions, as discussed in Caching and rate limiting.

      FIFO delivery does not by itself guarantee completion order when multiple workers, failures and retries are involved. If two changes to one account must stay ordered, use the queue's supported grouping mechanism and/or version-checked state transitions. Avoid imposing one global sequence on unrelated users when per-entity ordering is sufficient.

      Priority queues need a fairness policy so lower-priority work is not starved forever. Track queue age alongside depth: a short queue containing one overdue deletion can be more urgent than a long queue of cheap, newly arrived jobs.

      Key takeaways

      • Scale workers within downstream capacity and apply backpressure when necessary.
      • Coordinate provider rate limits across replicas; concurrency is a different control.
      • Ordering must cover retries and completion, not just enqueue order.

      Focused handlers and worker lifecycle

      Keep a task centered on one useful operation. Sending one report is easier to retry and diagnose than a handler that generates all reports, updates billing and deletes old files. Split work at meaningful checkpoints, rather than turning every helper call into a new job.

      Some tasks, such as encoding a large video, genuinely run for a long time. They need suitable resource limits, execution deadlines, progress reporting and claim renewal. Split or checkpoint them when the processing format allows it; duration alone does not make a task incorrectly designed.

      • Before execution: validate input, confirm required state and detect expired or canceled work.
      • During execution: bound external calls, renew claims when needed and record useful progress.
      • On success: durably record required effects or outputs before acknowledging completion.
      • On failure: preserve diagnostic context and let the retry policy receive the actual error.
      • On shutdown: stop claiming new jobs, drain within a bounded period, then safely release or allow claims to expire.

      Cancellation is cooperative. Marking a job canceled does not recall an email already sent or stop a worker that never checks cancellation. Define which steps are reversible, which are final and how a worker that loses its claim avoids applying obsolete results.

      Workers should use their own scoped service credentials and protect access to payloads and outputs. Do not assume a job remains authorized merely because it sat in a trusted queue; recheck relevant revocation, ownership or cancellation state before sensitive operations.

      Key takeaways

      • Use focused tasks with meaningful retry and checkpoint boundaries.
      • Long work needs explicit timeout, renewal, cancellation and progress behavior.
      • Graceful shutdown and state checks are part of reliable execution.

      Monitoring and a reliability checklist

      A quick API response says little about whether background work is healthy. Measure the whole interval from acceptance to the intended result, as well as the individual worker attempts.

      SignalWhat it helps reveal
      Queue depth and age of oldest eligible jobA growing backlog or work missing its service deadline.
      Enqueue, start and completion ratesWhether processing capacity keeps up with arrivals.
      Queue wait, execution time and total latencyWhere the delay occurs and whether users get results on time.
      Retries, terminal failures and dead-letter countTransient outages, poison messages or broken handlers.
      Worker health, claim expirations and resource useCrashes, stalled processing, lost ownership or exhaustion.
      Outbox age and provider responsesFailures before queue delivery or after the worker contacts a dependency.

      Log the job ID, task type, attempt, correlation ID and a safe error classification. Keep raw passwords, verification tokens and sensitive payloads out of logs. Put high-cardinality job IDs in logs or traces rather than metric labels. Prometheus can collect metrics, while Grafana can display dashboards; alerts still need thresholds, an owner and a recovery procedure.

      Failure cases worth checking

      1. Submit the same logical job twice and confirm that business effects do not multiply.
      2. Stop a worker after its effect succeeds but before acknowledgement; confirm safe redelivery.
      3. Fail publication after a database commit; confirm the durable intent is eventually relayed.
      4. Throttle or time out the provider; confirm bounded retries and visible terminal failures.
      5. Let a job expire, cancel it or change ownership before execution; confirm the worker follows the current policy.
      6. Restart the scheduler and workers during a backlog; confirm missed-run, overlap and shutdown behavior.

      Background processing improves responsiveness by moving when and where work is performed. Reliability comes from the surrounding design: durable acceptance, replay-safe effects, bounded retries, clear status and observable recovery. A queue supplies mechanisms; the application must decide the guarantees it promises.

      Key takeaways

      • Monitor acceptance-to-completion latency, queue age, failure rates and worker health.
      • Use correlated, privacy-conscious logs and actionable alerts.
      • Check duplicate delivery, partial success, outages and restarts before relying on the workflow.
