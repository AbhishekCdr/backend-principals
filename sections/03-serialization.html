    Lesson 03

    Serialization & Deserialization

    A JavaScript client sends an object. A Rust server receives it. The two languages share no data types — one is dynamic and interpreted, the other strict and compiled. So how does one make sense of the other? By agreeing on a common format before either of them starts talking.

    the problem OSI framing common format text vs binary JSON

    The problem, stated precisely

    The setup is the one from Lesson 01: a client — a browser — and a server, running on localhost or somewhere remote in AWS, GCP or Azure. They communicate over a network: HTTP, or gRPC, or WebSockets. We are focusing on HTTP and REST-style communication, and we will assume the client is a JavaScript app — React, Angular, Vue, it does not matter.

    The client sends a request; the server responds; the client parses the response and makes sense of it. That last clause is what this lesson is about. Consider:

    Client

    JavaScript

    Dynamically typed. Not compiled. Objects are loose bags of keys. This is what it wants to send:

    { name: "Abhishek", age: 27 }

    Server

    Rust

    Strictly typed. Compiled. Data lives in structs with fixed field types. Nothing about JavaScript's runtime shape exists here.

    struct User { name: String, age: u8 }

    So: how does a value produced in one language, transmitted over a network, arrive at a machine somewhere else on the internet, get understood in that machine's own type system, have business logic run against it, and come back in a form the original client can understand again?

    Where your responsibility begins and ends

    It helps to know roughly where this sits in the OSI model. If you have studied it you will know the data does not travel as your object — it becomes frames, then packets, then in the end voltage signals and bits over copper or fibre. You do not need to master any of that. What you need is the right mental model:

    The mental model

    At the application layer, your data is in the agreed format — say JSON. Below that, it is converted into frames, packets and eventually 0s and 1s. That is not your concern. Those layers reverse themselves on the other side, and by the time the data reaches the server's application layer it is JSON again. The server only ever reads JSON.

    Your responsibility is the top layer. Everything in between takes care of itself.

    The round trip, layer by layer
    CLIENT                                          SERVER
------                                          ------
JS object                                       Rust struct
   ↓  serialize                                  ↑  deserialize
JSON            ←— application layer —→      JSON
   ↓                                               ↑
frames / packets                                frames / packets
   ↓                                               ↑
0 1 0 1 1 0 …  ←—— the network ——→  0 1 0 1 1 0 …

You own the top line. The rest is somebody else's problem.

    The solution: agree on a standard

    Imagine you were handed this problem cold: two machines in different locations, connected over a network, must exchange data such that either side can parse it — language-agnostically. The obvious answer, and the one the industry landed on, is to define a common standard. Which is a fancy way of saying: come up with a set of rules, and get both sides to agree to them.

    1. Client Serialize

      The client does its work in its own language, then converts the data from JavaScript into the agreed format and sends it over the network.

    2. Server Deserialize

      The server receives the agreed format and converts it into its own representation — a Rust struct — then runs whatever logic it needs to.

    3. Server Serialize again

      To reply, the server converts its struct back into the common format and sends it.

    4. Client Deserialize again

      The client parses it back into JavaScript and carries on.

    Definition

    Serialization and deserialization are the conversion of data to and from a common format — for transmission or for storage — so that the data is domain-agnostic. In this case, language-agnostic: machines written in different languages, running in different environments, can all make sense of it and respond.

    Key takeaways

    • Two languages cannot share types, so the problem is real, not theoretical.
    • Serialize on the way out, deserialize on the way in — on both sides.
    • Your responsibility stops at the application layer; frames, packets and bits handle themselves.

    The landscape of standards

    As with everything in backend, there are far more options than anyone can learn. Here is the map, and where we plant our flag.

    Family 01

    Text-based formats

    Human-readable. Easy to debug, larger on the wire.

    • JSON — the dominant choice for HTTP client–server communication. Roughly 80% of what you will meet.
    • YAML — mostly configuration.
    • XML — older, still present in enterprise and SOAP systems.
    Family 02

    Binary formats

    Not human-readable. Compact and fast, needs a schema and tooling.

    • Protobuf — the most popular; what gRPC uses.
    • Avro, and others — common in data pipelines.
    Why we only cover JSON

    The same reason we cover HTTP rather than gRPC and WebSockets, and Postgres rather than every database: you need one thing that is used everywhere, so you can get experience and pick up the rest as your career progresses. For serialization over HTTP, that thing is JSON.

    JSON

    JSON stands for JavaScript Object Notation. In looks and behaviour it closely resembles a JavaScript object, which explains the name — but it is not limited to JavaScript and turns up everywhere: configuration files, HTTP request and response bodies, and log files (JSON is a very popular choice for structured application logs). Our focus here is transmission.

    Its defining strength is that it is completely human-readable, and its data types are fundamental enough to exist in every language.

    A typical JSON object
    {   ← opening brace
  "id": 42,                          number
  "name": "Abhishek",                 string
  "isActive": true,                  boolean
  "roles": ["admin", "editor"],       array
  "address": {                        nested object
    "country": "India",
    "phone": 3456
  },
  "deletedAt": null                  null
}   ← closing brace

    The rules, in full

    RuleDetail
    Braces An object has an opening { and a matching closing }. Every nested object too.
    Keys are strings Keys must be inside double quotes and must be strings. You cannot use any other data type as a key. Not single quotes — double.
    Allowed values A string, a number, a boolean, null, an array, or another object.
    Nesting is recursive A nested object obeys exactly the same rules as the outer one: double-quoted string keys, values of the permitted types.
    That really is the whole specification

    There is no advanced JSON to learn. Braces, double-quoted string keys, a short list of value types, and recursion. Its simplicity is why it won.

    Key takeaways

    • Text formats (JSON, YAML, XML) are readable and bigger; binary formats (Protobuf, Avro) are compact and need a schema.
    • JSON is the default for HTTP because it is simple and universally understood.
    • The rules: braces, double-quoted string keys, six value types, recursion. Nothing more.

    Watching it happen

    Take the demo from Lesson 02 and look at it again — this time paying attention only to the data format rather than the route. Fire POST /api/books and open the request in an HTTP inspector.

    Request — what the client serialized
    POST /api/books HTTP/1.1
Content-Type: application/json

{
  "id": 4,
  "title": "The Pragmatic Programmer",
  "author": "Hunt & Thomas"
}

    Exactly the structure we described: braces, double-quoted string keys, one number and two strings. This is what goes onto the network.

    Response — what the server serialized back
    HTTP/1.1 201 Created
Content-Type: application/json

{
  "data": [
    { "id": 1, "title": "Clean Code",               "author": "Martin" },
    { "id": 4, "title": "The Pragmatic Programmer", "author": "Hunt & Thomas" }
  ]
}

    The server took the incoming JSON, deserialized it into its own types, added the record, then serialized the whole collection back out. Note the shape: an object whose data key holds an array, each element itself a JSON object obeying the same rules. The client receives it, parses it, and renders it.

    And the language on either end is irrelevant

    In this demo the client is JavaScript, but it could be PHP, Swift or a Go program. The server could be Rust, Python or Ruby. Neither side knows or cares — that is the entire payoff of agreeing on a format.

    Where that leaves us

    Serialization and deserialization have very few concepts to them. It is less a technique to master than a phenomenon to be aware of: the client serializes to a common format, the server deserializes it, understands it, performs its business logic, serializes its answer back, and the client deserializes that. That whole round trip is what the words mean.

    If you remember three things
    • Two languages cannot share types, so they share a format instead.
    • Your responsibility stops at the application layer — frames and packets are not your problem.
    • JSON: braces, double-quoted string keys, six value types, recursion. That is all of it.
